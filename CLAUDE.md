# CLAUDE.md - Project Conventions and Guidelines

## Project Overview
Narrative Modeling App — an AI-guided platform that democratizes machine learning by helping non-expert analysts build, explore, and deploy models without writing code.

> Per-issue implementation history lives in git/PRs, not here. This file holds durable conventions only.

## Architecture

### Frontend (`apps/frontend/`, Next.js)
- App Router, TypeScript strict, Tailwind CSS
- NextAuth v5 (Google, GitHub); frontend mints an HS256 JWT (`sub=userId`) in the session callback for the backend to verify. **That `session.apiToken` is the only credential that may reach the backend (#527).** The OAuth provider's access token is not persisted in the JWT and does not exist on the session any more — three call sites had been forwarding it (Google's credential, sent to our API) and one route sent the literal `"default"` when it had nothing, which the backend rejects but which was only ever one config change from a user. A proxy route with no `apiToken` answers 401; it never forwards a placeholder. `__tests__/lib/noProviderTokenForwarding.test.ts` greps the frontend for `session.accessToken`, `Bearer nextauth-` and `|| 'default'` so the class cannot return.
- **Tailwind v4, CSS-first (#345):** there is **no `tailwind.config.*`** — the whole theme lives in `app/globals.css` via `@theme` / `@theme inline`, `@utility`, `@custom-variant dark`, and `@plugin` (which is the *only* way plugins load; a plugin in `package.json` is not wired until it has an `@plugin` line). Never wrap a theme token in a colour function: the tokens are `oklch`, so `hsl(var(--token))` composes to invalid CSS that browsers **drop silently** — that shipped ~35 dead utilities and a wholly non-functional dark mode, green the whole time. Every semantic token needs a `-foreground` pair defined in **both** `:root` and `.dark`. `__tests__/styles/themeTokens.test.ts` compiles `globals.css` through real PostCSS and guards all of this; component tests can't, since they never run Tailwind.

- **Dark mode is live (#407):** `next-themes` (`attribute="class"`, `defaultTheme="system"`) via `components/ThemeProvider`, toggled from the sidebar. `attribute` MUST stay `class` — `@custom-variant dark (&:is(.dark *))` keys on it, and the `data-theme` default would silently make every `dark:` utility dead again, which is the state #407 found. Components use **semantic tokens** (`bg-card`, `text-foreground`, `text-muted-foreground`, `bg-muted`, `border-border`), never `bg-white`/`text-gray-900`/`bg-gray-50` — those stay light in dark mode and render text invisible. `__tests__/styles/semanticColours.test.ts` enforces this repo-wide; `components/Sidebar.tsx` is the one exemption (deliberately dark in both themes). jsdom has no `matchMedia`, so `jest.setup.js` polyfills it — every suite rendering through the root layout needs it.
- **Public pages are exactly two prefixes (#473):** `middleware.ts` is deny-by-default, and only `/auth/` and `/legal/` are exempt (plus `/api/`, which self-guards with 401). Both checks keep the **trailing slash** so the exemption cannot leak onto a lookalike route — `/legality` stays protected. **Any route added under `/legal/` is public by construction, not by review** — the prefix check cannot tell a policy page from an admin tool for editing one, so a new file there is unauthenticated the moment it exists. `/legal/terms` and `/legal/privacy` must stay anonymous-reachable: Stripe's reviewers, regulators and prospective customers all read them before an account exists, and behind the session wall they satisfy nothing. Their identity, jurisdiction, refund window and sub-processor table live in one place, `lib/legal/company.ts`, which the pages and their tests both read — the sub-processor list is a legal claim, so every row is traceable to the code that sends the data (notably `dataset_summarization.py`, which ships up to 5 sample rows of the customer's dataset to OpenAI). Retention wording is deliberately no stronger than the cascade actually performs, so tightening erasure means loosening the policy text, not the other way round. As of #497 the live cascade *does* remove trained models, training jobs and their S3 artifacts (`erasure_service._erase_models` + `model_storage.delete_model`, proven against real S3 in `test_erasure_model_artifact_localstack.py`); the only residual is the bounded backup window in `lib/legal/company.ts` (Atlas weekly snapshots), so the policy text may now understate erasure rather than overstate it.
- **`/admin` is authorised, not just authenticated (#477):** `middleware.ts` rewrites `/admin` and `/admin/*` to Next's not-found route unless the session token's email is on **`ADMIN_EMAILS`** (`lib/admin-allowlist.ts`), so a signed-in tenant gets the same 404 as for a page that does not exist. The rewrite target is Next's *internal* not-found route, so a unit test can only pin the rewrite header — the HTTP status is checked against a real build: `next build && next start`, mint a session with `@auth/core/jwt`'s `encode` (salt `authjs.session-token`), and `curl -o /dev/null -w '%{http_code}' -H "Cookie: …" /admin` must print 404 for a non-listed email (verified on 16.2.12; the RSC navigation fetch legitimately answers 200 with the not-found tree in the payload). Since #613 the blocking `@smoke` job repeats that check on every run against the **dev server** (the e2e stack is `next dev`; the production-build recipe above stays the manual check for `next start`-only rendering differences): `e2e/workflows/admin-guard.spec.ts` requests `/admin` as a document for the ordinary test user (404, no "Admin Dashboard") and for a second dev-credentials identity that `test-e2e.sh` puts on `ADMIN_EMAILS` (`TEST_ADMIN_EMAIL`, 200 with the heading) — the ordinary user is a non-admin by construction, not because the variable happened to be unset. The allowlist **fails closed** — unset means nobody is admin, the opposite of `INVITE_ALLOWLIST`'s empty-means-open — and it is the only admin concept in the codebase; there is no role field. `session.isAdmin` is computed server-side in the `auth.ts` session callback purely so the sidebar can hide the link; never make a route decision from it on the client. The admin page's only backend calls (`/health/status`, `/health/metrics`) do not exist (#479); whatever #479 adds must carry its own admin check, because nothing on the backend mirrors this allowlist yet.
- **`getToken` in middleware must match the cookie Auth.js actually wrote (#469):** over HTTPS Auth.js writes `__Secure-authjs.session-token` (secure prefix, and `salt` === that name); over http (dev/e2e) it writes the bare `authjs.session-token`. `getToken({ req, secret })` with no `secureCookie` defaults to the **bare** name and bare salt, so on the production/staging HTTPS URL it reads nothing and `middleware.ts` redirects **every** authenticated page to sign-in — invisible to CI, which runs over `http://localhost`. `middleware.ts` reads whichever cookie is present (secure variant first, then bare) rather than detecting HTTPS, which is unreliable behind the TLS-terminating nginx; `secureCookie` cascades to both `cookieName` and `salt` in next-auth beta.32, so passing it alone selects the matching pair. Never re-add a raw-header presence-guard keyed on `${name}=`: it misses Auth.js's chunked cookies (`<name>.0`, `.1`, … for oversized OAuth sessions, which `getToken` reassembles), and the bare name is a substring of the secure one. `__tests__/middlewareSecureCookie.test.ts` exercises the **real** `getToken` against a real `encode`d cookie (the mocked-`getToken` `middleware.test.ts` is blind to this); that needs `next-auth`/`@auth/core`/`jose`/`@panva/hkdf` (ESM-only) injected into `next/jest`'s `transformIgnorePatterns` in `jest.config.js`. Tradeoff of reading both variants: the middleware no longer relates to the request scheme, so it accepts a **bare** `authjs.session-token` even over HTTPS — the `Secure` attribute's browser-level protection is no longer the only gate against a same-name cookie written from a sibling subdomain sharing `Domain=` (cookie-tossing). JWT signature+expiry verification is the real backstop (an attacker without the signing secret still can't forge a valid token); accepted because edge middleware cannot see through the TLS-terminating nginx.
- **Right-to-erasure has a UI now (#482):** `app/settings/page.tsx` (the `/settings` landing — the sidebar linked here and it 404'd, #528) hosts "Delete my account data" → `POST /users/me/erase`, and the dashboard's recent-datasets rows carry a per-dataset erase → `POST /datasets/{id}/erase`. Both go through `lib/services/erasure.ts` (the only caller of those routes) and the shared `components/settings/ErasureConfirmDialog.tsx`, which gates the destructive action behind typing an exact word (`DELETE`, or the dataset name), surfaces the returned `DeletionManifest`, and — importantly — treats a manifest with `failures`/`completed_with_residuals` as an error to retry, never success (`hasResiduals` in `lib/types/erasure.ts` mirrors the backend `status`). The "what is retained" copy must track #480: billing (Subscription/Usage) is kept because `erase_user` keeps the account active. An account-erasure `@smoke` e2e is deliberately NOT run: every spec shares the one ordinary e2e user (`test-user-12345`), so a real account wipe would destroy the shared fixture — the smoke spec erases the test's own uploaded dataset instead, and the account flow is jest-covered.
- **Every `page.tsx` route must be reachable from navigation, and a guard enforces it (#528).** `/settings/billing` — the checkout entry point — shipped with **zero inbound links** and was unreachable; a page renders fine in isolation, so only a source-level check catches this. `__tests__/navigation/routeReachability.test.ts` (modelled on the backend's `test_every_router_is_mounted.py`) fails on any `app/**/page.tsx` route that no navigation reaches. It models the three real ways a route is reached — `href`/`push`/`replace`/`redirect`/`route:` literals (plain and template), the **workflow-stage config** (`lib/types/workflow.ts` `route:` entries, navigated via `WorkflowBar`/dashboard/quickstart through `buildStageUrl`; this is why `/evaluate`, `/features`, `/deploy` have no `href=`), and framework roots (`/` plus the NextAuth pages **derived from `auth.ts`'s `pages:` config**, not a `/auth/` prefix — a prefix would silently exempt any future `app/auth/` orphan). It is "referenced at least once", not a full graph walk, so a page linked only from another orphan is not yet caught. Genuinely-unreachable pages are allowlisted with a reason + tracking issue in `KNOWN_ORPHANS`; the anti-stale assertion fails if an allowlisted route becomes reachable or is deleted, so the list self-cleans. Current allowlist: `/recipes` and the legacy dataset-scoped `/datasets/[id]/engineer` flow (#738).
- **A space between an interpolation and the prose after it can vanish in the server render (#473).** Observed once, in a `<p>` whose JSX line *began* with `{expr}` and carried a second one mid-sentence: the served HTML read "Narrative Modeling Appservice" while jsdom rendered it correctly, so the component test stayed green. The obvious generalisation ("two interpolations on a line") does **not** hold — sibling lines with the same shape render fine, so do not go hunting by shape. Write `{' '}` explicitly after any `{expr}` followed by prose and the question never arises. No component test can see this; the check is `curl <page> | grep -E '[A-Za-z0-9.,)]<!-- -->[A-Za-z0-9(]'` against a running build, which flags every glued text-node boundary on the page.

### Backend (`apps/backend/`, FastAPI)
- Async FastAPI, MongoDB via Beanie ODM, AWS S3 for files, `BackgroundTasks` for AI/ML work
- Canonical Beanie model registry: `app/models/registry.py` (shared by app lifespan + `setup_database` fixture)

### MCP Server (`apps/mcp/`, FastMCP)
- Exposes `eda_summary_tool` over SSE; called by the backend on the same host. Entry point `main.py`. FastMCP from the installed `mcp` SDK (`mcp.server.fastmcp`), not vendored.
- **The backend client speaks real MCP over SSE (#506), not REST.** `app/services/mcp_integration.py` uses the `mcp` SDK (`sse_client` + `ClientSession` over the `/sse` stream, bearer token) and calls the tool by its registered name **`eda_summary_tool`** with a single `params` object **`{dataset_id, user_id}`** (`EdaInput`); the server reads the dataset from S3 server-side and authorizes ownership, so the client never sends dataset contents. Bound **both** `timeout` and `sse_read_timeout` by `MCP_TIMEOUT` (tool results arrive over the SSE stream; the SDK's read default is 300s). A `{success: False}`/transport failure **falls back**, never fabricates analysis. The pre-#506 client POSTed to nonexistent REST paths, `await`ed httpx's sync `.json()`, and used a wrong tool name/args — a test mocking an `AsyncMock` response hid all three.
- **`apps/backend` is deliberately NOT a package (no `__init__.py`) (#506).** Restoring one puts the repo `apps/` dir on pytest's `sys.path`, and the sibling `apps/mcp` package (literally named `mcp`) then **shadows the installed `mcp` SDK** during backend tests (`import mcp` → `apps/mcp`). Any backend import of the `mcp` SDK breaks the moment that file returns. A backend test that starts the MCP server as a subprocess must `pytest.skip` (not `require_service`) when `apps/mcp` isn't synced — the `backend-integration` job runs `CI_REQUIRE_SERVICES=true` and never syncs the sibling app, so `require_service` would fail the gate.

## Backend Conventions & Recurring Gotchas
- **`app/api/routes/__init__.py`'s `api_router` is attached to nothing (#471, removal in #530).** A router registered only there is dead: the whole data-issues feature 404'd that way while the frontend called it. Mount routers in `app/main.py` directly; `tests/test_api/test_every_router_is_mounted.py` walks the live route table and fails on any route module that is not mounted unless it is allow-listed there with the reason (`trained_model`, legacy CRUD). A feature that has never been reachable has never had its authz, metering or error paths exercised — review it as new code when you mount it (#471 needed `quota("ai_calls")` on `/detect`, released when the analyzer did not run, and the metering registry now follows one import hop so a route reaching a model *through a service* is in scope).
- **Two model surfaces:** `MLModel` (routes under `/api/v1/ml/`) is the **real** trained-model surface — build everything here. `ModelConfig` (`/api/v1/models/`) is **dead legacy**, never created by the training flow; its train/deploy/performance routes are `410 Gone`. Bot plans (Traycer/CodeRabbit) routinely target the wrong one.
- **Schema ↔ type mirrors:** backend Pydantic schemas mirror frontend TS types — change both together. Notably `app/schemas/evaluation.py` ↔ `apps/frontend/lib/types/evaluation.ts`.
- **`MLModel` mock fixture:** adding any optional `MLModel` field breaks the `sample_ml_model` MagicMock under `response_model=MLModel` validation unless the fixture sets it. Recurs constantly.
- **New optional fields degrade:** add `MLModel`/schema fields as optional/defaulted so pre-existing models still validate and endpoints return `partial=true` rather than 500.
- **Route order:** register specific `/ml/{model_id}/<sub>` routes **before** the catch-all `/{model_id}`.
- **Every handler in an authenticated router carries the auth dependency itself (#450, #563):** routers are mounted without router-level `dependencies`, so a handler that forgets `Depends(get_current_user_id)` is public by construction — `/ai/health` sat that way, reporting internal deployment state and making an outbound MCP call for anyone. A health-style endpoint belongs in `health.py` only if it is a readiness dependency of the app; otherwise it is authenticated like its siblings. **`/health/ready` is MongoDB-only and makes no outbound third-party call (#503):** it is unauthenticated and polled constantly by LBs/uptime monitors, so a per-request OpenAI call or blocking boto3 `head_bucket` there was a cost-amplification DoS + event-loop stall. Readiness answers "can THIS instance serve traffic" (Mongo reachable → 200, else 503 — the contract the Docker/compose healthchecks read); the "is every upstream healthy" question lives at the **authenticated, rate-limited** `GET /api/v1/health/dependencies` (mounted on `liveness_router` so it inherits the `/api/v1` `RateLimitMiddleware` — an authenticated-but-unthrottled root path would still be loopable). Any I/O in a health check is non-blocking (the S3 probe is `asyncio.to_thread`-offloaded). `/health` and `/health/live` stay trivial. The admin `/health/status` (#479, P1.3) can wrap the diagnostic with the admin allowlist.
- **AI services:** OpenAI (JSON mode) behind the shared circuit breaker + a deterministic rule-based fallback — endpoints must work fully **without** an API key. **Every OpenAI client is built through `app/utils/openai_client.py` (`build_openai_client` / `build_async_openai_client`), never `OpenAI(...)`/`AsyncOpenAI(...)` directly (#501)** — the factory sets a request `timeout` (else a hung upstream blocks past `gunicorn --timeout 120` and the worker dies) and `max_retries=0` (the circuit breaker is the only retry layer; stacking the SDK's own retries under 2–3 breaker attempts made worst-case latency unbounded). `OPENAI_REQUEST_TIMEOUT` (default 30s) is **clamped** to a ceiling derived from the worker timeout × max breaker attempts so a misconfigured env value can't reintroduce the worker-kill. `tests/test_utils/test_openai_client_registry.py` bans a raw construction anywhere in `app/`. **The synchronous client must never be called inline in an async function** — wrap it in `asyncio.to_thread` (the async `AsyncOpenAI` client is the alternative), or it blocks the event loop for the whole round-trip; this bit the AI-summary background task that fires after every upload.
- **Removable dependency levers:** heavy optional deps live in PEP 735 `[dependency-groups]` (`interpretability` = shap/numba stack; `tuning` = optuna), kept in `default-groups`, lazy-imported. Slim image: `uv sync --frozen --no-dev --no-group <group>`; the app degrades gracefully.
- **Error handling (#269):** central handlers in `app/middleware/error_handlers.py` sanitize **all 5xx** (generic body + `X-Request-ID`, never echo `str(e)`) and pass 4xx validation text through. Do not reintroduce `str(e)` in 5xx bodies. The sanitiser never sees a **200 `{success: false}`** body, and those used to carry `error=str(e)` too (data-issues, transformations — #637): a handler that reports failure in a 2xx body uses `internal_error_message("<What>")` from the same module (fixed sentence + the request id as the reference the operator greps the logs for) and logs the traceback with `logger.exception`; domain errors with a user-facing `.message` (`ValidationError`, `OperationError`) are the only exception text that may pass through. `tests/test_api/test_error_bodies_are_sanitized.py` forces a failure into every such route and asserts the body carries neither the message nor the S3 key. **Background jobs are the third surface (#518):** a failed training or batch job stored `str(exc)` as its user-facing error (`TrainingJob.error`, `BatchJob.error_message`, both shown in the job UI), leaking the same internals. Both failure paths now store `app/utils/job_failures.py::user_safe_failure_reason(exc)` — a classified, actionable sentence for the known recoverable modes (single-value target, too-few-rows, invalid CSV, could-not-determine-task, …) or a generic "quote your job id" fallback — and log the raw exception via `logger.exception` correlated by model_id/job_id. Add a new known failure mode to the classifier, never `str(e)` back into the job's error field.
- **Onboarding progress lives in its own `OnboardingProgress` collection, keyed by `user_id` (#541).** It is account-scoped state, not dataset state — it used to be smuggled onto an arbitrary `UserData` (and for a user with no dataset the save built an invalid `UserData` with no filename/s3_url, raising at step one). `_get_or_create_user_progress` reads through to the legacy `UserData.onboarding_progress` field once (migrated forward on next save); `_save_user_progress` is one atomic `update_one(upsert=True)` on the unique `user_id` index (concurrent first saves converge, no DuplicateKey 500). It is swept by erasure. The sample-dataset loader uploads a REAL S3 object via `dataset_s3_key`+`upload_file_to_s3` (no temp file, no fabricated URL).
- **Two dataset id-spaces:** `DatasetMetadata` (string `dataset_id`, S3 `datasets/{user}/...`, string-keyed children) and legacy `UserData` (ObjectId, `Link` DBRef children) are **dual-written**, linked only by `(user_id, s3_url)`. Deletion cascades across both via `DatasetErasureService` (#259). **That link is mutable, so every writer that moves a dataset to a new file must move both twins (#467):** go through `app/services/dataset_link.py::record_new_file(doc, new_url)`, which finds the twin through the *old* location and points both `file_path` and `s3_url` at the new one (the first move keeps the upload in `DatasetMetadata.source_s3_url`). Writing `s3_url` on one side alone is how erasure lost the PII-carrying twin and training — which reads `UserData.s3_url` — kept using the pre-transform file while the UI showed the transformation applied. `scripts/inventory_dataset_links.py` counts pairs whose link is already broken. **Every superseded current-file is tracked and erased (#525):** `record_new_file` appends the old `s3_url` to `superseded_s3_urls` (on both twins) on every move, because once `s3_url` moves off an object nothing else references it (a `DatasetVersion` points at a *separate* `versions/` copy, not the `transformed/` current-file). Erasure (`_erase_one_dataset`) sweeps `source_s3_url` + every `superseded_s3_urls` entry + the `DatasetVersion` objects, so a GDPR deletion reaches the whole lineage, not just the latest object. `scripts/inventory_orphaned_s3_objects.py` reports pre-#525 orphans (count + size); `scripts/reconcile_model_artifacts.py` does the same for model artifacts. **The BACKWARD writers move both twins too (#629):** `history_service`'s `undo`/`redo`/`jump_to_position` set `file_path` alone, leaving `s3_url` and the twin at the pre-navigation file — training then read the state the user just undid. They now go through `record_new_file(dataset, version.s3_url)` like the forward writers, and must set the restored **version's** `num_rows`/`num_columns`/`columns` on the dataset first, since `record_new_file` copies the doc's shape onto the twin and `model_training` reads `num_rows`/`num_columns` off the twin for the mode recommendation. Because undo/redo **revisit** URLs, `record_new_file` keeps the invariant **the current file is never in `superseded_s3_urls`** (it drops `new_url` from the list when setting it current), or erasure would delete the live file on a move-back; harmless no-op for the forward writers, which never revisit.
- **Erasure deletes only from its own bucket (#616):** `erasure_service._s3_key(url_or_key, bucket_name, manifest)` refuses a stored URL that names a bucket other than the one erasure runs against — the key goes on the manifest as a failure naming both buckets and nothing is deleted, because deleting that key from *our* bucket would remove whatever unrelated object shares the name. Bucket-less URLs fall back to the configured bucket; bare keys pass through. The failure is prefixed `s3 delete` so that, like every other S3 residual, it does **not** block the parent's Mongo deletion (`_delete_parent_if_clean` only retains a tombstone for Mongo-child failures) — a stored URL never changes between runs, so a blocking failure would make that dataset permanently un-erasable.
- **`erase_user` erases the user's data but keeps the account (#480):** its only caller is `POST /users/me/erase`, which deletes data, not the auth record. `_sweep_user_scoped` deletes every account-scoped collection the user owns — `APIKey` (the auth path does a live `find_one({key_hash})` per request with no cross-request cache, so deletion revokes immediately), the feature store (`StoredFeature`/`FeatureVersion`, the latter keyed by parent `feature_id` not `user_id`, so resolve owner feature ids first/`FeatureCollection`), and recipes (`TransformationRecipe`/`RecipeExecutionHistory`/`SharedRecipe`) — but **retains `Subscription` and `UsageRecord`**: the account stays active and billable, so deleting the local Subscription mirror would enforce a paying customer as FREE until the next Stripe webhook and deleting UsageRecord would reset quota mid-period. That is live account state, not orphaned data; full billing teardown belongs to an account-closure flow that does not exist yet. A recipe the user shared onward lives in the *recipient's* row (`user_id`=recipient), so it is not swept by user_id — its `original_owner_id` **and** the duplicate `metadata.shared_by` are anonymized to a tombstone rather than deleting the recipient's copy. The same "scrub the co-tenant's row, don't delete it" rule covers two more cross-tenant residuals: a `BatchJob` owns S3 objects (`input_path`/`output_path` under `batch-jobs/{user}/…`), swept via `_erase_batch_jobs` through the one S3 core in both the user sweep and the model cascade (#661); and the erased id can sit in **another** tenant's `StoredFeature.shared_with` / `FeatureCollection.shared_with`, `$pull`ed from every co-tenant's ACL (#662). Both record their counts on the manifest.
- **Chunked upload (#454, #462, #463, #464):** the flow was broken end-to-end until #582 and its four defects had to land together, so treat it as one surface. Init takes **`Form(...)`**, not query params — the client posts a url-encoded body, and the mismatch 422'd every init before the handler ran. Sessions are owned: `init_upload` records `user_id`, ids come from `secrets.token_urlsafe` (never derived from filename/size/timestamp), and every operation resolves through **`get_session(session_id, user_id)`**, which returns `None` for both unknown and foreign ids so the two answer identically — a distinguishable response confirms another tenant's session id exists. Session ids are also spliced into filenames under `temp_dir`, hence the `[A-Za-z0-9_-]` guard. `complete` **claims** the session (reads and removes it in one synchronous step) before any await: there is no await between the lookup and `user_data.insert()`, so two racing completes otherwise both pass the checks and write two S3 objects, two `UserData` rows and two charged quota units, both 200 so nothing refunds. **Concurrency is derived from live sessions, not a leaky counter (#526):** the per-user cap is `_active_upload_count = ChunkedUploadHandler.count_active_sessions(user)` (non-expired chunked sessions) **+** `RateLimiter.active_uploads[user]` (transient, always-`finally`-balanced work: every `/upload/secure` request and every chunked `complete` finalization). `init` does NOT `start_upload` — the live session *is* the count, so an abandoned session (closed tab) stops counting at expiry and can never permanently lock the user out (there is no counter to forget on a missing `complete`/`abort`). `complete` takes a transient slot *after* claiming (which popped the session) so the parse+S3+insert still counts, released in `finally`. Both `/secure` and chunked `init` check the same combined total, so it is one shared budget. **`upload_chunk` holds a per-session `asyncio.Lock` around its read-modify-write (#580):** without it, two concurrent POSTs of the same not-yet-uploaded chunk both passed the `already_uploaded` check and both appended, and that duplicate could make `len(uploaded_chunks) == total_chunks` fire while a *different* chunk was still missing — flipping a holed session to `complete`. The membership check must be atomic with the append, so the file write is inside the hold (concurrent *different* chunks of one session serialize). Locks are created lazily (no `await` between the get and the insert, so race-free on the loop) and swept when their session is gone. Like the session dict, the lock is **per-worker** — two gunicorn workers racing the same chunk are still unguarded; the durable fix is the Redis-backed store the `# In production, use Redis` note anticipates. (Before #526: one `start_upload` at init leaked when the session was abandoned; the chunk route's *double*-release had pinned the count at 0, hiding the cap until #582.) S3 keys are **server-derived**, `datasets/{user_id}/[masked_]{uuid}.{ext}`, built only by `dataset_s3_key` in `app/utils/s3.py` — every dataset-writing route (`/upload/`, `/secure`, `/confirm-pii-upload`, chunked `complete`, and `/datasets/upload` since #496) calls it, and there is deliberately no helper that can express a key without the owner (#581 deleted `generate_s3_filename`, which three routes were still reaching for). The client filename is metadata only and must never reach the key. Objects written before #581 sit at the bucket root as bare `{uuid}.{ext}`; `scripts/reconcile_unprefixed_s3_keys.py` moves them under their owner (copy, verify ETag+length, rewrite `UserData`/`DatasetMetadata`, then delete; orphans reported, never touched; dry-run by default). Erasure's `_s3_key` derives keys through the same `parse_s3_url` the readers use (#481) — the hand-rolled parser it replaced returned `bucket/key` for endpoint-style URLs and kept presigned query strings, so `delete_object` matched nothing and erasure reported success over a surviving object. The sibling routes `/secure` and `/confirm-pii-upload` still enforce a high-risk-PII confirmation gate the chunked route does not (#583).
- **Client filenames are normalised at the model (#585):** `UserData` and `DatasetMetadata` run `sanitize_filename` on `filename` / `original_filename` — basename only, no control characters, no leading dots, ≤255 chars, never empty — so every writer (`/upload/secure`, `/confirm-pii-upload`, `/chunked/{id}/complete`, `/upload/`, `/datasets/upload`, and the next one) stores the same safe form. Both documents also set `Settings.validate_on_save = True`: Pydantic validates on construction, not on assignment, so `PUT /user_data/{id}`'s `setattr` path skipped the validators until save re-ran them and no consumer building a `Content-Disposition` header or a path from them has to know they were once raw. The S3 key never came from the filename (#464); this closes the stored copy. Normalise rather than reject: exporters produce odd-but-honest names, and a raw copy "alongside" would keep the trap.
- **One bucket, one resolver, readers and writers alike (#567, #621, #622):** `app.config.resolve_configured_bucket()` (`AWS_S3_BUCKET`, then the historical names) is the only precedence; `utils.s3.configured_bucket()` / `allowed_bucket()` delegate to it, `S3Service` and `VersioningService` read through them **per call** (`VersioningService.bucket_name` is a property; `S3Service` writers use `_live_bucket()`), and there is no `settings.S3_BUCKET` — it was a third precedence frozen at import. Every `S3Service` write method (`upload_file_obj`, `delete_file`, `get_file_size`, `generate_presigned_url`) runs its key through `validate_object_key(..., allow_legacy_root=True)` before touching boto3, exactly like `download_file_bytes`; a new writer must build a namespaced key (`datasets|transformed|models|batch-jobs|exports/{tenant}/…`). `validate_object_key` is bucket/traversal/namespace hygiene, **not** per-tenant authorization — pass an ownership-checked key. `tests/test_services/test_s3_write_contract.py` sets three env names to three values and asserts every resolver and both services agree. **No call site may read the bucket env vars itself (#507):** resolve only through `configured_bucket()`/`allowed_bucket()` — `test_s3_write_contract.py::test_no_call_site_resolves_the_bucket_independently` greps `app/` and fails on a raw `os.getenv("AWS_S3_BUCKET"|…)` outside `config.py`, which is how the upload presign and the health readout had drifted onto their own precedence. **Startup fails fast on a missing/unwritable bucket (#495):** the lifespan calls `s3_service.verify_bucket_writable()` **only when `is_production_like()`** — it raises on no configured bucket, on mock-mode credentials in production, or on a failed put+delete write-probe, so a deploy refuses to boot rather than write to a guessed bucket (and it catches a broken credential rotation, P1.33). The `_live_bucket`/reader default `"narrative-modeling-dev"` is therefore dev-only-reachable; in production the boot check fires first. dev/test/CI skip the probe (`is_production_like()` is False), so it never trips a test that boots the app via `LifespanManager`.
- **Every boto3 S3 client is built through `create_s3_client()` with a bounded Config (#519).** The factory always attaches a `botocore.config.Config` — `connect_timeout=5`, `read_timeout=20`, standard retries `max_attempts=3`, `max_pool_connections=20` (env-overridable), path-style merged in for an `AWS_ENDPOINT_URL` — so a hung S3 endpoint can't outlive the 120s gunicorn worker (worst case ≈ `attempts × (connect+read)` ≈ 80s; `read_timeout` is the per-socket-read idle, not a transfer cap, so it never truncates a streaming download). Never construct a raw `boto3.client("s3", ...)`. `get_s3_client()` (the utils entry) **reuses** one client, keyed on a `(access-key, secret, endpoint, region)` signature so a rotation or endpoint change rebuilds on its own; it stays lazy (returns `None` on missing env, so secret-less builds don't crash) and shares the thread-safe *client*, never the session. `reset_s3_client()` clears the cache (tests / post-rotation). `S3Service`/`VersioningService` build once at construction. Known residual: `download_file_from_s3` still builds per call (bounded Config applies; reuse is #722).
- **Which S3 location to download (#170, #466):** `s3_url` is always a URL; `file_path` is a **raw key** right after an upload and a **full URL** once a transformation has written one back. The validated downloader takes only URLs, so `file_path or s3_url` handed a key to it and the *first* transformation on every dataset failed while every later one worked. Never branch on the shape yourself — go through `app/utils/s3.py::downloadable_url(file_path, s3_url)`, which passes a URL through and places a key in the allowed bucket; the strict resolver then checks it like any other URL. `S3Service.download_file_bytes` is the one *key-only* entry point — feed it the key from `resolve_validated_object(downloadable_url(...), allow_legacy_root=True)` (bucket allowlist checked *before* the key is extracted; the allowance keeps pre-#581 root-level datasets readable until #615), never `file_path` directly. Only a LocalStack test (`tests/test_integration/test_transformation_first_apply_localstack.py`) can see this class of bug; a mocked downloader accepts anything.
- **`file_type` must track `s3_url`, and the loader enforces it against the bytes (#524).** A transformation rewrites `s3_url` to a `.parquet` object; `app/services/dataset_link.py::record_new_file` writes the matching `file_type` (from the new extension) in the same operation on both twins (#467/#630), so the pair can't diverge going forward. Note `visualization_cache.py` / `feature_store_service.py` still `read_csv` unconditionally (no `file_type` dispatch) — a pre-existing gap, not covered here.
- **`UserData.id` is an ObjectId; a request id is a string (#465):** `UserData.id == file_id` and `{"_id": request.dataset_id}` build `{"_id": "<str>"}` and match nothing — ten endpoints answered a permanent 404 while their tests patched `find_one` and stayed green. Coerce with `app/utils/object_id.py::require_object_id(value, what)` (400 on a malformed id); only `Document.get(str)` is coerced by Beanie itself. A handler that wraps its lookup in `try/except Exception` must `except HTTPException: raise` first, or the 404 becomes a 200 `{success: false, error: "404: …"}` — which is what the four `transformations.py` handlers did. Tests for a lookup must seed a real document; a patched `find_one` cannot see this class of bug.
- **One S3 download core (#531, #567):** every read of a stored URL or key goes through `app/utils/s3.py` — `resolve_validated_object()` (parse → `allowed_bucket()` → `validate_object_key()`) and `check_object_size()`. Exactly one `get_file_from_s3` (utils, BytesIO) and one `download_file_from_s3` (`s3_service`, temp file) exist, both on that core; `S3Service.download_file_bytes` validates its key the same way. **No route or service may call boto3's `get_object`/`download_file*` itself** — `tests/test_services/test_s3_download_registry.py` finds any raw download outside the core and fails, which is how `column_stats.py` and the preview route were caught bypassing the allowlist. The BytesIO reader alone admits the pre-#581 root-level `(masked_){uuid}.{ext}` shape (`allow_legacy_root=True`) because production `UserData.s3_url` still points at those objects until the operator runs #615; that flag is the one line to flip afterwards. The temp-file path stays strict. **Only the download surface is validated:** `S3Service.upload_file_obj`, `delete_file`, `get_file_size` and `generate_presigned_url` take server-derived keys against the configured bucket without going through the core — do not hand them client input. Every reader now pays one `head_object` for the size cap before the read.
- **Transformation engine contract:** the engine executes exactly **4** types — `TransformationEngine.TRANSFORMATION_CLASSES` = `remove_duplicates`, `trim_whitespace`, `drop_missing`, `fill_missing`; `FILL_MISSING` uses `method` (mean/median numeric-only, plus mode/ffill/bfill) and is how imputation is exposed. **`GET /transformations/available` is derived from that registry via `available_transformations()` (#499), never a hand-list** — it once advertised ~22 types while 4 executed, so ~18 menu entries failed or silently did nothing. Display metadata (`CATEGORY`/`LABEL`/`DESCRIPTION`/`PARAMETERS_SCHEMA`/`REQUIRES_COLUMNS`) lives on each transformation class; `test_transformation_available_registry.py` asserts advertised == executable and that every advertised type runs. **The config UI (`TransformationConfigDialog.tsx`) treats a param as required unless its schema has `required: false` or a `default`** — every advertised param is optional at the engine level, so each must be marked `required: false` (guarded by the same test) or default-behavior flows are unconfigurable. A non-executable enum type (an old saved recipe) fails gracefully (`validate_transformation` catches the `ValueError` → `success=False`, not a 500). The `/datasets` upload path stores `data_schema=[]` with real columns in `inferred_schema` (a `SchemaInference` dump).
- **Changing an existing index's options needs a new index name (#565).** Beanie builds indexes at `init_beanie`; turning `Indexed()` into `Indexed(unique=True)` keeps the name `experiment_id_1`, and Mongo refuses to rebuild an existing name with different options (`IndexOptionsConflict`), so the app would fail to start against any collection that already has the old index. Declare the new one as a named `IndexModel` in `Settings.indexes` (`experiment_id_unique`), leave the legacy index to `scripts/check_ab_test_duplicates.py --drop-legacy-index`, and run that script's duplicate check before the first deploy — a unique index that cannot build also fails startup.
- **A Beanie `Link` field persists as a DBRef, so query it by `$id`, not by the bare id (#543).** `Model.link_field == some_id` (and `{"link_field": ObjectId(...)}`) matches **nothing** — the stored value is `{$ref, $id}`. Query `{"link_field.$id": PydanticObjectId(...)}`, the same key the erasure cascade's `_LINK_KEYED_MODELS` deletes by. This silently broke the `column_stats` cache: the DBRef `dataset_id` never matched, so every GET recomputed and re-inserted a full set, growing the collection without bound while never serving from cache. The fix added a `dataset_column_unique` index (via #565's new-name rule + `scripts/dedupe_column_stats.py`, run before deploy). Two consequences of that unique index, both in `app/api/routes/column_stats.py`: the self-healing recompute must delete legacy null-owner rows **before** the `insert_many` (the index keys on `(dataset_id, column_name)` *without* `user_id`, so a surviving null-owner row for an existing column would `DuplicateKeyError` the owner-stamped insert) yet **after** the S3 download+parse (so a failed download can't wipe good cached rows); and a concurrent cache-miss recompute race means the losing writer's `insert_many` hits the index, so `get`/`recalculate` catch `BulkWriteError`/`DuplicateKeyError` and serve the winner's rows rather than 500 (an ordered `insert_many` stops at the first duplicate, so the loser wrote nothing partial).
- **Beanie `save()`** surfaces a unique-index violation as `RevisionIdWasChanged`, not `DuplicateKeyError`.
- **Artifact integrity (#266):** model artifacts are HMAC-SHA256 signed (signature in Mongo, bytes in S3); joblib/pickle loads verify before deserializing and refuse on mismatch.
- **Model export (#468):** `ModelStorageService.load_model(model_id, user_id)` is tenant-scoped and returns a **tuple** `(model, feature_engineer)`; `ModelExportService._load_owned` is the one place that calls it, after `_owned()` has answered 404 for a model the caller does not own (checked *before* the converter-availability check, so a missing converter never changes the answer for someone else's model). Every export route maps `NotFoundError` → 404, `ExportFormatUnavailable` → 501 (body sanitised by the 5xx handler; `/export/formats` carries `available` flags), other `ValueError` → 400. ONNX lives in the `export` dependency group — in `default-groups` so dev and CI run the real conversion, excluded from the image by the Dockerfile's `--no-group export` (so production answers 501 unless that flag is dropped); PMML needs a Java runtime, has no group, and is advertised/served only when `java` is on the path. The Docker ZIP ships `model.pkl` pickled from the loaded artifacts with `requirements.txt` pinned to the pickling scikit-learn/numpy/pandas. **Preprocessing is exported so the delivered container can load it (#632):** `feature_engineer.pkl` is a plain **state dict** (`app/services/model_export_runtime.py::feature_engineer_state` — only fitted stock sklearn transformers plus lists/strings, **no reference to the platform's `FeatureEngineer` class**), and `inference.py` **inlines** `StandaloneFeatureEngineer` (`app/services/model_export_assets/_standalone_fe.py`, whose `transform` mirrors `FeatureEngineer.transform` step-for-step and is **synchronous**) so both exports — the Docker ZIP and the single-file `GET /export/python` download — are self-contained with no `app` code. Before #632 the export pickled the platform `FeatureEngineer` directly, so the container raised `ModuleNotFoundError` and only models with an empty engineer ran. Keep the standalone transform bug-for-bug identical to the platform's (it preserves the pre-existing label-encoding-under-`"encoder"` quirk) or container predictions silently diverge. The test for this surface must mock `load_model` with the real signature and tuple; the old suite mocked a dict-returning one-argument shape and stayed green while every format 500'd.
- **Model cache + inference (#265, #489):** `_ModelArtifactCache` is a TTL-LRU keyed by `(model_id, user_id)`, invalidated on delete/retrain/deploy. All inference routes through `run_locked_inference` (per-model lock + `to_thread`). **The cache is process-local and the container runs 2 workers, so a local evict alone left siblings serving a stale/deleted model until TTL (#489).** Correctness now rides on `MLModel.cache_generation`, a persisted monotonic counter: `invalidate_model_cache` is async and does an atomic Mongo `$inc` **plus** the local evict, and `load_model` validates every cache hit against the current generation — from the caller's already-fresh doc via `expected_generation` (the production route passes it, zero extra query; there is no `await` between its `find_one` and the cache read, so it's authoritative) or one indexed `find_one` otherwise; a gone doc raises not-found, a higher generation reloads. Bump the generation at any **new** in-place invalidation point (an in-place retrain would be one — today every save mints a fresh `model_id`, so `delete_model`/save keep a bare local evict: delete removes the doc, save has no prior generation). Keep the `(model_id, user_id)` key — never regress to `model_id`-only.
- **`delete_model` deletes S3 first and NEVER deletes the Mongo row while an artifact remains (#521).** It used to swallow an S3 delete failure and delete the row anyway — orphaning the object (unreferenced storage cost + a GDPR erasure that reported success over surviving customer-derived data, since a model artifact encodes its training data). It now collects every artifact key (`model_path`, `feature_transformer_path`, `evaluation_data_path`, `shap_values_path` via `_key_of`), attempts each delete, and if **any** fails raises `ModelArtifactDeletionError` keeping the row (the only findable reference); the row is deleted only once every artifact is gone. Mock mode (no bucket) skips S3 entirely and deletes the row, exactly like `erasure_service._delete_s3` — do not remove that guard or every credential-less test's delete raises. Callers: the `DELETE /ml/{id}` route maps the error to a retryable **502**; the erasure cascade's **per-model** try/except records it as a residual (both `_erase_models` and `_sweep_user_scoped` must catch per-model, or one model's S3 failure aborts the rest). `scripts/reconcile_model_artifacts.py` (read-only, age-filtered so an in-flight training artifact written before its doc isn't a false orphan) reports pre-#521 orphans; run against prod is #726.
- **datetime:** use `datetime.now(UTC)` / the `app/utils/datetime.py` helpers (`utcnow`, `as_utc`). Mongo reads datetimes back **naive** — coerce stored values with `as_utc` before arithmetic against aware `now`.
- **Plan enforcement (#368):** `app/billing/enforcement.py`. `quota(<metric>)` is a route dependency that **atomically reserves** a unit via `metering.consume()` — one conditional `$inc` (`units <= limit - amount` + `upsert`), where a record already at the cap misses the filter, the upsert collides with the unique index, and that `DuplicateKeyError` **is** the denial. Answers **402** (not 429 — that's #151's) with limit/used/resets_at/upgrade_available. **Enforcement is the only thing that counts these metrics** — a guarded route must NOT also call `metering.record()`. `QuotaRefundMiddleware` returns the reserved units on any >=400, so a malformed upload doesn't burn quota — it refunds the **reserved amount against the reserved period**, since a request that fails across a month rollover would otherwise credit a month it never charged. JSON predict routes use `quota(..., per_record=True)` — a `predictions` limit must count predictions, not requests, or batching becomes the way around it. **A batch retry charges like a creation (#460)** — it re-reads the same S3 input from the start (there is no resume), so it re-executes the *full* `progress.total_records`, which is the field to size the reservation from (set at creation, deliberately not reset by `retry_job`; note it is the service's pandas count, which can differ by one from the route's `_count_csv_rows` on a trailing blank line). `retry_job` **claims** the job with one conditional `find_one_and_update` carrying every precondition — status and a `$expr` retry-budget check — because read-check-write let a double-click spawn two processing tasks over one document. The route's own 404/409 checks exist for the *message*, not the mutual exclusion. Batch jobs count their CSV rows (stdlib `csv`, so a quoted newline isn't a row) and reserve them **before creating the job** — creation `auto_start`s processing, so a check afterwards would have to unwind a running job, and an unconditional true-up isn't a limit at all (`MAX_BATCH_PREDICT_RECORDS` is 1000x the FREE ceiling). That count **fails closed (#486)**: `_count_csv_rows` used to `return 0` on any error, and `csv` raises `_csv.Error` on a field over its 131072-byte default, so one oversized field reserved 0 and ran the whole batch unmetered — it now raises `CsvCountError` (a bounded `MAX_CSV_FIELD_BYTES`, 1 MiB, enforced via `csv.field_size_limit`, never raised to a huge value which would just trade the bypass for memory exhaustion) and the route answers **400**. Never revert it to a lenient `return 0`. Reservations on one request **accumulate** rather than replace: a batch reserves twice, and overwriting silently burns the first on every failed job. Enforcement fails **closed** (a storage error denies); `record()` fails open. Any test hitting a metered route needs `setup_database` — the dependency reads `Subscription`, and class-level Beanie field access raises `AttributeError` without an initialised Beanie. **Model calls are metered too (#461):** `ai_calls` is the fourth metric, and it is the one ceiling that is **finite on every tier, ENTERPRISE included** — it is the backstop against an unbounded OpenAI invoice, so `plans.py` reads it through `_env_positive_int` and a `-1` override falls back and warns rather than uncapping it. Every route that can reach a model carries `quota("ai_calls")`, including the two 501 stubs in `ai_analysis.py` (so #274 cannot reopen the hole) and `ai_orchestration.py`'s `/recommend-tools` and `/stage-guidance`, whose "rule-based" service takes an OpenAI pass whenever a key is present; `tests/test_billing/test_ai_routes_are_metered.py` is the registry for `/api/v1/ai` (all methods, not just POST). **The Next.js `/api/chat` proxy must never call OpenAI itself** — it did, outside every backend control, so the monthly ceiling did not apply to it; it now forwards to the backend's `POST /ai/chat` (fail-fast bounds, API JWT) and the frontend has no `openai` dependency at all. **Every AI route has a rule-based fallback, and a fallback is not a paid call:** the route must `enforcement.release(request)` when the service reports no model ran — `generated_by != "openai"` (report card, error suggestions), `generated_by != "hybrid"` (orchestration), `metadata["ai_used"]` false (feature suggestions) — or a keyless deployment bills, then blocks, purely local analysis. A service that gains a model call must also gain that signal. `/billing/status` derives its `limits` from `METERED_METRICS`, never a hand-written tuple, or the billing page silently hides a metric.
- **Entitlement (#366, #458, #510):** `Subscription.is_entitled` is the single predicate; `effective_tier` is what callers read (`plan_tier` alone keeps serving PRO to a lapsed row). It requires **both** an entitled status **and** an unlapsed period. `PAST_DUE` is entitled on purpose — Stripe is still retrying — but `unpaid` is **not**: that is the status a subscription reaches once Stripe has *given up*, and mapping the two together handed permanent paid access to a customer whose payments had permanently failed. Never re-merge them. The period check exists because status is only as fresh as the last webhook and nothing reconciles on a schedule, so without it one dropped event grants a tier forever; the grace is **per status** and the two must not collapse into one: `ENTITLEMENT_GRACE` (3 days) absorbs delivery lag on an ACTIVE row whose renewal already happened, while `DUNNING_GRACE` (30 days) covers PAST_DUE, because Stripe's Smart Retries run out to ~4 weeks and a single 3-day window would cut off on day three a customer whose card succeeds on day eight — silently rescinding the serve-through-dunning policy stated right above it. A **missing** `current_period_end` falls back to `updated_at` + the same grace — bounded, never "entitled forever", which is the same bug wearing a different field. Both values come back from Mongo naive, so both go through `as_utc`. `current_period_end` itself lives on the subscription **item** in the pinned API version (`STRIPE_API_VERSION` in `stripe_client.py`, guarded by `tests/test_billing/test_stripe_api_version.py` against the SDK's own constant — *not* `stripe.api_version`, which `_client()` overwrites, making that assertion pin==pin); `_period_end()` reads the legacy top-level location first and the item second, and must never clear a known value on an event that omits it. `scripts/reconcile_subscriptions.py` is the repair path for the other direction (a missed **renewal**, which no local rule can fix) and the backfill for pre-#510 rows; it reconciles **tier as well as status** — an upgrade changes only the price, so a status-and-period comparison reports "everything matches" while an ENTERPRISE customer is enforced as PRO — and its write is conditional on `updated_at` so a webhook landing mid-run is not overwritten. **The webhook itself persists via a single conditional upsert, not a read-modify-write (#509):** `Subscription` has no Beanie revision, so two concurrent events would both read the old row and the later `save()` would silently drop the earlier — a `subscription.updated` racing a `subscription.deleted` could leave a cancelled tenant entitled. `_apply` now does one `update_one` whose filter requires `last_event_at <= event.created` (or unset); a strictly-older event matches nothing, the upsert's insert hits the unique `user_id` index, and the stale event is dropped. A *first* `DuplicateKeyError` means a concurrent event just created the row (the new-tenant `checkout.completed`+`subscription.created` burst) — retry once, where the same filter decides apply-or-reject. Only event-present fields are `$set`, and a duplicate delivery converges on the same row (idempotent in effect).
- **The published refund window is enforced from `Subscription.first_paid_at` (#602).** `/legal/terms#refunds` promises a full refund within `refundWindowDays` of the first paid charge; the webhook stamps `first_paid_at` **once** (first-write-wins `update_one({user_id, first_paid_at: None})`) on the first genuinely **paid** checkout — `payment_status == "paid"` or `async_payment_succeeded`, deliberately **narrower than the `settled` flag** that grants entitlement, because `no_payment_required` (a trial / 100%-discount) is entitled but is not a charge and must not open the window. `app/billing/refunds.py` (`REFUND_WINDOW_DAYS`, `is_in_refund_window`, `refund_window_ends_at`, both via `as_utc`, inclusive at the boundary) is the single eligibility source; `tests/test_billing/test_refund_window.py` parses `apps/frontend/lib/legal/company.ts` and fails if `refundWindowDays` ≠ `REFUND_WINDOW_DAYS`, so the published and enforced numbers can't drift — change the policy in `company.ts` and this constant together. `GET /billing/status` exposes read-only `refund_eligible` + `refund_window_ends_at`; a cross-tenant **admin** operator view waits on the #479 admin backend.
- **Training config is bounded per tier (#500):** `POST /ml/train` takes typed `TrainingConfigRequest` / `TuningConfigRequest` / `FeatureConfigRequest` with `extra="forbid"` — an undeclared knob cannot reach the engine, so add new engine knobs to the request model *and* to `TrainingCeilings` in `app/billing/plans.py` (the single source of per-tier ceilings), or they are unreachable. Anything over the caller's ceiling is a **422 naming the knob, value and limit — never clamped** (a clamped run trains a model the caller did not ask for). Estimator hyperparameters (`n_estimators`, `max_depth`) are not caller-reachable at all — the tuner's search space is server-defined. Every run ends at the tier's `wall_clock_seconds` via `asyncio.wait_for` in `train_model_task`; the engine's own `time_limit` is *soft* (checked between candidates, after the tuning phase) and stops nothing by itself. A fit already inside a worker thread cannot be killed — the job is marked FAILED and the thread finishes on its own. FREE's ceilings must stay >= the `comprehensive` mode preset (`tests/test_billing/test_training_ceilings.py` guards it) or that mode silently disappears for free users.
- **Training concurrency + parallelism are bounded on the shared VPS (#498):** `app/services/training_admission.py` mirrors the batch mechanism (#515). `enforce_training_per_user_cap` refuses the N+1th PENDING/RUNNING training per tenant with `TrainingConcurrencyLimitError` → **429** (checked in the route before insert, after the `quota("training_runs")` reservation, so the refund middleware returns the unit); a per-loop `Semaphore(MAX_CONCURRENT_TRAINING_JOBS)` gates `engine.run` in `train_model_task` (the wall-clock `wait_for` sits *inside* it, so queue time isn't charged), and a job cancelled while queued is skipped on acquire. `bounded_n_jobs` clamps estimator parallelism to `TRAINING_MAX_N_JOBS` (default 2, ≤ host cpu) — never re-introduce a raw `n_jobs=-1` in `automl_engine`/`feature_selection_service`/`hyperparameter_tuner`; the engine threads it as `self.n_jobs`, the tuner clamps `TuningConfig.n_jobs` at point of use. All three caps read through `_env_positive_int` (a 0/negative override can't disable them). **Known residual:** a wall-clock timeout releases the semaphore slot while the sklearn `fit` in its `to_thread` worker keeps using a core until it finishes (unkillable), so the cap can be briefly exceeded during an overrun — size `MAX_CONCURRENT_TRAINING_JOBS` with margin.
- **PII risk: a column name is a hint, values are evidence (#608).** `PIIDetector` runs both the name check and the value-pattern check on every column and keeps the stronger signal; `NAME_MATCH_CONFIDENCE` equals `HIGH_RISK_CONFIDENCE` (0.8) and the report needs *strictly greater*, so a label alone is medium and only matching values make a column high — the level that sends `/upload/secure` to the confirmation gate. Before #608 the name check `continue`d past the values, so `ssn` full of SSNs was medium while `ref_code` with the same values was high, and the honestly-named file skipped the gate. Change those constants knowing that raising a population from medium to high routes it through `/confirm-pii-upload`.
- **The AI summary is built from a PII-masked frame, never the stored schema, on the secure paths (#490).** `generate_ai_summary_safe(user_data_id, df)` in `secure_upload.py` summarizes the frame it is handed via `prepare_dataset_summary_from_df` + `call_openai_api` — it must NOT delegate to `generate_dataset_summary(user_data_id)` (which reads the stored `data_schema`), because the chunked `complete` path stores a **raw** schema and would ship raw PII `example_values` to OpenAI. All three secure paths pass `_summary_frame(df, pii_detections)`, which masks whenever any PII is detected — `mask_pii=false` is a *storage* choice, not consent to send PII to a third-party sub-processor. The original bug: the wrapper passed the DataFrame where `generate_dataset_summary` expected a `str` id, so every call raised inside `UserData.get(df)` and was swallowed, leaving the summary permanently null for PII-confirmed and chunked uploads; the wrapper now logs at WARNING (with the dataset id) on a null/failed result rather than swallowing. **`/upload/secure` was the third path and was fixed to match (#679):** it branches on `pii_report["has_pii"]` — a flagged dataset (medium risk here; high risk returns early to `/confirm-pii-upload`) goes through `generate_ai_summary_safe` + `_summary_frame`, only a clean one keeps the stored-schema `generate_dataset_summary`. **`_summary_frame` masks EVERY flagged column, not just the report's medium+ ones:** it calls `mask_pii(..., min_confidence=0.0)`, because a weak value-pattern match (confidence in `(PATTERN_MATCH_FLOOR 0.1, 0.5]`) sets `has_pii` but leaves `risk_level="low"`, and `mask_pii`'s default `>MEDIUM_RISK_CONFIDENCE (0.5)` cutoff — the right one for the *stored*-copy masking at `/confirm-pii-upload` — would otherwise ship that column's raw values to OpenAI. The floor is a parameter precisely so the summary path (mask all detected) and the storage path (mask medium+) can differ.
- **Metering the upload surface (#459):** `quota("uploads")` belongs on **every** route that creates a dataset, and there are more of them than the name "upload" suggests — `/upload/secure`, `/upload/confirm-pii-upload`, `/upload/chunked/{id}/complete`, `/upload/`, `/datasets/upload`, and `onboarding/sample-datasets/{id}/load` (store.py's bare `POST /api/v1/`, which could never succeed, was removed in #472) (a sample load inserts a full `UserData` unconditionally, so unmetered it mints datasets without limit). `datasets/{id}/features/{fid}/apply` reserves **inside the handler**, only when `create_new_dataset` is true — a route dependency would bill every in-place apply. `tests/test_billing/test_dataset_routes_are_metered.py` is a **registry**, not a list of per-route tests: it walks the live route table and fails on any unclassified POST under its prefixes, which is the only thing that catches a new route. Note its two real limits — it polices **only** the prefixes in `_IN_SCOPE_PREFIXES` (a dataset-creating route mounted elsewhere is invisible; that is exactly how the onboarding loader was missed), and `app.routes` is **not flat** on FastAPI 0.139 — routers are lazy `_IncludedRouter` wrappers, so the naive `isinstance(r, APIRoute)` walk finds almost nothing and cheerfully reports that everything is metered. A 2xx that does no work must hand its unit back with `enforcement.release(request)` — the refund middleware only sees >= 400, and `/upload/secure`'s high-PII branch answers 200 having created nothing, which was charging a unit there *and* again at `/confirm-pii-upload`.
- **Batch prediction concurrency is bounded (#515):** `batch_prediction.py` no longer spawns unbounded `asyncio` tasks. A per-process `asyncio.Semaphore(MAX_CONCURRENT_BATCH_JOBS)` (default 2, resolved per running loop so the test suite's many loops don't share one) gates the auto-started path — excess jobs queue rather than all executing; `auto_start=False` (tests) bypasses it. `create_batch_prediction_job` refuses a caller already at `MAX_CONCURRENT_BATCH_JOBS_PER_USER` (default 3) PENDING/RUNNING jobs with `BatchConcurrencyLimitError` → **429**, checked **before** the S3 upload so a refusal leaves no orphan object and the reserved `predictions` units are refunded by the middleware. Result streaming was already O(chunk_size) (`_read_data_chunks` + a temp-file result stream); this closes the task-spawn half. A job cancelled while still queued is skipped when it acquires the semaphore (cancelling a job already running is #485).
- **Stale in-flight jobs are reaped, not left RUNNING forever (#484):** training/batch jobs run in-process, so a restart/deploy/crash used to leave them RUNNING permanently — holding quota and (since #498/#515) a concurrency slot. Both models carry `last_heartbeat` (set at creation, bumped on every progress write — and for training's *partial* `$set` writes it must be included explicitly, plus `app/utils/heartbeat.py`'s background pump keeps it fresh through a slow candidate/chunk). `app/services/job_reaper.py::reap_stale_jobs` marks in-flight jobs whose heartbeat is older than `STALE_JOB_TIMEOUT_SECONDS` (default 1800) FAILED and refunds their reserved quota against the **reserved** period (`period_key_for(created_at)`): training 1 `training_runs`, batch `total_records` `predictions`. It runs on startup and every `JOB_REAPER_INTERVAL_SECONDS` from the lifespan. **Two things make it safe under the 2 gunicorn workers:** staleness is heartbeat-based (never "reap all on startup"), so a live job with a recent heartbeat is never touched; and each reap is an atomic `find_one_and_update` claim, so concurrent reapers claim disjoint jobs and refund exactly once. `retry_job` must refresh `last_heartbeat` or the retry inherits the failed run's stale value and is reaped before it starts. Known limitation: a batch retried across a month boundary then reaped under-refunds the retry period (the `units>=amount` clamp prevents minting).
- **Batch cancel actually stops the run (#485):** cancelling used to write CANCELLED and be silently overwritten by the running task's own terminal `save()` (a lost write). Now **every** status-touching write in the batch task is conditional/status-guarded so a concurrent cancel is never clobbered: `_claim_running` (the opening PENDING/RUNNING→RUNNING claim — do NOT revert it to a plain `mark_started(); save()`, that reintroduces the bug just before the first chunk), the per-chunk `_persist_progress` (partial, guarded on RUNNING), and `_finalize_if_running` (terminal write only if still RUNNING). `cancel_job` is an atomic conditional transition. The loop re-checks cancellation between chunks (and once more before the S3 upload) and, on cancel, discards the partial output (never uploaded), refunds the unprocessed remainder via `_refund_remainder` (`total_records - processed` against `period_key_for(created_at)`), and sets the terminal status in memory so the completion webhook reports CANCELLED. A cancelled job is terminal, so #484's reaper never also refunds it. Batch S3 keys are **`batch-jobs/{user_id}/{model_id}/{job_id}/{input.csv|results.ext}`** (#487) — keyed by the unique server-generated `job_id`, generated up front in `create_batch_prediction_job` and threaded into `_prepare_input_data`, not by a second-granularity timestamp (which collided for two same-second jobs, overwriting one input and leaking another tenant's results). A retry reuses the same `job_id`, so it deterministically overwrites its own output.
- **The prediction log is durable and shared, not in-memory (#488):** `prediction_monitoring.PredictionLog` persists to the `PredictionEvent` Mongo collection, not a process-local dict — with 2 gunicorn workers the old dict showed each dashboard only its worker's half of traffic and reset on every deploy. Same interface (`log_prediction` / `get_recent_predictions`); readers/drift are unchanged. Retention is a **TTL index** (`PREDICTION_EVENT_TTL_SECONDS`, 30d) — never re-introduce the old per-model 10000 quadratic trim or keep input rows forever. `get_recent_predictions` sorts `-_id`, caps, reverses to chronological (for the drift older/recent split) and returns UTC-aware timestamps. The serving hot path logs a whole batch with one `insert_many` (`log_predictions`), never one insert per record. `PredictionEvent` stores request `input_data`, so it is **erased with its model** (`erasure_service` deletes it by `model_id` wherever a model is deleted) — a new PII-carrying collection must always be wired into the erasure cascade.
- **Rate limiting (#151, #455, #483):** global `RateLimitMiddleware` on all `/api/v1`; per-key buckets only on `/production/v1/models`. Anonymous requests are keyed on the socket peer, or on **`X-Real-IP`** when `RATE_LIMIT_TRUST_PROXY` is set — nginx sets that header from `$remote_addr` and *overwrites* it, so behind the proxy it is authoritative (one hop only: a CDN or LB in front of nginx would make `$remote_addr` the LB, which needs nginx's `real_ip` module — no such layer exists today). **`X-Forwarded-For` is never read**: nginx *appends* to it, so element `[0]` is whatever the client sent, and reading it under either flag setting let a caller mint a bucket per request. The flag only helps if compose passes it (`docker-compose.staging.yml` does; before #483 it did not, so staging bucketed every anonymous request under nginx's container IP) and every backend `location` sets the header — `tests/test_security/test_nginx_real_ip.py` pins both. **Disabled in the test env** — a test that means to exercise the limiter must build the middleware with `enabled=True`, or its 429 assertions are vacuous. Both stores read `limit <= 0` as **no enforcement**, so a per-key `rate_limit` of 0 does not throttle, it *removes* the only control on the paid serving surface. Hence three guards, all needed: `CreateAPIKeyRequest.rate_limit` is `ge=1`; `app/billing/api_keys.py` clamps it to `api_key_rate_limit_ceiling(tier)` at creation **and** `reconcile_user_api_keys` runs from the Stripe webhook's `_apply` on every subscription save (the limiter never reads a subscription on the hot path, so nothing else would revisit a key minted under a richer tier); and the middleware floors the stored value at 1 for rows written before that. **`reconcile_user_api_keys` moves the effective `rate_limit` BOTH directions to `min(requested_rate_limit, ceiling)` (#588), not only down (#455's original was lower-only).** Creation records the tenant's asked-for value in `APIKey.requested_rate_limit`; a transient non-entitled status (an `async_payment_failed` makes `effective_tier` FREE) clamps the effective value down, and when the subscription returns to entitled the reconcile raises it **back** toward the request — otherwise a paying tenant's 10k/hr key stayed at 1k/hr forever. The pivot is the recorded request: a key *we* clamped rises again; a key the tenant *set low on purpose* has `requested_rate_limit` == that low value, so `min` leaves it there; nothing ever exceeds the request or the tier ceiling. The pipeline update uses `$ifNull(requested_rate_limit, rate_limit)` so pre-#588 rows fall back to their current value — only ever lowered, never surprise-raised (`fix_api_key_rate_limits.py` / a new key is their path). Every tier's ceiling in `plans.py` must stay **finite** — and note the trap: `UNLIMITED` (-1) is that module's documented "no ceiling" sentinel for *every other* limit, but for a rate limit it means the opposite, so `PLAN_*_API_KEY_RATE_LIMIT` reads through `_env_positive_int`, which refuses a non-positive override, warns, and falls back to the default rather than bricking the tier at 1/window. `api_key_rate_limit` is deliberately **not** in `METERED_METRICS`: it is a throughput ceiling, not a per-period counter, and `limit_for` rejects it. `scripts/fix_api_key_rate_limits.py` audits/repairs existing rows.
- **Redis cache surface (#452):** the whole user-facing cache API is `DELETE /api/v1/cache/me`, scoped by the token. **Never build a Redis pattern from caller input**, and never leave one unanchored: rate-limit buckets (`ratelimit:<identity>`) share this Redis, so a `*:{user_id}*` glob purges the caller's own limiter — which is how a cache route became a limiter bypass. A user-scoped key family must be declared in `_USER_SCOPED_KEYS` (exact) or `_USER_SCOPED_PATTERNS` (anchored to a literal namespace prefix, id glob-escaped) in `app/services/redis_cache.py`, or `/me` silently stops purging it. `delete_pattern` stays available for **server-built** patterns (`viz:{dataset_id}:*`, `stats_{dataset_id}_*`). **`delete_pattern` sweeps with `SCAN`, never `KEYS` (#570):** `KEYS` scans the whole keyspace in one blocking call and stalls the shared instance (the rate-limit buckets live here too), so it iterates `SCAN` (`COUNT 500`) and deletes in batches, deduplicated across cursor pages (`SCAN` can return a key twice). `MATCH` uses the same glob grammar as `KEYS`, so the escaped patterns and the return count are unchanged. The `FakeRedis` test double carries the anchored-glob guard on `scan()` (the path `delete_pattern` now takes), not just `keys()`.
- **Version ownership (#446–#448, #453):** everything under `/api/v1/versions` and `/api/v1/datasets/{id}/versions` authorizes on **`DatasetVersion.user_id`** (server-set, indexed) via the `require_owned_dataset` / `require_owned_version` helpers in `app/api/routes/versions.py`. Call them **outside** the handler's `try` — the module's broad `except Exception` blocks turn a 404 into a 500, and `compare_versions` has no `except HTTPException: raise` at all. Unknown and foreign ids must answer identically, and the ownership check runs **before** any other guard, or the guard's own 400 (`Cannot delete base version`) becomes an existence oracle. `versioning_service.get_version(user_id=...)` compares against the same `DatasetVersion.user_id` since #453 (it used to join to `DatasetMetadata` and read `if dataset and ...`, so a version whose dataset row was gone **passed**); `create_transformation_version` resolves its parent through it (#559), so a parent the caller does not own is refused inside the service — a caller that skipped its own guard is no longer a hole. Scoping the entry point is not enough for lineage — `get_lineage_chain` and `compare_versions` walk `parent_version_id`, so they take a `user_id` and stop at the first hop the caller does not own, or another tenant's lineage reaches `lineage_chain`/`lineage_path`/`transformation_count`. **Deleting a version deletes its S3 object too, S3-first, and keeps the row if S3 fails (#561):** `VersioningService.delete_version` removes the object before the Mongo doc and, on failure, raises `VersionArtifactDeletionError` (route → retryable **502**) keeping the row — the only record of the key — so the object stays findable, the same choice #521 made for model artifacts (never the swallow-and-orphan the retention path `cleanup_old_versions` uses). The key is resolved through `parse_s3_url` for any URL shape, and a URL naming a **different** bucket than the configured one is refused (row kept), the #616 guard — deleting that key from our bucket would no-op and orphan the real object, or hit a same-named one. The `DELETE /versions/{id}` route previously dropped only the doc, orphaning the object and destroying its only key-record in the same request.

A **red `claude-review` job conclusion means the verdict is absent, not clean.** The `--max-turns` ceiling is bounded by the run time (~7 turns/min), so review economy (the single-`gh pr diff`-fetch prompt rule) is the real lever beyond it. The `Report incomplete review` step posts a visible "did not complete" comment on a genuine failure (gated `!cancelled() && outcome in (failure,cancelled)` so a concurrency-cancel or job timeout stays quiet, but a step failure or the step's own timeout fires) so silence can't pass for a pass — **and the review step carries its OWN `timeout-minutes: 9`, shorter than the job's `timeout-minutes: 10`, on purpose:** a *job*-level timeout kills the whole job and the reporting step would never run, so the step timeout must fire first (failing the step) while the job keeps time to post the comment. Keep step-timeout < job-timeout, and both > the max_turns budget.
- `deploy.yml` ships `main` → staging over SSH (secret-gated). **The VPS firewalls port 22 off the public internet** (`ufw` allows it only from the home subnet and `on tailscale0`), so the runner joins the tailnet first — `HOST` must be the box's **tailnet** name/`100.x` address, never `dev.briaanalytics.com`, and `SSH_KNOWN_HOSTS` must be labelled with that same value (#384). Humans on the home subnet still SSH to the public name directly. `integration-tests.yml`/`e2e-tests.yml` are manual (`workflow_dispatch`). **Staging health is probed per subsystem, on a schedule and after every deploy (#552):** `/health` is liveness and `/health/ready` is Mongo-only by design (#503), so a rotated Atlas credential (the running process keeps its authenticated pool) and a missing S3 bucket both sat behind green signals for weeks. `python -m app.health_probe` (under `app/` because the image ships nothing else) hits the running service's `/health/ready` and, in a fresh process, opens a new Mongo connection and runs the S3/OpenAI checks (the service's own pool stays green on a stale credential until restart, so only a new connection sees it); every status must be `healthy`. `staging-health.yml` runs it hourly over the same tailnet/SSH path and opens/closes a `[P1] [ops]` issue; `deploy.yml`'s gate polls `/health/ready` (never bare `/health`) and then runs the probe in the container `up -d` just recreated — the restart-after-rotation smoke. Rotation itself follows `docs/operations/CREDENTIAL_ROTATION.md` (`up -d --force-recreate`, never `restart`); `test_staging_health_wiring.py` fails if compose interpolates a secret the runbook does not name. **The alert dedupes on the stable phrase `Staging health probe is failing`, never the full bot title (#757):** the operator retitles every issue with a `PX.Y` prefix, and an exact-title search then misses the open alert and files a duplicate beside it. On failure both workflows run `scripts/deploy/backend_state.sh` over ssh stdin and put the result in the issue/run — container status, `RestartCount`/`OOMKilled`/exit code, and an exception-*class* histogram of the last 200 backend log lines, **never a raw line** (the repo is public; a pymongo auth error names the Atlas cluster). Probe exit 137 means the container died under the `exec`, i.e. a boot loop, not a probe bug.
- **Staging env vars: compose is the contract, and `${VAR:?}` is a deploy gate (#457).** A variable only reaches the container if `docker-compose.staging.yml` lists it — `.env.staging` alone does nothing, which is how billing sat inert in the only deployed environment with no `STRIPE_*` at all. `scripts/deploy/preflight_staging_env.sh` derives the **required** set by grepping that file for `${VAR:?}` guards and `deploy.yml` runs it before `up`, so **adding a guard for a value that is not yet provisioned fails the next deploy**: mark a new variable optional (`${VAR:-}`) until the value exists, then flip it. (The script strips comments first — before #457 a comment *explaining* the `${VAR:?}` pattern made the preflight demand a variable literally named `VAR`.) Compose injects env at container **creation**, so `up -d`, never `restart`. Optional passthrough means an absent value arrives as `""`, not unset: any "is it configured" predicate must treat blank as unset, and **every consumer must read through that same accessor** — `stripe_client.setting()` is the pattern, and fixing only the reporting layer is what left `_price_for`, `tier_for_price` and the webhook's signature check reading raw values: a trailing newline on `STRIPE_WEBHOOK_SECRET` mismatches every real Stripe signature (charged, never entitled, and it looks like a forgery), and one on `STRIPE_PRICE_ENTERPRISE` silently downgrades enterprise customers to PRO. `Settings` fields that nothing reads back (e.g. `STRIPE_PUBLISHABLE_KEY`) are not worth passing. `PLAN_*` limit overrides are deliberately passed nowhere in deployment: `app/billing/plans.py` is the single source, its numbers are the ADR-003 product values (#474), and `test_plan_limits_are_the_product_values.py` greps every deploy surface for a stray override. The one place they are set is `apps/frontend/test-e2e.sh`, which lifts FREE's ceilings for the e2e backend — every e2e test shares one user, and a single smoke run with retries exhausts 20 uploads a month (#550).
- **The edge config is not deployed by anything (#456).** `nginx-staging.conf` is copy-pasted onto the box by hand, so the live file has drifted from the repo's and **editing the repo file alone changes nothing in production** — diff the two before believing an edge fix shipped. The one path that must never be lost in that copy is the Stripe webhook: the backend mounts `POST /webhooks/stripe/webhook` **outside** `/api/v1` (so the limiter can't 429 Stripe's small IP pool, #367), so a `location /api/` block does not cover it and it falls through to Next.js — which *307s Stripe to the sign-in page*, silently, while checkout keeps succeeding and entitlement never follows. Its `location` block carries its own `client_max_body_size`: the route is unauthenticated and `await request.body()` runs before signature verification, and `BodySizeLimitMiddleware` only inspects a **declared** `Content-Length`, so a chunked body bypasses it entirely and only the edge cap binds. `tests/test_security/test_nginx_webhook_route.py` parses the real config against the real mount so the two cannot drift.
- Guides: `apps/backend/docs/TEST_INFRASTRUCTURE.md`, `apps/backend/docs/TDD_GUIDE.md`.

## Environment Variables
- Frontend: `.env.local` | Backend: `.env`
- **`NEXT_PUBLIC_API_URL` includes the version prefix** — `http://localhost:8000/api/v1`, matching `.env.local`, the Dockerfile dummy and `ci.yml`. Append only the resource path (`${API_BASE_URL}/datasets/...`); never re-add `/api` or `/api/v1`, and never "normalize" with `.replace(/\/api$/, '')` — that strip matches nothing and hides the mistake. Getting this wrong 404s silently: it broke the AI Insights panel and chunked-upload resume for as long as they existed, and the suites missed it because they built the expected URL with the same expression as the code (#406). `__tests__/lib/apiUrlConstruction.test.ts` pins the paths against the real FastAPI route table. **The other way to get it wrong is no base at all (#470):** the onboarding page and `SampleDatasetSelector` called `fetch('/api/v1/onboarding/…')` — relative to the *frontend* origin, so a 404 with no auth header, on the screen every first-time user is redirected into — and the e2e mocks matched on `url.includes()` so they never noticed. All onboarding calls go through `lib/services/onboarding.ts` now, and the same test file bans bare relative `/api/v1` literals in `app/`, `components/` and `lib/` (Next.js route handlers under `app/api/**` are the one legitimate relative target).
- **`MONGODB_URI` is bare; the database name lives in `MONGODB_DB`** — the backend selects with `client[db_name]` (`app/main.py`), and the frontend's NextAuth adapter takes `MongoDBAdapter(client, { databaseName: process.env.MONGODB_DB })`. **Both halves must be given the same value**, or auth and application data land in different databases. Omitting it does not fail — the driver resolves `client.db(undefined)` to the URI's default database, which on a bare URI is the one literally named `test`; that is where staging's NextAuth users and accounts went until #545. Any deploy surface that passes `MONGODB_URI` to the frontend must pass `MONGODB_DB` too (`docker-compose.staging.yml` does, for both services). `__tests__/lib/authAdapterDatabase.test.ts` pins the wiring — it needs virtual mocks because `@auth/mongodb-adapter` is ESM-only (no `require` condition), which is also why `scripts/check-auth-adapter.mjs` rebuilds the adapter instead of importing `auth.ts`. **Since #551 the frontend fails fast (production only) via `assertDatabaseConfig` (`lib/auth-config.ts`, called at `auth.ts` load):** the invariant is "the database is named exactly once and both halves agree", not "`MONGODB_DB` is set" — a bare URI with no `MONGODB_DB` errors (else the silent `test` fallback), a URI whose path DB disagrees with `MONGODB_DB` errors, and a URI that carries the DB in its path with no `MONGODB_DB` still starts (`.env.staging.example`'s shape). The backend still reads `MONGODB_DB` and ignores any URI path, so the same URI-path-vs-`MONGODB_DB` disagreement is silent there (follow-up).
- Required: AWS credentials, MongoDB URI, OpenAI API key, NextAuth secret
- `SKIP_AUTH=true` bypasses auth — honored **only** when `ENVIRONMENT` is `development`/`test`; startup fails hard otherwise (#149). Maps all requests to `dev-user-default`.

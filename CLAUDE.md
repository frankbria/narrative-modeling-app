# CLAUDE.md - Project Conventions and Guidelines

## Project Overview
SheetPredict — an AI-guided platform that democratizes machine learning by helping non-expert analysts build, explore, and deploy models without writing code.

**The product has one name, SheetPredict (#765).** A page shows `COMPANY.serviceName` (`apps/frontend/lib/legal/company.ts`); `COMPANY.valueLine` is the signed value line, held equal to `docs/product/positioning.md` by the sign-up page's test. The API's vendor media type is `application/vnd.sheetpredict.v1+json`. `apps/backend/tests/test_security/test_product_name.py` reads every tracked text file and fails on a retired name, comments and guides included, so describe an old name without writing it. Identifiers are not names and keep theirs: the repository, the packages, the databases, the buckets, and the test-user address. The historical record (`tasks/`, the `claudedocs/` trees, the `archive/` and `sprints/` docs) and `positioning.md` are exempt, by path, in that test.

> Per-issue implementation history lives in git/PRs, not here. This file holds durable conventions only.

## Architecture

### Frontend (`apps/frontend/`, Next.js)
- App Router, TypeScript strict, Tailwind CSS
- NextAuth v5 (Google, GitHub); frontend mints an HS256 JWT (`sub=userId`, `iat`, `exp`) in the session callback (`lib/api-token.ts`) for the backend to verify. The backend verifies it with **PyJWT** (`nextauth_auth._verify`: HS256 only, `exp` and a non-empty `sub` required, no `id` fallback, 30s leeway because PyJWT rejects a future `iat`; #844 replaced python-jose, which had an unpatched critical CVE). The user path catches `jwt.PyJWTError`, the base class, because a key error is not an `InvalidTokenError`, and the admin path maps every failure to its 404. Backend tests mint through `tests/api_tokens.py::mint_api_token`, which builds the frontend's token by hand with `hmac`, so the verifying library cannot also be the minting one. **That `session.apiToken` is the only credential that may reach the backend (#527).** The OAuth provider's access token is not persisted in the JWT and does not exist on the session any more — three call sites had been forwarding it (Google's credential, sent to our API) and one route sent the literal `"default"` when it had nothing, which the backend rejects but which was only ever one config change from a user. A proxy route with no `apiToken` answers 401; it never forwards a placeholder. `__tests__/lib/noProviderTokenForwarding.test.ts` greps the frontend for `session.accessToken`, `Bearer nextauth-` and `|| 'default'` so the class cannot return.
- **Tailwind v4, CSS-first (#345):** there is **no `tailwind.config.*`** — the whole theme lives in `app/globals.css` via `@theme` / `@theme inline`, `@utility`, `@custom-variant dark`, and `@plugin` (which is the *only* way plugins load; a plugin in `package.json` is not wired until it has an `@plugin` line). Never wrap a theme token in a colour function: the tokens are `oklch`, so `hsl(var(--token))` composes to invalid CSS that browsers **drop silently** — that shipped ~35 dead utilities and a wholly non-functional dark mode, green the whole time. Every semantic token needs a `-foreground` pair defined in **both** `:root` and `.dark`. `__tests__/styles/themeTokens.test.ts` compiles `globals.css` through real PostCSS and guards all of this; component tests can't, since they never run Tailwind.

- **Dark mode is live (#407):** `next-themes` (`attribute="class"`, `defaultTheme="system"`) via `components/ThemeProvider`, toggled from the sidebar. `attribute` MUST stay `class` — `@custom-variant dark (&:is(.dark *))` keys on it, and the `data-theme` default would silently make every `dark:` utility dead again, which is the state #407 found. Components use **semantic tokens** (`bg-card`, `text-foreground`, `text-muted-foreground`, `bg-muted`, `border-border`), never `bg-white`/`text-gray-900`/`bg-gray-50` — those stay light in dark mode and render text invisible. `__tests__/styles/semanticColours.test.ts` enforces this repo-wide; `components/Sidebar.tsx` is the one exemption (deliberately dark in both themes). jsdom has no `matchMedia`, so `jest.setup.js` polyfills it — every suite rendering through the root layout needs it.
- **Public pages are two prefixes plus an exact-path allowlist (#473, #475):** `middleware.ts` is deny-by-default, and only `/auth/` and `/legal/` are exempt as prefixes (plus `/api/`, which self-guards with 401) — both keep the **trailing slash** so the exemption cannot leak onto a lookalike route (`/legality` stays protected) — and marketing pages are listed **by exact path** in `PUBLIC_PATHS` (`/pricing`; #766's landing page joins it), never as a prefix, so `/pricingx` and `/pricing/anything` stay behind the wall. `/pricing` renders `lib/billing/plans.json`, the one source for every published price and limit (billing page, landing page); the backend's `test_pricing_source_matches_plans.py` holds it equal to `plans.py` and the ADR-003 price column, so change all three together. ENTERPRISE is always "contact us", never a price (ADR-003 AC3). **Any route added under `/legal/` is public by construction, not by review** — the prefix check cannot tell a policy page from an admin tool for editing one, so a new file there is unauthenticated the moment it exists. `/legal/terms` and `/legal/privacy` must stay anonymous-reachable: Stripe's reviewers, regulators and prospective customers all read them before an account exists, and behind the session wall they satisfy nothing. Their identity, jurisdiction, refund window and sub-processor table live in one place, `lib/legal/company.ts`, which the pages and their tests both read — the sub-processor list is a legal claim, so every row is traceable to the code that sends the data (notably `dataset_summarization.py`, which ships up to 5 sample rows of the customer's dataset to OpenAI). Retention wording is deliberately no stronger than the cascade actually performs, so tightening erasure means loosening the policy text, not the other way round. As of #497 the live cascade *does* remove trained models, training jobs and their S3 artifacts (`erasure_service._erase_models` + `model_storage.delete_model`, proven against real S3 in `test_erasure_model_artifact_localstack.py`); the only residual is the bounded backup window in `lib/legal/company.ts` (Atlas weekly snapshots), so the policy text may now understate erasure rather than overstate it.
- **`/admin` is authorised, not just authenticated (#477):** `middleware.ts` rewrites `/admin` and `/admin/*` to Next's not-found route unless the session token's email is on **`ADMIN_EMAILS`** (`lib/admin-allowlist.ts`), so a signed-in tenant gets the same 404 as for a page that does not exist. The rewrite target is Next's *internal* not-found route, so a unit test can only pin the rewrite header — the HTTP status is checked against a real build: `next build && next start`, mint a session with `@auth/core/jwt`'s `encode` (salt `authjs.session-token`), and `curl -o /dev/null -w '%{http_code}' -H "Cookie: …" /admin` must print 404 for a non-listed email (verified on 16.2.12; the RSC navigation fetch legitimately answers 200 with the not-found tree in the payload). Since #613 the blocking `@smoke` job repeats that check on every run against the **dev server** (the e2e stack is `next dev`; the production-build recipe above stays the manual check for `next start`-only rendering differences): `e2e/workflows/admin-guard.spec.ts` requests `/admin` as a document for the ordinary test user (404, no "Admin Dashboard") and for a second dev-credentials identity that `test-e2e.sh` puts on `ADMIN_EMAILS` (`TEST_ADMIN_EMAIL`, 200 with the heading) — the ordinary user is a non-admin by construction, not because the variable happened to be unset. The allowlist **fails closed** — unset means nobody is admin, the opposite of `INVITE_ALLOWLIST`'s empty-means-open — and it is the only admin concept in the codebase; there is no role field. `session.isAdmin` is computed server-side in the `auth.ts` session callback purely so the sidebar can hide the link; never make a route decision from it on the client. The admin page's only backend calls (`/health/status`, `/health/metrics`) do not exist (#479). The backend mirror is `app/config.py::is_admin_email` + the `require_admin` dependency in `nextauth_auth.py` (#768; same `ADMIN_EMAILS`, fails closed, verified JWT email claim, 404 for everyone else) — `GET /metrics` uses it, and whatever #479 adds must too.
- **`getToken` in middleware must match the cookie Auth.js actually wrote (#469):** over HTTPS Auth.js writes `__Secure-authjs.session-token` (secure prefix, and `salt` === that name); over http (dev/e2e) it writes the bare `authjs.session-token`. `getToken({ req, secret })` with no `secureCookie` defaults to the **bare** name and bare salt, so on the production/staging HTTPS URL it reads nothing and `middleware.ts` redirects **every** authenticated page to sign-in — invisible to CI, which runs over `http://localhost`. `middleware.ts` reads whichever cookie is present (secure variant first, then bare) rather than detecting HTTPS, which is unreliable behind the TLS-terminating nginx; `secureCookie` cascades to both `cookieName` and `salt` in next-auth beta.32, so passing it alone selects the matching pair. Never re-add a raw-header presence-guard keyed on `${name}=`: it misses Auth.js's chunked cookies (`<name>.0`, `.1`, … for oversized OAuth sessions, which `getToken` reassembles), and the bare name is a substring of the secure one. `__tests__/middlewareSecureCookie.test.ts` exercises the **real** `getToken` against a real `encode`d cookie (the mocked-`getToken` `middleware.test.ts` is blind to this); that needs `next-auth`/`@auth/core`/`jose`/`@panva/hkdf` (ESM-only) injected into `next/jest`'s `transformIgnorePatterns` in `jest.config.js`. Tradeoff of reading both variants: the middleware no longer relates to the request scheme, so it accepts a **bare** `authjs.session-token` even over HTTPS — the `Secure` attribute's browser-level protection is no longer the only gate against a same-name cookie written from a sibling subdomain sharing `Domain=` (cookie-tossing). JWT signature+expiry verification is the real backstop (an attacker without the signing secret still can't forge a valid token); accepted because edge middleware cannot see through the TLS-terminating nginx.
- **Signup is `SIGNUP_MODE=invite|open`, read by both halves (#768):** `lib/invite-allowlist.ts::resolveSignupMode` and `app/config.py::resolve_signup_mode` must agree. An explicit value wins; **unset in production is `invite`** (fails closed — the old "empty `INVITE_ALLOWLIST` means open" made opening signup one deleted variable); unset in dev/test stays open unless an allowlist is set, so e2e needs nothing; a typo fails closed. Invite mode with an empty list admits nobody; the credentials provider passes only in open mode. `open` is logged at startup on both halves. Compose requires it (`${SIGNUP_MODE:?}`, #780) and leaves `INVITE_ALLOWLIST` optional, because compose cannot require a variable in one mode only: `preflight_staging_env.sh` refuses a mode that is neither value, and refuses `invite` with an empty allowlist. Do not flip it to `open` before the #768 backstops and #769 telemetry are live in production (#765 D3).
- **Right-to-erasure has a UI now (#482):** `app/settings/page.tsx` (the `/settings` landing — the sidebar linked here and it 404'd, #528) hosts "Delete my account data" → `POST /users/me/erase`, and the dashboard's recent-datasets rows carry a per-dataset erase → `POST /datasets/{id}/erase`. Both go through `lib/services/erasure.ts` (the only caller of those routes) and the shared `components/settings/ErasureConfirmDialog.tsx`, which gates the destructive action behind typing an exact word (`DELETE`, or the dataset name), surfaces the returned `DeletionManifest`, and — importantly — treats a manifest with `failures`/`completed_with_residuals` as an error to retry, never success (`hasResiduals` in `lib/types/erasure.ts` mirrors the backend `status`). The "what is retained" copy must track #480: billing (Subscription/Usage) is kept because `erase_user` keeps the account active. The `@smoke` spec erases one dataset as the shared e2e user, and erases a whole account as the isolated `erasure` user (#743): a real account wipe as the shared user would destroy what every other spec depends on.
- **Every `page.tsx` route must be reachable from navigation, and a guard enforces it (#528).** `/settings/billing` — the checkout entry point — shipped with **zero inbound links** and was unreachable; a page renders fine in isolation, so only a source-level check catches this. `__tests__/navigation/routeReachability.test.ts` (modelled on the backend's `test_every_router_is_mounted.py`) fails on any `app/**/page.tsx` route that no navigation reaches. It models the three real ways a route is reached — `href`/`push`/`replace`/`redirect`/`route:` literals (plain and template), the **workflow-stage config** (`lib/types/workflow.ts` `route:` entries, navigated via `WorkflowBar`/dashboard/quickstart through `buildStageUrl`; this is why `/evaluate`, `/features`, `/deploy` have no `href=`), and framework roots (`/` plus the NextAuth pages **derived from `auth.ts`'s `pages:` config**, not a `/auth/` prefix — a prefix would silently exempt any future `app/auth/` orphan). It is "referenced at least once", not a full graph walk, so a page linked only from another orphan is not yet caught. Genuinely-unreachable pages are allowlisted with a reason + tracking issue in `KNOWN_ORPHANS`; the anti-stale assertion fails if an allowlisted route becomes reachable or is deleted, so the list self-cleans. Current allowlist: `/recipes` and the legacy dataset-scoped `/datasets/[id]/engineer` flow (#738).
- **The dashboard page is a shell over `components/dashboard/` (#765).** `StageOverview.tsx` holds the quick actions, the progress bar, the stage cards and the help card; `RecentLists.tsx` the two recent lists with their loading, failed and empty states (`ListState`); `lib/hooks/useOnboardingRedirect.ts` the first-time redirect. The page keeps the two fetches and the two dialogs. The sidebar's entries are the module-level `MENU_ITEMS` in `components/Sidebar.tsx`, so adding or removing one touches no function.
- **The prediction page is a shell over `components/predict/` (#838).** `app/predict/page.tsx` holds only what both modes share (`loading`, the action error, the mode, the touched fields) and hands a `PredictionContext` to `usePredictionForm` / `useSinglePrediction` (`predictionForm.ts`) and `useBatchPrediction`. `SinglePredictionPanel` and `BatchPredictionPanel` render the two modes, and `PredictionResult` renders `InputWarnings`, the per-record `{column: "unseen" | "missing"}` the backend returns. The single form cannot send an unseen or blank value (dropdowns, every field required), so the batch summary's `input_warning_count` line is where a UI user sees the flag. The CRAP gate attributes any JSX line in a page to the page component, so one new line in a large page means splitting the page. It reads `??` as two branches, an inline arrow in JSX as unmeasured (name it in the component body), and a file it has not been `git add`ed as absent.
- **The Feature Engineering stage is a choice of columns, and training honours it (#969).** `/features` reads the dataset's columns through `lib/services/datasetColumns.ts::loadColumns` (the read the Model stage uses: `/user_data/{id}`, then `/datasets/{id}` for the other id-space) and records `{selectedFeatures, excludedFeatures}` (`lib/features/columnChoice.ts`). `useTrainingRun` sends the excluded half as `feature_config.exclude_columns`, never the target. On the backend `FeatureEngineeringConfig.exclude_columns` becomes the engineer's `excluded_by_choice`: part of the `excluded_features` union that fit, serving and the export drop, and reported apart as `excluded_user_columns` (`training_config`, the report's "Left out by you"). Before #969 the page called three routes that did not answer (the feature-definition list under the wrong id-space, and two that never existed), so the stage could not be completed and the workflow stopped before training, while two e2e journeys served all three from mocks. **A stage page needs one spec that mocks none of its routes** (`e2e/workflows/features-stage.spec.ts` is this page's), and the body the Model stage posts is pinned to `TrainModelRequest`'s own schema: `test_train_request_schema_fixture.py` captures it into `__tests__/fixtures/trainModelRequestSchema.json` (`UPDATE_FIXTURES=1`) and `trainRequest.contract.test.ts` validates against it.
- **Every backend error goes through `lib/services/apiError.ts`, and a plan-limit 402 opens ONE dialog (#767).** Services used to hand-roll `throw new Error(detail || '…')`, dropping the status and the body, so a quota refusal rendered as a bare `HTTP 402` on every surface but the chat proxy. `throw await apiError(response, '<fallback>')` keeps the old message (the backend `detail` string/message, else the fallback) and adds `status` + `detail`; a `quota_exceeded` body becomes a `QuotaExceededError` (metric always, `limit/used/tier/resets_at` nullable for the thin test-seam variant) **and is handed to the `planLimit` store (`lib/billing/planLimit.ts`), which the single `components/billing/PlanLimitDialog` in the root layout renders** — the dialog is structural, not per call site, so a new metered call adopts it by using the helper and nothing else. The error is still thrown, so inline error text keeps working. Retry loops must not retry a `QuotaExceededError` (`useChunkedUpload` skips it). The `/api/chat` proxy passes the backend 402 body through **unchanged** (every other upstream failure stays the generic sanitised body) so `AIChat` parses it with the same helper. `QUOTA_DETAIL_FIELDS` in `apiError.ts` is the mirror of `enforcement.py::reserve`'s detail keys; `tests/test_api/test_quota_enforcement.py::TestQuotaBodyMatchesTheFrontendParser` parses the TS constant against a real 402, so rename a field in both places. `components/billing/UsageWarningBanner` (root layout, sibling of `StageGuardBanner`) fetches `/billing/status` once per mount and warns at ≥80% of any finite metric with a link to `/settings/billing`; that page reads `?checkout=success|cancelled` once into state, clears the param, and on success polls the status (`CHECKOUT_POLL_MS × CHECKOUT_POLL_MAX` in `lib/services/billing.ts`) until the tier moves, because the webhook lands after Stripe's redirect. **The e2e real-402 spec runs as the PRO admin tenant, not the FREE user:** `test-e2e.sh` lifts FREE's ceilings process-wide for the shared user and limits are per tier, so `seed_e2e_data.py` puts `test-admin-12345` on an entitled PRO `Subscription` and `PLAN_PRO_UPLOADS=2` makes that tenant's second upload a real 402 (`e2e/workflows/plan-limit.spec.ts`, which uploads until the dialog appears because usage persists across runs on a local Mongo). No other spec may upload as the admin tenant.
- **A space between an interpolation and the prose after it can vanish in the server render (#473).** Observed once, in a `<p>` whose JSX line *began* with `{expr}` and carried a second one mid-sentence: the served HTML read "SheetPredictservice" while jsdom rendered it correctly, so the component test stayed green. The obvious generalisation ("two interpolations on a line") does **not** hold — sibling lines with the same shape render fine, so do not go hunting by shape. Write `{' '}` explicitly after any `{expr}` followed by prose and the question never arises. No component test can see this. **The smoke gate reads the served HTML instead (#603):** `e2e/workflows/glued-text.spec.ts` fetches `/legal/terms`, `/legal/privacy` and `/pricing` as documents on every run and fails with the offending text (`…The |SheetPredict|service is…`) for any text-node boundary with a word character on both sides (`e2e/helpers/gluedText.ts`; React separates adjacent text nodes with `<!-- -->`). The same spec sweeps every route with no dynamic segment in the full e2e run, not in the smoke gate. By hand: `curl <page> | grep -E '[A-Za-z0-9.,)]<!-- -->[A-Za-z0-9(]'`.
- **A page is narrower than the viewport, so its layout follows its container (#809).** The app shell reserves 256px on the left for the sidebar and 320px on the right for the chat panel (`lg:ml-64 lg:mr-80` in `app/layout.tsx`), so at a 1280px viewport a page has about 670px, and a `lg:` or `md:` grid inside it switches far too early: the onboarding progress column was 142px wide, with titles cut and labels on top of each other. Inside a page use Tailwind v4 container queries (`@container` on a wrapper, `@3xl:` on the grid; a named one, `@container/page` with `@3xl/page:`, when a child is a container too), as `SampleDatasetSelector` (#807) and the onboarding page do. The onboarding page is a shell over `components/onboarding/`. jsdom lays nothing out, so `e2e/helpers/layoutProblems.ts::textLayoutProblems` measures one card in a real browser (text cut off, outside the card, or drawn over other text) and `onboarding.spec.ts` runs it at 1024, 1280 and 1440px.
- **Frontend error tracking is Sentry, errors only, and every event goes through one scrubber (#769).** `lib/observability/sentry.ts::sentryOptions` is shared by `instrumentation-client.ts` (browser, `NEXT_PUBLIC_SENTRY_DSN`, **inlined at build time**, so a new DSN needs an image rebuild) and `instrumentation.ts` (server/edge, runtime `SENTRY_DSN`, `onRequestError = captureRequestError`). No DSN means no SDK. `sendDefaultPii: false` does **not** stop the server SDK attaching raw request headers, since its deny list only covers IP headers, and `captureRequestError` records `request_path` *with* the query. So `scrubSentryEvent` (`beforeSend`) replaces `request` with its query-less URL, strips `contexts.nextjs.request_path`, deletes `user`, drops console breadcrumbs and strips URL breadcrumbs. A new field that can carry a URL or a header gets scrubbed there, and `sentryServer.test.ts` (node env, real `captureRequestError`) proves the server path. `app/global-error.tsx` is the only boundary (Next 16's prop is `retry`, not `reset`). It renders its own document without app styles, and its copy must not claim the error was recorded, because with no DSN it wasn't. The `SUB_PROCESSORS` Sentry row states exactly what the scrubber lets through, so loosen one and you must change the other. The client SDK patches `global.fetch`, so a jest suite that inits it must restore jest.setup's fetch mock.
- **The training page (`app/model/page.tsx`) is a shell over `components/model-training/` (#841, #919).** `useTrainingRun` owns the run (start, cancel, completion, and `retrainKeeping`, which reruns the same target and mode with `feature_config.keep_columns` = everything kept so far plus the new picks; a run started from the form keeps nothing, because the form shows no kept columns); `ExcludedColumnsPanel` reads the model report's `excluded_identifier_columns` / `excluded_date_columns` / `excluded_empty_columns` after a run and offers a checkbox for the first two only, since an empty column has nothing to learn from. **A dataset's column names come from `columns`, read from the upload's own record first (`GET /user_data/{id}`, falling back to `data_schema[].field_name`) and then `GET /datasets/{id}`:** the upload page hands every later stage a `UserData` id, which `/datasets/{id}` answers 404 for, and a `/datasets` upload stores `data_schema=[]`. The page read `/datasets/{id}` → `data_schema` and so offered no target for any dataset, while its jest stub answered one body for every URL and the e2e specs that open `/model` returned early when the target could not be picked. `e2e/workflows/train-form.spec.ts` (`@smoke`) is the one spec that fills the form on the real stack; the early-returning ones in `train.spec.ts` prove nothing.

### Backend (`apps/backend/`, FastAPI)
- Async FastAPI, MongoDB via Beanie ODM, AWS S3 for files, `BackgroundTasks` for AI/ML work
- Canonical Beanie model registry: `app/models/registry.py` (shared by app lifespan + `setup_database` fixture)

### MCP Server (`apps/mcp/`, the `mcp` SDK's `MCPServer`)
- Exposes `eda_summary_tool` over SSE; called by the backend on the same host. Entry point `main.py`. The server class is `MCPServer` from the installed `mcp` SDK (`mcp.server.mcpserver`; `FastMCP` in 1.x), not vendored. **The server and the backend's client are on the same SDK major and move together (#620):** each app pins `mcp>=2,<3`, and a new major is a migration of both, never a relock. Relock either app for it with `uv lock --upgrade[-package mcp] --exclude-newer <a week ago>` and then a plain `uv lock`, which drops the recorded date and keeps the versions.
- **The backend client speaks real MCP over SSE (#506), not REST.** `app/services/mcp_integration.py` uses the `mcp` SDK (`sse_client` + `ClientSession` over the `/sse` stream, bearer token) and calls the tool by its registered name **`eda_summary_tool`** with a single `params` object **`{dataset_id, user_id}`** (`EdaInput`); the server reads the dataset from S3 server-side and authorizes ownership, so the client never sends dataset contents. Bound **both** `timeout` and `sse_read_timeout` by `MCP_TIMEOUT` (tool results arrive over the SSE stream; the SDK's read default is 300s). A `{success: False}`/transport failure **falls back**, never fabricates analysis. **The client reads the result's fields as attributes (`result.is_error`, `result.structured_content`), never through `getattr` with a default (#620):** 2.x renamed them from the 1.x camelCase, and the default turned the old names into "no error", so a failed tool call would have come back as a result. A tool error is raised after the session closes, because inside it the transport's task group replaces the message with "unhandled errors in a TaskGroup". Unit tests build the SDK's own `CallToolResult`, not a stand-in. The pre-#506 client POSTed to nonexistent REST paths, `await`ed httpx's sync `.json()`, and used a wrong tool name/args — a test mocking an `AsyncMock` response hid all three.
- **`apps/backend` is deliberately NOT a package (no `__init__.py`) (#506).** Restoring one puts the repo `apps/` dir on pytest's `sys.path`, and the sibling `apps/mcp` package (literally named `mcp`) then **shadows the installed `mcp` SDK** during backend tests (`import mcp` → `apps/mcp`). Any backend import of the `mcp` SDK breaks the moment that file returns. A backend test that starts the MCP server as a subprocess uses `require_service` when `apps/mcp` isn't synced: the `backend-integration` job runs `uv sync --frozen` in `apps/mcp` before its tests (#998), so with `CI_REQUIRE_SERVICES=true` a missing server fails the gate, while locally an unsynced `apps/mcp` still skips. Until #998 the job never synced it and the SSE round trip skipped on every run. `test_mcp_round_trip_runs_in_ci.py` pins the sync step and bans a plain `pytest.skip` in that suite.

## Backend Conventions & Recurring Gotchas
- **`app/main.py` is the only place a router is mounted (#471, #530).** Two aggregators used to sit beside it (`api_router` in `app/api/routes/__init__.py`, `api_v1_router` in `app/api/v1/`), attached to nothing, and a router registered only there was dead: the whole data-issues feature 404'd that way while the frontend called it. Both are gone. `tests/test_api/test_every_router_is_mounted.py` walks the live route table and fails on any route module that is not mounted (its allow-list is empty), and on any `include_router` call outside `main.py`. A feature that has never been reachable has never had its authz, metering or error paths exercised — review it as new code when you mount it (#471 needed `quota("ai_calls")` on `/detect`, released when the analyzer did not run, and the metering registry now follows one import hop so a route reaching a model *through a service* is in scope).
- **The published API description is the live route table (#512).** `GET /api/v1/docs/openapi.json|yaml` return `published_spec(app)` from `app/services/api_documentation.py`: a copy of `app.openapi()` plus a description, the project's licence and the support contact. It names no server: a document without one describes the host it was fetched from, and behind the TLS proxy the app does not know its own public scheme (`request.base_url` says `http`). Nothing there may state by hand what the app can state itself: each operation already carries its own authentication requirement (no blanket rule), the rate limits in the description are read from `settings` and `PLAN_LIMITS` (the limiter is off in the test env, and the text says so), and no host is typed. The hand-written general SDK (`/docs/clients`, `/docs/integrations`, `/docs/postman`) is gone: it targeted `/models/train` and `/data/upload`, which no route serves. The SDK is the per-model one (`sdk_generator.py`, `/ml/{id}/sdk`). - **Two dataset id-spaces:** `DatasetMetadata` (string `dataset_id`, S3 `datasets/{user}/...`, string-keyed children) and legacy `UserData` (ObjectId, `Link` DBRef children) are **dual-written**, linked only by `(user_id, s3_url)`. Deletion cascades across both via `DatasetErasureService` (#259). **That link is mutable, so every writer that moves a dataset to a new file must move both twins (#467):** go through `app/services/dataset_link.py::record_new_file(doc, new_url)`, which finds the twin through the *old* location and points both `file_path` and `s3_url` at the new one (the first move keeps the upload in `DatasetMetadata.source_s3_url`). **It writes each twin with one targeted `$set`, never `save()` (#723):** a full save of the caller's in-memory snapshot reverted whatever another writer had changed since it was loaded (#520's clobber class). It owns the link fields plus `_SHAPE_FIELDS` (`num_rows`, `num_columns`, `columns`, `file_type`, and `data_schema` on the caller's own document). A caller that sets any other field before the move must add it there, or the field is silently not persisted. Writing `s3_url` on one side alone is how erasure lost the PII-carrying twin and training — which reads `UserData.s3_url` — kept using the pre-transform file while the UI showed the transformation applied. `scripts/inventory_dataset_links.py` counts pairs whose link is already broken. **Every superseded current-file is tracked and erased (#525):** `record_new_file` appends the old `s3_url` to `superseded_s3_urls` (on both twins) on every move, because once `s3_url` moves off an object nothing else references it (a `DatasetVersion` points at a *separate* `versions/` copy, not the `transformed/` current-file). They now go through `record_new_file(dataset, version.s3_url)` like the forward writers, and must set the restored **version's** `num_rows`/`num_columns`/`columns` on the dataset first, since `record_new_file` copies the doc's shape onto the twin and `model_training` reads `num_rows`/`num_columns` off the twin for the mode recommendation. **`record_new_file` also clears what was computed from the old file (#960):** the chart caches (Redis `viz:{id}:*` and the `VisualizationCache` rows, which never expire) and the column statistics are keyed by the upload's id and carry no trace of which file they came from, so after a transformation, an undo or a data-issue fix the histogram, box plot and correlation matrix kept answering with the data from before. A new cache of anything derived from a dataset's file is cleared there too (`_forget_what_was_computed`), or carries the file's URL in its key. **The chart cache does both (#964):** a `VisualizationCache` row records the `source_url` it was computed from and its Redis key ends in a digest of it, and `get_cached_visualization(…, source_url)` serves an entry only for that file, because a request that began before a move can finish after the clear and write the old chart back. The generators read the dataset first and pass `dataset.s3_url` to the read and to the write. An entry with no `source_url` predates the field and is treated as a miss. Because undo/redo **revisit** URLs, `record_new_file` keeps the invariant **the current file is never in `superseded_s3_urls`** (it drops `new_url` from the list when setting it current), or erasure would delete the live file on a move-back; harmless no-op for the forward writers, which never revisit.
- **A dataset's children are keyed by two different ids, and erasure sweeps both (#943).** Training stores `MLModel.dataset_id` and `TrainingJob.dataset_id` as `str(UserData.id)`; the transformation path keys versions, configs and lineage on `DatasetMetadata.dataset_id`. The two are equal only for a #850 twin. `_erase_one_dataset` used to sweep models and string-keyed children only when a `DatasetMetadata` parent existed, and only under the id it was called with, so erasing a UI upload (no twin until its first transformation) left every model trained on it, the model's S3 artifacts and its training job, and answered `completed`. It now resolves both parents through `(user_id, s3_url)` in **either** direction (`_owned_parents`) and runs `_erase_keyed_children` for every id in `_id_of(parent)`. A new child collection keyed by `dataset_id` goes in `_STRING_KEYED_MODELS` and is then swept under both. A test of this cascade must store the model **the way `train_model_task` does** (under the upload's id): the #497 proof seeded one under the id it then erased and never met the bug. **Every delete of a dataset is this cascade (#864):** `DELETE /user_data/{id}` deleted the row alone, leaving the upload's object, its twin, its versions and its history where nothing would find them; it now calls `erase_dataset` like `DELETE /datasets/{id}` and the erase route, and answers a retryable 502 only while the row is still there (a child the cascade could not delete keeps it); an object left once the row is gone is on the audit log, and the delete answers success. The e2e `cleanupDataset` fixture relies on it, so a spec's dataset takes its models, training and batch jobs with it.
- **Erasure deletes only from its own bucket (#616):** `erasure_service._s3_key(url_or_key, bucket_name, manifest)` refuses a stored URL that names a bucket other than the one erasure runs against — the key goes on the manifest as a failure naming both buckets and nothing is deleted, because deleting that key from *our* bucket would remove whatever unrelated object shares the name. Bucket-less URLs fall back to the configured bucket; bare keys pass through. The failure is prefixed `s3 delete` so that, like every other S3 residual, it does **not** block the parent's Mongo deletion (`_delete_parent_if_clean` only retains a tombstone for Mongo-child failures) — a stored URL never changes between runs, so a blocking failure would make that dataset permanently un-erasable.
- **`erase_user` erases the user's data but keeps the account (#480):** its only caller is `POST /users/me/erase`, which deletes data, not the auth record. `_sweep_user_scoped` deletes every account-scoped collection the user owns — `APIKey` (the auth path does a live `find_one({key_hash})` per request with no cross-request cache, so deletion revokes immediately), the feature store (`StoredFeature`/`FeatureVersion`, the latter keyed by parent `feature_id` not `user_id`, so resolve owner feature ids first/`FeatureCollection`), and recipes (`TransformationRecipe`/`RecipeExecutionHistory`/`SharedRecipe`) — but **retains `Subscription` and `UsageRecord`**: the account stays active and billable, so deleting the local Subscription mirror would enforce a paying customer as FREE until the next Stripe webhook and deleting UsageRecord would reset quota mid-period. That is live account state, not orphaned data; full billing teardown belongs to an account-closure flow that does not exist yet. A recipe the user shared onward lives in the *recipient's* row (`user_id`=recipient), so it is not swept by user_id — its `original_owner_id` **and** the duplicate `metadata.shared_by` are anonymized to a tombstone rather than deleting the recipient's copy. The same "scrub the co-tenant's row, don't delete it" rule covers two more cross-tenant residuals: a `BatchJob` owns S3 objects (`input_path`/`output_path` under `batch-jobs/{user}/…`), swept via `_erase_batch_jobs` through the one S3 core in both the user sweep and the model cascade (#661); and the erased id can sit in **another** tenant's `StoredFeature.shared_with` / `FeatureCollection.shared_with`, `$pull`ed from every co-tenant's ACL (#662). Both record their counts on the manifest.
- **Chunked upload (#454, #462, #463, #464):** the flow was broken end-to-end until #582 and its four defects had to land together, so treat it as one surface. Init takes **`Form(...)`**, not query params — the client posts a url-encoded body, and the mismatch 422'd every init before the handler ran. Sessions are owned: `init_upload` records `user_id`, ids come from `secrets.token_urlsafe` (never derived from filename/size/timestamp), and every operation resolves through **`get_session(session_id, user_id)`**, which returns `None` for both unknown and foreign ids so the two answer identically — a distinguishable response confirms another tenant's session id exists. Session ids are also spliced into filenames under `temp_dir`, hence the `[A-Za-z0-9_-]` guard. `complete` **claims** the session (reads and removes it in one synchronous step) before any await: there is no await between the lookup and `user_data.insert()`, so two racing completes otherwise both pass the checks and write two S3 objects, two `UserData` rows and two charged quota units, both 200 so nothing refunds. **Concurrency is derived from live sessions, not a leaky counter (#526):** the per-user cap is `_active_upload_count = ChunkedUploadHandler.count_active_sessions(user)` (non-expired chunked sessions) **+** `RateLimiter.active_uploads[user]` (transient, always-`finally`-balanced work: every `/upload/secure` request and every chunked `complete` finalization). `init` does NOT `start_upload` — the live session *is* the count, so an abandoned session (closed tab) stops counting at expiry and can never permanently lock the user out (there is no counter to forget on a missing `complete`/`abort`). `complete` takes a transient slot *after* claiming (which popped the session) so the parse+S3+insert still counts, released in `finally`. Both `/secure` and chunked `init` check the same combined total, so it is one shared budget. **Expiry is enforced where a session is resolved (#584):** `get_session` answers 410 for the caller's own session once it is past `expires_at`, so no operation can append to or complete one (only `resume` used to look). The owner check comes first, so a foreign or unknown id is still the same `None`; `abort` passes `expired_ok=True`, since discarding an expired session is the point. The expiry sweep (`cleanup_expired_sessions`, run on every `/upload/secure` and chunked `init`) also reads `{temp_dir}/*.json` for sessions this process does not hold, which after a restart is all of them, and deletes the expired ones' files. It never loads a live one into the store: another worker may own it and the copy would go stale. **`upload_chunk` holds a per-session `asyncio.Lock` around its read-modify-write (#580):** without it, two concurrent POSTs of the same not-yet-uploaded chunk both passed the `already_uploaded` check and both appended, and that duplicate could make `len(uploaded_chunks) == total_chunks` fire while a *different* chunk was still missing — flipping a holed session to `complete`. The membership check must be atomic with the append, so the file write is inside the hold (concurrent *different* chunks of one session serialize). Locks are created lazily (no `await` between the get and the insert, so race-free on the loop) and swept when their session is gone. Like the session dict, the lock is **per-worker** — two gunicorn workers racing the same chunk are still unguarded; the durable fix is the Redis-backed store the `# In production, use Redis` note anticipates. (Before #526: one `start_upload` at init leaked when the session was abandoned; the chunk route's *double*-release had pinned the count at 0, hiding the cap until #582.) S3 keys are **server-derived**, `datasets/{user_id}/[masked_]{uuid}.{ext}`, built only by `dataset_s3_key` in `app/utils/s3.py` — every dataset-writing route (`/upload/`, `/secure`, `/confirm-pii-upload`, chunked `complete`, and `/datasets/upload` since #496) calls it, and there is deliberately no helper that can express a key without the owner (#581 deleted `generate_s3_filename`, which three routes were still reaching for). The client filename is metadata only and must never reach the key. Objects written before #581 sit at the bucket root as bare `{uuid}.{ext}`, and since #615 no reader admits them. `scripts/reconcile_unprefixed_s3_keys.py` moves any such object that a served database still references under its owner (copy, verify ETag+length, rewrite `UserData`/`DatasetMetadata`, then delete; orphans are reported and never touched; dry-run by default). On staging every one was an orphan. Erasure's `_s3_key` derives keys through the same `parse_s3_url` the readers use (#481) — the hand-rolled parser it replaced returned `bucket/key` for endpoint-style URLs and kept presigned query strings, so `delete_object` matched nothing and erasure reported success over a surviving object. The sibling routes `/secure` and `/confirm-pii-upload` still enforce a high-risk-PII confirmation gate the chunked route does not (#583).
- **A request that fails after writing an S3 object deletes what no document ended up owning (#735).** Every upload route puts the object before it inserts the row, so a failure in between (schema inference, validation, the insert) left an object erasure could never reach. `/datasets/upload` parses first and answers 400 for a file it cannot read (`UnreadableFileError`), so that file is never put (#899). `app/utils/s3.py::upload_file_to_s3` records each key it writes in a per-request context variable (a decorator, `_recorded`), and `UnownedUploadCleanupMiddleware` (`app/middleware/upload_cleanup.py`, mounted beside `QuotaRefundMiddleware`) acts on a 4xx/5xx or an unhandled exception. It is one middleware rather than a `try/except` per route for the refund middleware's reason: a new writer is covered by calling the helper. **Ownership is looked up, never inferred from where the request failed:** an object is kept if any `UserData` or `DatasetMetadata` row names its key in `s3_url`, `file_path`, `source_s3_url` or `superseded_s3_urls`, or a `TransformationConfig.current_file_path` or `BulkTransformationJob.output_file_path` does (a new field that can hold a dataset location must join `_OWNERS`), because an insert can land and then raise, and `/datasets/upload` writes two rows. The match accepts the key raw or percent-encoded, since `/upload/` stores a presigned URL. The lookup is scoped to the tenant in the key's second segment, so a writer through the helper must key its object `{namespace}/{user_id}/…` with the same `user_id` its rows carry (every one does); a key of another shape is kept. When the lookup or the delete itself fails, the object is left and logged: an orphan is reported by `scripts/inventory_orphaned_s3_objects.py`, while deleting a referenced object loses the customer's file. **A route that reports failure in a 200 says so with a decorator (#898):** `@discards_uploads_on_reported_failure`, placed under the `@router` line, runs the same ownership lookup when the handler's answer has `success` false. It is on `POST /transformations/apply`, `/transformations/pipeline/apply` (so auto-clean and recipe apply, which call it in-process), `/data-issues/apply-fix`, `/data-issues/batch-fix` and the feature apply route; a new route that uploads and then answers `success: false` takes the same line. `discard_unowned_uploads()` is the call underneath, the counterpart of `enforcement.release(request)`. A bulk transformation job outlives its request, so `_process_bulk_job` starts its own record (`record_request_uploads()`) and discards from it when the job fails, before it marks the job failed so a client polling the status never sees "failed" with the file still there; that also keeps the job's file out of the request's list, which a task started with `asyncio.create_task` would otherwise inherit. Because the lookup decides, a failure reported after the dataset has moved keeps the file the row now names. Not covered: a client disconnect, and objects written without the helper (versions, model artifacts, batch jobs). A test that patches `upload_file_to_s3` at the route module bypasses the recorder: wrap the stand-in with `app.utils.s3._recorded` (`test_reported_failure_discards_uploads.py` does), or use a real put (LocalStack).
- **An Excel dataset's `file_type` is its extension, set at the model (#902).** `/upload/secure` and chunked `complete` wrote `"excel"`, `/upload/` and `/datasets/upload` wrote `"xls"`/`"xlsx"`, and readers disagreed about which they knew (the feature store raised `Unsupported file type: excel`). `UserData` and `DatasetMetadata` both run `app.utils.filenames.excel_under_its_extension` as a `model_validator(mode="before")`: `"excel"` becomes `xls` or `xlsx` from the filename, then the object's URL (a workbook nothing names is `xlsx`). Validators also run when a row is read, so a row stored before this reads back under its extension and no reader needs the old spelling; do not add `"excel"` to a new reader. The one reader with its own vocabulary is `DataProcessor` (`/data/process`, `/datasets/upload`), which calls a workbook `excel` and maps the stored extension through `_reader_type`; a new reader dispatches on `xls`/`xlsx`. Because the model hides the stored value, `scripts/audit_dataset_file_types.py` reads the **raw** documents and fixes with a targeted `$set`, never a model `save()`. **`/upload/confirm-pii-upload` stores the type of the bytes it wrote (#937):** `csv` for a masked copy, whose key ends in `.csv` too, and the upload's extension otherwise (`_store_confirmed`). Before that it stored no type, and a masked workbook was CSV under an `.xlsx` key. Two rules cover those rows: training reads a row with no declared type by its bytes (it reads through `read_dataframe_from_bytes` like every other reader since #1019, so a declared type its bytes contradict fails the job with that reason, not a bare parse error), and `dataset_link._file_type_of` calls any `masked_` object `csv` whatever its name says, so the audit script and twin creation do not type one as a workbook. A writer that changes the bytes' format must change the stored type and the key's extension with it.
- **Client filenames are normalised at the model (#585):** `UserData` and `DatasetMetadata` run `sanitize_filename` on `filename` / `original_filename` — basename only, no control characters, no leading dots, ≤255 chars, never empty — so every writer (`/upload/secure`, `/confirm-pii-upload`, `/chunked/{id}/complete`, `/upload/`, `/datasets/upload`, and the next one) stores the same safe form. Both documents also set `Settings.validate_on_save = True`: Pydantic validates on construction, not on assignment, so `PUT /user_data/{id}`'s `setattr` path skipped the validators until save re-ran them and no consumer building a `Content-Disposition` header or a path from them has to know they were once raw. The S3 key never came from the filename (#464); this closes the stored copy. Normalise rather than reject: exporters produce odd-but-honest names, and a raw copy "alongside" would keep the trap. **Every download header is built by `app/utils/filenames.py::attachment_disposition` (#648):** a model's name is a display name, so it is not normalised where it is stored, and it reached `Content-Disposition` raw in eight export routes (quotes and CR/LF passed through, and a name outside latin-1 could not be exported at all: the encode error surfaced as a 400). The builder normalises, then writes both RFC 6266 forms (`filename="ascii"; filename*=UTF-8''…`). `test_no_download_header_is_built_by_hand` fails on an `attachment; filename` literal anywhere else in `app/`.
- **One bucket, one resolver, readers and writers alike (#567, #621, #622):** `app.config.resolve_configured_bucket()` (`AWS_S3_BUCKET`, then the historical names) is the only precedence; `utils.s3.configured_bucket()` / `allowed_bucket()` delegate to it, `S3Service` and `VersioningService` read through them **per call** (`VersioningService.bucket_name` is a property; `S3Service` writers use `_live_bucket()`), and there is no `settings.S3_BUCKET` — it was a third precedence frozen at import. Every `S3Service` write method (`upload_file_obj`, `delete_file`, `get_file_size`, `generate_presigned_url`) runs its key through `validate_object_key()` before touching boto3, exactly like `download_file_bytes`; a new writer must build a namespaced key (`datasets|transformed|models|batch-jobs|exports/{tenant}/…`). `validate_object_key` is bucket/traversal/namespace hygiene, **not** per-tenant authorization — pass an ownership-checked key. `tests/test_services/test_s3_write_contract.py` sets three env names to three values and asserts every resolver and both services agree. **No call site may read the bucket env vars itself (#507):** resolve only through `configured_bucket()`/`allowed_bucket()` — `test_s3_write_contract.py::test_no_call_site_resolves_the_bucket_independently` greps `app/` and fails on a raw `os.getenv("AWS_S3_BUCKET"|…)` outside `config.py`, which is how the upload presign and the health readout had drifted onto their own precedence. **Startup fails fast on a missing/unwritable bucket (#495):** the lifespan calls `s3_service.verify_bucket_writable()` **only when `is_production_like()`** — it raises on no configured bucket, on mock-mode credentials in production, or on a failed put+delete write-probe, so a deploy refuses to boot rather than write to a guessed bucket (and it catches a broken credential rotation, P1.33). The `_live_bucket`/reader default `"narrative-modeling-dev"` is therefore dev-only-reachable; in production the boot check fires first. dev/test/CI skip the probe (`is_production_like()` is False), so it never trips a test that boots the app via `LifespanManager`. **On a versioned bucket a plain delete is not a delete (#529):** it keeps the bytes as a noncurrent version and adds a delete marker, so the probe left one of each per boot of each worker (154 of each on staging inside a month, in a bucket with no current object). The probe now deletes the version it wrote (`_remove_probe`, `VersionId` from the put) and falls back to the plain delete when the policy lacks `s3:DeleteObjectVersion`, so it can never refuse a boot. Anything else that writes and removes a scratch object in the bucket does the same. What a plain delete leaves is bounded only by the bucket's lifecycle rule (`scripts/ops/configure-s3-backup.sh`: noncurrent versions after 30 days, then their delete markers), and that rule is on a bucket only once the operator has run the script (#299).
- **Every boto3 S3 client is built through `create_s3_client()` with a bounded Config (#519).** The factory always attaches a `botocore.config.Config` — `connect_timeout=5`, `read_timeout=20`, standard retries `max_attempts=3`, `max_pool_connections=20` (env-overridable), path-style merged in for an `AWS_ENDPOINT_URL` — so a hung S3 endpoint can't outlive the 120s gunicorn worker (worst case ≈ `attempts × (connect+read)` ≈ 80s; `read_timeout` is the per-socket-read idle, not a transfer cap, so it never truncates a streaming download). Never construct a raw `boto3.client("s3", ...)`. `get_s3_client()` (the utils entry) **reuses** one client, keyed on a `(access-key, secret, endpoint, region)` signature so a rotation or endpoint change rebuilds on its own; it stays lazy (returns `None` on missing env, so secret-less builds don't crash) and shares the thread-safe *client*, never the session. `reset_s3_client()` clears the cache (tests / post-rotation). `S3Service`/`VersioningService` build once at construction. `download_file_from_s3` uses the shared client too (#722): `get_s3_client() or create_s3_client()`, so with no credentials in the environment it still builds one and lets boto3 report what is missing, as before. A test that stubs the downloader's client patches `app.services.s3_service.get_s3_client` (the point of use), or `app.utils.s3.create_s3_client` when it is the reuse itself under test. Patching `s3_service.create_s3_client` only reaches the no-credentials fallback, so such a test passes in CI, which exports no AWS variables, and fails on a machine that has them. `tests/conftest.py` empties the shared client cache around every test, so a stubbed `boto3.client` is never handed a client an earlier test built. A test that sets credentials also sets `AWS_ENDPOINT_URL` to a dead local address, because a client built for real with fake credentials sends its request to AWS.
- **A chart reads only the columns it draws and filters on (#712):** `s3_service.read_columns_from_bytes(content, columns)` asks a Parquet file (what a dataset is once transformed) for those columns alone and parses a CSV with the others skipped; the three chart routes share `visualizations._chart`, which works the column set out from the chart and the parsed filter list before anything is downloaded. The object is still downloaded whole: the saving is in decoding and memory.
- **Which S3 location to download (#170, #466):** `s3_url` is always a URL; `file_path` is a **raw key** right after an upload and a **full URL** once a transformation has written one back. The validated downloader takes only URLs, so `file_path or s3_url` handed a key to it and the *first* transformation on every dataset failed while every later one worked. Never branch on the shape yourself — go through `app/utils/s3.py::downloadable_url(file_path, s3_url)`, which passes a URL through and places a key in the allowed bucket; the strict resolver then checks it like any other URL. `S3Service.download_file_bytes` is the one *key-only* entry point — feed it the key from `resolve_validated_object(downloadable_url(...))` (bucket allowlist checked *before* the key is extracted), never `file_path` directly. Only a LocalStack test (`tests/test_integration/test_transformation_first_apply_localstack.py`) can see this class of bug; a mocked downloader accepts anything.
- **`file_type` must track `s3_url`, and the loader enforces it against the bytes (#524).** A transformation rewrites `s3_url` to a `.parquet` object; `app/services/dataset_link.py::record_new_file` writes the matching `file_type` (from the new extension) in the same operation on both twins (#467/#630), so the pair can't diverge going forward. **That derivation reads the object's name, so a name must say what the object holds (#888):** a transformation version is keyed `…/versions/{version_id}/data.parquet`, not under the upload's filename. Before that a version held parquet under the upload's name (`…/d.csv`), and an undo stamped `csv` over parquet bytes, which broke training. No served database holds such a version (counted on staging in #892), so `record_new_file`, the column-stats loader and the audit script read the type off the name alone; a writer that stores one format under another's name reopens this. Downstream, `s3_service._read_dataframe` validates a **known** `file_type` against the object's magic bytes (`PAR1` at head **and** footer — both, so a CSV starting with `PAR1` isn't a false positive) and raises `FormatMismatchError` ("stored file_type and s3_url disagree") instead of an opaque pandas parse error; the `file_type=None` path (used by the transformation readers via `data_utils.get_dataframe_from_s3`, 14 call sites) dispatches on the file's own bytes (`_kind_of`: Parquet magic, the zip header of `.xlsx`, the OLE header of `.xls`, a leading `[`/`{` for JSON, else CSV) since #858. It used to try `read_csv` first, which does not fail on JSON: it returns junk columns, and a transformation then wrote them back over the dataset. `"excel"`, which `/upload/secure` stores for a workbook, is a declared type the typed path reads too. Legacy rows written before the fix are reconciled by `scripts/audit_dataset_file_types.py` (read-only default, `--apply`, extension is authoritative; #731 runs it on prod). The chart readers (`visualization_cache._dataset_frame`, `routes/visualizations._load_dataframe`) and the feature store read through `s3_service.read_dataframe_from_bytes` since #733: the charts by what the bytes are, the feature store by its declared type. Before that they parsed everything as CSV, so every chart failed for a dataset transformed once. The data preview and export (`data_processing._preview_format`, `_read_source_dataframe`) do too since #940: by the stored type, or by the bytes for a row with none, never by the upload's filename, which made every transformed dataset's export fail. A new reader of a stored dataset uses that function or `load_dataframe_from_s3`, never a bare `pd.read_csv`.
- **`UserData.id` is an ObjectId; a request id is a string (#465):** `UserData.id == file_id` and `{"_id": request.dataset_id}` build `{"_id": "<str>"}` and match nothing — ten endpoints answered a permanent 404 while their tests patched `find_one` and stayed green. Coerce with `app/utils/object_id.py::require_object_id(value, what)` (400 on a malformed id); only `Document.get(str)` is coerced by Beanie itself. A handler that wraps its lookup in `try/except Exception` must `except HTTPException: raise` first, or the 404 becomes a 200 `{success: false, error: "404: …"}` — which is what the four `transformations.py` handlers did. Tests for a lookup must seed a real document; a patched `find_one` cannot see this class of bug.
- **One S3 download core (#531, #567):** every read of a stored URL or key goes through `app/utils/s3.py` — `resolve_validated_object()` (parse → `allowed_bucket()` → `validate_object_key()`) and `check_object_size()`. Exactly one `get_file_from_s3` (utils, BytesIO) and one `download_file_from_s3` (`s3_service`, temp file) exist, both on that core; `S3Service.download_file_bytes` validates its key the same way. **No route or service may call boto3's `get_object`/`download_file*` itself** — `tests/test_services/test_s3_download_registry.py` finds any raw download outside the core and fails, which is how `column_stats.py` and the preview route were caught bypassing the allowlist. `validate_object_key` no longer admits the pre-#581 bucket-root `(masked_){uuid}.{ext}` shape, so none of its readers or writers do either (#615). The transitional `allow_legacy_root` flag is gone because the only DBs still referencing those objects are legacy pre-staging ones that no deployed service reads. Do not reintroduce it. Two consequences follow. First, erasing a row that still points at a root key records an `s3 delete` residual and still deletes the row, leaving the object behind. Every bucket-root object is one of these, so `list-objects-v2 --delimiter /` finds them. Second, only `reconcile_unprefixed_s3_keys.py` touches root objects, through raw boto3. The write methods validate their key too (#622), but a key is hygiene, not authorization, so do not hand them client input. Every reader now pays one `head_object` for the size cap before the read.
- **Transformation engine contract:** the engine executes exactly **4** types — `TransformationEngine.TRANSFORMATION_CLASSES` = `remove_duplicates`, `trim_whitespace`, `drop_missing`, `fill_missing`; `FILL_MISSING` uses `method` (mean/median numeric-only, plus mode/ffill/bfill) and is how imputation is exposed. **`GET /transformations/available` is derived from that registry via `available_transformations()` (#499), never a hand-list** — it once advertised ~22 types while 4 executed, so ~18 menu entries failed or silently did nothing. Display metadata (`CATEGORY`/`LABEL`/`DESCRIPTION`/`PARAMETERS_SCHEMA`/`REQUIRES_COLUMNS`) lives on each transformation class; `test_transformation_available_registry.py` asserts advertised == executable and that every advertised type runs. **The config UI (`TransformationConfigDialog.tsx`) treats a param as required unless its schema has `required: false` or a `default`** — every advertised param is optional at the engine level, so each must be marked `required: false` (guarded by the same test) or default-behavior flows are unconfigurable. **The Prepare stage's calls live in `apps/frontend/lib/services/pipelineApi.ts` (#855), and their payloads are pinned to the routes' request models:** `test_transformation_request_schemas_fixture.py` writes each route's JSON schema plus the `/available` registry into `__tests__/fixtures/` (`UPDATE_FIXTURES=1`), and `pipelineApi.contract.test.ts` validates the built payloads against them, so a renamed request field fails jest instead of 422-ing in production. **Recipe browse and load are pinned the same way (#859):** `fetchRecipes(filter)` reads `/transformations/recipes` (all), `?include_public=false` (mine) and `/transformations/recipes/popular`; `test_recipe_list_response_fixture.py` captures each route's query parameters and a real response into `__tests__/fixtures/recipeLists.json`, and the contract test checks every list request against them and reads a recipe's `steps` out of the captured response. `components/transformation/RecipeBrowser.tsx` shows a failed list as an alert (it used to fetch a route that does not exist and swallow the 404, so Browse was always empty), and `recipeFlow` builds the pipeline from `recipeSteps(recipe)`. The browser pages through the list (`fetchRecipePages`; page one is the route's default, a later page names itself) up to its `total` (#929), and loading refuses a recipe holding a step type that `/transformations/available` does not list, naming the step (`unrunnableSteps`). `e2e/workflows/prepare-pipeline.spec.ts` saves a recipe, finds it in Browse and loads it back on the real stack (`@smoke`). **One order for both views (#862):** `components/transformation/runOrder.ts::planOrder(nodes, edges)` is the order the steps run in: the arrows drawn on the Visual canvas when there are any, the listed order when there are none. Preview, Apply, recipe save, Export Code, the Chain view's list and the "drop what a part-way apply already ran" logic all read it; none may map `nodes` directly. Arrows that are not one chain through every step (a fork, a merge, a loop, a step left unconnected) are refused on the page with the reason. A Chain-view reorder or delete, and a step added while arrows exist, redraw the arrows (`chainEdges`), so the two views cannot disagree. jsdom cannot drag an arrow, so `TransformationPipeline.order.test.tsx` replaces `ReactFlow` with one button per possible arrow that calls the component's own `onConnect`. **Export Code is a real route (#860):** `POST /transformations/export-code` takes `{steps}` and returns `{language, filename, code}`, a pandas script with a `transform(df)` and a command line. Each transformation class writes its own statements in `code()` beside the `apply` they mirror (abstract on `BaseTransformation`, so a type cannot join the engine without it); every parameter is emitted with `repr`, so a column name is a string literal and never code. `test_pipeline_code_export.py` executes the generated script for every case and compares the frame with the engine's, so change `apply` and `code` together. A saved recipe's export (`POST /recipes/{id}/export`) returns the same script; it used to have a hand-written generator that emitted nothing for `drop_missing`. `POST /transformations/preview` runs **every** step in order (all but the last on the whole frame, the last previewed) and names a failing step; apply stays one request per step so each is a history step, and a part-way failure reports how many steps landed (`PipelineApplyError.applied`) so the UI drops them instead of re-sending them. A non-executable enum type (an old saved recipe) fails gracefully (`validate_transformation` catches the `ValueError` → `success=False`, not a 500). The `/datasets` upload path stores `data_schema=[]` with real columns in `inferred_schema` (a `SchemaInference` dump).
- **Transformation history is one `TransformationConfig` per dataset (#800).** `apply_transformation` reuses the dataset's newest owned config, so steps accumulate in one ordered list with the model's own `current_position` / `can_undo` / truncate-on-new-step. Every history operation resolves it through `TransformationService.get_dataset_config(dataset_id, user_id)`, never `get_transformation_config`, which looks up by `config_id`, a different id space; that mismatch made every history route 404. The lookup is owner-scoped, so another tenant's dataset is the same `NotFoundError` as an unknown one. Datasets transformed before #800 hold one config per step, and the newest is their current state. **A transformation accepts either id space (#850):** the UI uploads through `/upload/secure` and chunked `complete`, which write only `UserData`, and hands that ObjectId to the Prepare stage. Preview, apply and the history move resolve it with `dataset_link.ensure_metadata_twin(dataset_id, user_id)`, which reuses the upload's twin on `(user_id, s3_url)` or creates one keyed by the upload's own id, with a best-effort base version. A new transformation-path lookup goes through it, never `DatasetMetadata.find_one({"dataset_id": …})`, or UI uploads 404 again. The bulk service does too (`bulk_transformation_service._owned_dataset`, and `_process_bulk_job` for the job it later runs); `apply_bulk_transformation` resolves the dataset before it creates the job, so a foreign or unreadable upload is refused with nothing created (#856). CSV, Excel, JSON and Parquet uploads get a twin (`_TRANSFORMABLE`); any other type is refused with its type named, because a tab-separated file reads as one junk column and the apply would overwrite the live file with it. The base version is written by the first apply, from the frame it transforms (`TransformationService._version_for` → `_parent_version`), and never at twin creation, so a failed write heals on the next apply.
- **One apply at a time for a dataset, across workers (#853).** Two first transformations at the same moment (a double-click) both missed the lookup for the dataset's history and both created one, both created the upload's metadata twin, and each transformed the same starting file. `app/services/dataset_lease.py::dataset_lease(name)` is the mutex: a `DatasetLease` document whose `_id` is the name, so the insert itself decides the holder and no unique index had to be added to a collection that already holds duplicates. A living holder renews it every `RENEW_SECONDS`, so it expires (after `LEASE_SECONDS`) only when its holder died, and a release deletes only the holder's own. `apply_pipeline` runs under `apply:{user}:{history_key}` and reads the dataset after taking it, so the second apply transforms what the first wrote; one that cannot get it within `WAIT_SECONDS` answers `success: false` and writes nothing. `ensure_metadata_twin` creates the twin under `twin:{user}:{upload id}` and looks again once it holds it. Every other writer that moves a dataset takes the same lease (#1022): through `dataset_link.holding_the_dataset(dataset_id, user_id)` (undo, redo and jump in `HistoryService`; the bulk job inside `_process_bulk_job`, since it runs after its request answered) or the route decorator `@holds_the_dataset(dataset_id_of, busy)` (the two data-issue fix routes and the feature apply route), which builds the route's own failure answer from `DATASET_BUSY` when the wait runs out. `test_writers_wait_for_the_dataset.py` fails on a `record_new_file` call site that is not listed with the module that takes its lease. An in-process `asyncio.Lock` is not a substitute: the container runs two workers. A unit test with no database stubs `dataset_lease` at the module that uses it.
- **Every move of a dataset is either a history step or closes the history (#851).** `record_new_file(doc, url, *, in_history=False)`: only the two callers the history itself drives pass `in_history=True` (`TransformationService._record_step`, which records the step for that move, and `HistoryService._move_to_step`); `test_dataset_link.py::test_only_the_history_itself_marks_a_move_as_its_own` greps for any other. Every other move (bulk transformations, the data-issue fix routes, a feature column added in place, and whatever comes next) runs `_close_history`: one pipeline update that sets `TransformationConfig.undo_floor` to just past the current step and drops the redo tail, so `can_undo()` / `can_reach(position)` refuse to restore a version from before an edit the history does not list (undo and jump answer 400 saying so). Engine transformations do record steps: `apply_pipeline(user_id, dataset_id, steps)` is the one apply path (`apply_transformation` is a one-step pipeline; `POST /transformations/pipeline/apply`, auto-clean and recipe apply all reach it), all or nothing, each step its own history step and version. A multi-step pipeline is run twice, once dry and once while recording, so it never holds more than two frames; every version and the one new `transformed/` file are written before any step is recorded or the dataset moved, so a failed upload leaves both as they were. An empty pipeline (auto-clean with every option off) writes nothing. Clearing the history resets the floor. A history step must accept whatever the engine executes: `fill_missing` with no column named is valid, since a step that refuses it fails the apply after its file and version are written.
- **The first step of a history can be undone only when the version from before it is known (#962).** Position `-1` is the dataset before any step. `TransformationConfig.base_version_id` is recorded when a history's first step is written (`TransformationService._remember_the_start`), to that step's parent version, and only if the dataset had never moved off its upload (`source_s3_url` unset): then the latest version is the file being transformed. A dataset already moved by an edit no step describes has no version of its current file, so nothing is recorded and its first step is not undoable, as every first step was before. `can_reach(-1)` needs the base and an open history (`undo_floor == 0`); `_close_history` at position `-1` drops every step and forgets the base, because the edited file is where the history now starts. Do not derive "the state before step 0" from `parent_version_id` at undo time. **A new version derives from the version at the history's cursor, not from the latest by number (#852):** `_version_at_cursor` is the step at `current_position` (or `base_version_id` at `-1`), and within one apply each later step derives from the version the step before it just wrote, because the cursor does not move until every version is written. The latest version is the fallback only when the history does not know. Before this, apply, apply, undo, apply recorded the undone version as the new one's parent. A test of lineage needs steps that each change the bytes: identical content is stored as one version, so a step that changes nothing has no version of its own.
- **Changing an existing index's options needs a new index name (#565).** Beanie builds indexes at `init_beanie`; turning `Indexed()` into `Indexed(unique=True)` keeps the name `experiment_id_1`, and Mongo refuses to rebuild an existing name with different options (`IndexOptionsConflict`), so the app would fail to start against any collection that already has the old index. Declare the new one as a named `IndexModel` in `Settings.indexes` (`experiment_id_unique`), leave the legacy index to `scripts/check_ab_test_duplicates.py --drop-legacy-index`, and run that script's duplicate check before the first deploy — a unique index that cannot build also fails startup.
- **A Beanie `Link` field persists as a DBRef, so query it by `$id`, not by the bare id (#543).** `Model.link_field == some_id` (and `{"link_field": ObjectId(...)}`) matches **nothing** — the stored value is `{$ref, $id}`. Query `{"link_field.$id": PydanticObjectId(...)}`, the same key the erasure cascade's `_LINK_KEYED_MODELS` deletes by. This silently broke the `column_stats` cache: the DBRef `dataset_id` never matched, so every GET recomputed and re-inserted a full set, growing the collection without bound while never serving from cache. The fix added a `dataset_column_unique` index (via #565's new-name rule + `scripts/dedupe_column_stats.py`, run before deploy). Two consequences of that unique index, both in `app/api/routes/column_stats.py`: the self-healing recompute must delete legacy null-owner rows **before** the `insert_many` (the index keys on `(dataset_id, column_name)` *without* `user_id`, so a surviving null-owner row for an existing column would `DuplicateKeyError` the owner-stamped insert) yet **after** the S3 download+parse (so a failed download can't wipe good cached rows); and a concurrent cache-miss recompute race means the losing writer's `insert_many` hits the index, so `app/utils/column_stats.py::_store` swallows a duplicate-key-only `BulkWriteError` and the loser serves **the list it computed**, never a re-read (#715): `insert_many` is not atomic across documents, so the winner may have written only some of its rows when the loser collides, and a re-read served that truncated list as 200. Any other bulk failure still raises, and neither route catches the collision itself. **A cached set is a hit only if it is complete (#889):** `_complete` compares the owner's rows with the dataset's own column count (no download), because `insert_many` commits in batches and a reader mid-write, or after a writer that died between batches, used to be served the columns written so far. The healing insert is unordered (`ordered=False`), so the rows already there collide and are skipped and the missing ones go in.
- **A dataset document has several writers at once, by design, and each writes only its own fields (#983).** After every upload a background task waits seconds for the model and then stores `aiSummary`, while the Explore page has `POST /data/process` store `schema`, `statistics`, `quality_report` and `is_processed`. Both used to `save()` the copy they had read before their `await`, so whichever finished last put the other's fields back: an upload followed by Explore left the dataset marked unprocessed (and `/ai/summarize` and export answering 400), or dropped the summary. `generate_dataset_summary`, `generate_ai_summary_safe`, `/data/process` and `/ai/summarize` (#981) now use `document.set({...})`, as the model routes do (#674) and `record_new_file` does (#723). **Never `save()` a `UserData` that was read before an `await`.** `test_dataset_writers_keep_each_others_fields.py` runs each writer for real with another's result landing mid-wait, and fails on a `.save(` in those three modules; a test that patches `UserData.save` cannot see this class at all, which is how it survived. `PUT /user_data/{id}` still saves whole, with no `await` between its read and its write, because it relies on `validate_on_save` (#585).
- **Beanie `save()`** surfaces a unique-index violation as `RevisionIdWasChanged`, not `DuplicateKeyError`.
- **Artifact integrity (#266):** model artifacts are HMAC-SHA256 signed (signature in Mongo, bytes in S3); joblib/pickle loads verify before deserializing and refuse on mismatch.
- **Model export (#468):** `ModelStorageService.load_model(model_id, user_id)` is tenant-scoped and returns a **tuple** `(model, feature_engineer)`; `ModelExportService._load_owned` is the one place that calls it, after `_owned()` has answered 404 for a model the caller does not own (checked *before* the converter-availability check, so a missing converter never changes the answer for someone else's model). Keep the standalone transform bug-for-bug identical to the platform's or container predictions silently diverge; `test_standalone_transform_matches_the_platform` holds them equal for both encodings. **Each encoding is gated on the key it fits (#697):** one-hot on `"encoder"`, label on `"label_encoders"` (it used to sit under `"encoder"`, so every label-encoded AutoML run failed on its own test-set transform). Label values are keyed by `_label_keys` at fit and serving alike (integral floats drop their `.0`, so `1.0` fitted from a NaN-bearing column matches a served `1`). **One-hot is matched on the same key at serving (#906):** `_one_hot` builds the block itself and never calls the fitted encoder's `transform`, which matches by raw value and type. A low-cardinality numeric column is fitted with int categories and a boolean column with blanks with bool ones, while the form sends every categorical as a string, so its own dropdown value was an all-zeros block. It matches on `_match_keys`: the label key, with a missing value kept apart from the text `"nan"` (both can be categories when no imputer was fitted) and, in a column fitted on numbers, numeric text read as the number (`"1.0"`, `"01"`). "Fitted on numbers" is decided from the category values, because the imputer hands fit an object block and `categories_` has dtype `object`. `_categorical_options` offers the label keys, so a new option source must go through `_label_keys` too. A test for a serving path sends what the form sends (strings), not the fitted types. Integer categories beyond int64 share a key through `to_numeric`'s float64; no reader in the platform produces them, so that is accepted. **A JSON null is a blank, and every serving surface says what the model had not seen (#838):** `_prepare` (both engineers) turns `None` into NaN in the categorical columns, because `SimpleImputer` fills NaN only and a null used to skip the fill a blank got at training. `FeatureEngineer.input_warnings(frame)` reads the raw frame and returns one dict per row, `{column: "unseen" | "missing"}`, empty for a clean row; "missing" covers numeric inputs too. It stores nothing on the engineer, which is cached and shared across requests. The session and API-key predict routes get it from `infer_records` (the one transform-and-infer both routes share, in `model_training.py`) and return it as `input_warnings`; batch attaches it in `_predict_chunk`, after either inference path, writes an `input_warnings` CSV column that is always in the header, and counts flagged predictions in the summary as `input_warning_count`, which the batch UI turns into a pointer at that column. The single-prediction form cannot send an unseen or blank value (dropdowns, every field required), so a batch file is where a UI user meets this. Both serving paths get the transformed frame and the report together from `FeatureEngineer.served(frame)`, which prepares the frame once and runs in a worker thread (#909: a 10,000-row batch chunk held the event loop for over 300 ms, the per-row result assembly, `_assemble_rows`, too). A new serving surface calls `served` the same way, and a fake engineer in a test needs it. The export applies the null fix and does not report warnings. A category unseen at fit time is **served like a missing one** — the column's most-frequent training value, what the categorical imputer already fills a blank with — never an out-of-range code: a `-1` made a label-encoded linear model extrapolate past the first category (0.999 confidence, no `low_confidence` flag, where one-hot's all-zeros row gave 0.58 and was flagged). `-1` survives only when no categorical imputer was fitted (`handle_missing=False`). **Per-row identifiers are excluded at fit (#806):** `FeatureEngineer._identifier_columns` drops text columns ≥95% unique over their filled cells, and integer columns that are unique, monotone in the *original* row order (`sort_index()`, because the training split shuffles) **and named like an ID** (`_IDENTIFIER_NAME`): the name gate exists because a file sorted by a real integer feature is unique and monotone too. `feature_config.keep_columns` forces a column back in. The list is persisted as `excluded_features` on the fitted engineer and in the export state dict, and both transforms drop it if supplied; pre-#806 pickles have no attribute, hence the `getattr`/`.get` defaults. It is reported in the training log, `MLModel.training_config["excluded_identifier_columns"]` and the model report. **Date columns leave the features the same way (#840):** read from CSV a date is text, so it was one-hot encoded into a feature per distinct date, and a `datetime64` column (Parquet) was in neither feature list and reached the estimator as it was. `_is_date_column` accepts a `datetime64` column outright, and text only when 95% of a sample is *written* as a full date (`_DATE_SHAPE`) and then parses. Parsing alone is not the test: `dateutil` reads "Jan", "Mon" and "1/2" as dates, and those are categories. `excluded_features` holds identifiers and dates together, since that is what both transforms drop; `excluded_dates` is the subset, and the fit metadata's `excluded_features` key is identifiers only because `train_model_task` persists it as `excluded_identifier_columns`. Dates are reported apart: `training_config["excluded_date_columns"]`, their own line in the training log (`exclusion_notes`) and in the model report. `keep_columns` keeps a date in, encoded as text. A kept `datetime64` column is made text by `_datetimes_as_text` in `_prepare` (both engineers) and at fit, one value at a time (`2025-01-31`, with its time when it has one): the engine transforms its test split from the original frame, so text made per column, which drops the time only when every value is at midnight, keyed the test rows differently from the fit. A date is excluded, not expanded into year, month or weekday: expanding needs a date parser at serving and in the export, and a date field in the form. **A column with no values is the third kind left out (#911):** pandas reads an unused CSV column as `float64`, all NaN, `_identify_feature_types` makes it a categorical (zero distinct values), and `SimpleImputer` drops a column it has no value to learn a fill from. `_handle_missing_values` answered that shape mismatch by dropping every categorical column, so one empty column failed the run with a `KeyError`. Empty columns now go to `excluded_empty` before imputation (`keep_columns` cannot keep one, and an all-blank date is reported as empty), and `_handle_missing_values` has no recovery branch: do not add one, since a column the imputer would drop must be excluded and reported, never worked around. The three kinds are written to `training_config` by `_recorded_exclusions` (`excluded_identifier_columns`, `excluded_date_columns`, `excluded_empty_columns`), so a fourth kind touches that helper, `exclusion_notes`, the report's `DatasetSection` and the page, and not `train_model_task`. **The exported `ModelInference` validates against `input_features`** (the engineer's numeric + categorical inputs), never `model.feature_names`, which are the engineered columns: checking those made both exports refuse every raw row of any categorical model, and a test fixture that set raw names into `feature_names` hid it. The test for this surface must mock `load_model` with the real signature and tuple; the old suite mocked a dict-returning one-argument shape and stayed green while every format 500'd.

- **Plan enforcement (#368):** `app/billing/enforcement.py`. `quota(<metric>)` is a route dependency that **atomically reserves** a unit via `metering.consume()` — one conditional `$inc` (`units <= limit - amount` + `upsert`), where a record already at the cap misses the filter, the upsert collides with the unique index, and that `DuplicateKeyError` **is** the denial. Answers **402** (not 429 — that's #151's) with limit/used/resets_at/upgrade_available. **Enforcement is the only thing that counts these metrics** — a guarded route must NOT also call `metering.record()`. `QuotaRefundMiddleware` returns the reserved units on any >=400, so a malformed upload doesn't burn quota — it refunds the **reserved amount against the reserved period**, since a request that fails across a month rollover would otherwise credit a month it never charged. JSON predict routes use `quota(..., per_record=True)` — a `predictions` limit must count predictions, not requests, or batching becomes the way around it. **A batch retry charges like a creation (#460)** — it re-reads the same S3 input from the start (there is no resume), so it re-executes the *full* `progress.total_records`, which is the field to size the reservation from (set at creation, deliberately not reset by `retry_job`; note it is the service's pandas count, which can differ by one from the route's `_count_csv_rows` on a trailing blank line). `retry_job` **claims** the job with one conditional `find_one_and_update` carrying every precondition — status and a `$expr` retry-budget check — because read-check-write let a double-click spawn two processing tasks over one document. The route's own 404/409 checks exist for the *message*, not the mutual exclusion. Batch jobs count their CSV rows (stdlib `csv`, so a quoted newline isn't a row) and reserve them **before creating the job** — creation `auto_start`s processing, so a check afterwards would have to unwind a running job, and an unconditional true-up isn't a limit at all (`MAX_BATCH_PREDICT_RECORDS` is 1000x the FREE ceiling). That count **fails closed (#486)**: `_count_csv_rows` used to `return 0` on any error, and `csv` raises `_csv.Error` on a field over its 131072-byte default, so one oversized field reserved 0 and ran the whole batch unmetered — it now raises `CsvCountError` (a bounded `MAX_CSV_FIELD_BYTES`, 1 MiB, enforced via `csv.field_size_limit`, never raised to a huge value which would just trade the bypass for memory exhaustion) and the route answers **400**. Never revert it to a lenient `return 0`. Reservations on one request **accumulate** rather than replace: a batch reserves twice, and overwriting silently burns the first on every failed job. Enforcement fails **closed** (a storage error denies); `record()` fails open. Any test hitting a metered route needs `setup_database` — the dependency reads `Subscription`, and class-level Beanie field access raises `AttributeError` without an initialised Beanie. **A global daily AI ceiling sits under every tenant quota (#768):** `app/billing/ai_ceiling.py` counts model calls across all tenants per UTC day (`AI_CALLS_DAILY_CEILING`, `_env_positive_int`, default 500 = ADR-003's $60/day worst case) as a `UsageRecord` under the sentinel tenant `__global__` with a `YYYY-MM-DD` period key, via `metering.consume(..., period_key=)`. It is enforced in `with_circuit_breaker` for every breaker named `openai*`, once per logical call **outside** the tenacity retry; past it the breaker raises `AICeilingReached` (a `CircuitBreakerOpen`), so every service takes its rule-based fallback and every route releases the unit — `/ai/chat`, which has no fallback, answers a refunded 503. It counts the unmetered post-upload summaries too. Alert: one ERROR log per day per worker + `ai_ceiling_denials_total`. **Every `chat.completions.create` must live inside an `openai*` breaker** — `tests/test_billing/test_ai_ceiling.py::TestEveryModelCallIsBehindTheCeiling` walks `app/` and fails otherwise. A route that keys its release on "did a model run" must set that flag only after the call returns (the feature `/suggest` `ai_used` bug). **A feature-suggestion lookup never generates (#728):** explain, apply, apply-multiple and feedback read `get_cached_suggestions` only and carry no quota. Suggestion ids are minted per generation, so a regenerated set cannot hold the id asked for; an expired set is not found. Only `/suggest` and `/suggest-more` call `suggest_features`, and both release when `ai_used` is false. **Model calls are metered too (#461):** `ai_calls` is the fourth metric, and it is the one ceiling that is **finite on every tier, ENTERPRISE included** — it is the backstop against an unbounded OpenAI invoice, so `plans.py` reads it through `_env_positive_int` and a `-1` override falls back and warns rather than uncapping it. - **Entitlement (#366, #458, #510):** `Subscription.is_entitled` is the single predicate; `effective_tier` is what callers read (`plan_tier` alone keeps serving PRO to a lapsed row). It requires **both** an entitled status **and** an unlapsed period. `PAST_DUE` is entitled on purpose — Stripe is still retrying — but `unpaid` is **not**: that is the status a subscription reaches once Stripe has *given up*, and mapping the two together handed permanent paid access to a customer whose payments had permanently failed. Never re-merge them. The period check exists because status is only as fresh as the last webhook and nothing reconciles on a schedule, so without it one dropped event grants a tier forever; the grace is **per status** and the two must not collapse into one: `ENTITLEMENT_GRACE` (3 days) absorbs delivery lag on an ACTIVE row whose renewal already happened, while `DUNNING_GRACE` (30 days) covers PAST_DUE, because Stripe's Smart Retries run out to ~4 weeks and a single 3-day window would cut off on day three a customer whose card succeeds on day eight — silently rescinding the serve-through-dunning policy stated right above it. A **missing** `current_period_end` falls back to `updated_at` + the same grace — bounded, never "entitled forever", which is the same bug wearing a different field. Both values come back from Mongo naive, so both go through `as_utc`. `current_period_end` itself lives on the subscription **item** in the pinned API version (`STRIPE_API_VERSION` in `stripe_client.py`, guarded by `tests/test_billing/test_stripe_api_version.py` against the SDK's own constant — *not* `stripe.api_version`, which `_client()` overwrites, making that assertion pin==pin); `_period_end()` reads the legacy top-level location first and the item second, and must never clear a known value on an event that omits it. `scripts/reconcile_subscriptions.py` is the repair path for the other direction (a missed **renewal**, which no local rule can fix) and the backfill for pre-#510 rows; it reconciles **tier as well as status** — an upgrade changes only the price, so a status-and-period comparison reports "everything matches" while an ENTERPRISE customer is enforced as PRO — and its write is conditional on `updated_at` so a webhook landing mid-run is not overwritten. **The webhook itself persists via a single conditional upsert, not a read-modify-write (#509):** `Subscription` has no Beanie revision, so two concurrent events would both read the old row and the later `save()` would silently drop the earlier — a `subscription.updated` racing a `subscription.deleted` could leave a cancelled tenant entitled. `_apply` now does one `update_one` whose filter requires `last_event_at <= event.created` (or unset); a strictly-older event matches nothing, the upsert's insert hits the unique `user_id` index, and the stale event is dropped. A *first* `DuplicateKeyError` means a concurrent event just created the row (the new-tenant `checkout.completed`+`subscription.created` burst) — retry once, where the same filter decides apply-or-reject. Only event-present fields are `$set`, and a duplicate delivery converges on the same row (idempotent in effect). **The checkout event alone entitles the customer (#598):** a checkout session carries no price, so a settled `checkout.session.completed` reads the subscription from Stripe (`stripe_client.retrieve_subscription`) for the tier, price and period end, and answers 503 for Stripe to retry when that read fails. The tier used to come only from `customer.subscription.created/updated`, the endpoint was subscribed to three events without `created`, and the first staging checkout paid and stayed FREE. Each event has its own handler in `_HANDLERS`; `.env.staging.example` names every `HANDLED_EVENTS` entry for the operator to subscribe, and `test_staging_example_lists_every_webhook_event` holds them equal. **Every Stripe call is bounded:** `stripe_client._client()` sets a 10-second timeout and one retry (`REQUEST_TIMEOUT_SECONDS`, `MAX_NETWORK_RETRIES`), because the SDK's own defaults are 80 seconds and two retries, and that lookup runs while Stripe is waiting for the webhook's answer.

- **`train_model_task` and `AutoMLEngine.run` are orchestrators (#842).** Where another note here says something happens "in `train_model_task`", it is in one of its steps in `model_training.py`: `_build_engine` (the request and the mode's defaults), `_JobReporter` (the task's `on_progress` / `on_event` / cancellation check, all partial writes), `_run_training` (the slot, both in-flight checks, the load) with `_fit_within` (the wall-clock `wait_for`), `_store_trained_model`, and `_record_completion` / `_record_failed` / `_record_cancelled`, one per ending. FREE's ceilings must stay >= the `comprehensive` mode preset (`tests/test_billing/test_training_ceilings.py` guards it) or that mode silently disappears for free users.
- **Training concurrency + parallelism are bounded on the shared VPS (#498):** `app/services/training_admission.py` mirrors the batch mechanism (#515). `enforce_training_per_user_cap` refuses the N+1th PENDING/RUNNING training per tenant with `TrainingConcurrencyLimitError` → **429** (checked in the route before insert, after the `quota("training_runs")` reservation, so the refund middleware returns the unit); a per-loop `Semaphore(MAX_CONCURRENT_TRAINING_JOBS)` gates `engine.run` in `train_model_task` (the wall-clock `wait_for` sits *inside* it, so queue time isn't charged), and a job cancelled while queued is skipped on acquire. **The dataset is loaded inside the semaphore too, and parsed off the loop (#665):** `_load_training_frame` downloads and then runs `_parse_dataset` in `asyncio.to_thread`, after the slot is taken, so a queued job holds no frame in memory and a large parse does not stall other requests (pandas still holds the GIL for parts of a parse, so the loop hitches for a fraction of it rather than all of it). The engine's `TimeoutError` → wall-clock mapping wraps `engine.run` only; the download's own socket timeout must keep its own message. Its progress line goes through the task's `on_event`, a partial write, because a full `save()` there could overwrite a cancellation that arrived during the download. `bounded_n_jobs` clamps estimator parallelism to `TRAINING_MAX_N_JOBS` (default 2, ≤ host cpu) — never re-introduce a raw `n_jobs=-1` in `automl_engine`/`feature_selection_service`/`hyperparameter_tuner`; the engine threads it as `self.n_jobs`, the tuner clamps `TuningConfig.n_jobs` at point of use. All three caps read through `_env_positive_int` (a 0/negative override can't disable them). **Known residual:** a wall-clock timeout releases the semaphore slot while the sklearn `fit` in its `to_thread` worker keeps using a core until it finishes (unkillable), so the cap can be briefly exceeded during an overrun — size `MAX_CONCURRENT_TRAINING_JOBS` with margin.
- **PII risk: a column name is a hint, values are evidence (#608).** `PIIDetector` runs both the name check and the value-pattern check on every column and keeps the stronger signal; `NAME_MATCH_CONFIDENCE` equals `HIGH_RISK_CONFIDENCE` (0.8) and the report needs *strictly greater*, so a label alone is medium and only matching values make a column high — the level that sends `/upload/secure` to the confirmation gate. Before #608 the name check `continue`d past the values, so `ssn` full of SSNs was medium while `ref_code` with the same values was high, and the honestly-named file skipped the gate. Change those constants knowing that raising a population from medium to high routes it through `/confirm-pii-upload`.
- **The AI summary is built from a PII-masked frame, never the stored schema, on the secure paths (#490).** `generate_ai_summary_safe(user_data_id, df)` in `secure_upload.py` summarizes the frame it is handed via `prepare_dataset_summary_from_df` + `call_openai_api` — it must NOT delegate to `generate_dataset_summary(user_data_id)` (which reads the stored `data_schema`), because the chunked `complete` path stores a **raw** schema and would ship raw PII `example_values` to OpenAI. All three secure paths pass `_summary_frame(df, pii_detections)`, which masks whenever any PII is detected — `mask_pii=false` is a *storage* choice, not consent to send PII to a third-party sub-processor. The original bug: the wrapper passed the DataFrame where `generate_dataset_summary` expected a `str` id, so every call raised inside `UserData.get(df)` and was swallowed, leaving the summary permanently null for PII-confirmed and chunked uploads; the wrapper now logs at WARNING (with the dataset id) on a null/failed result rather than swallowing. **`/upload/secure` was the third path and was fixed to match (#679):** it branches on `pii_report["has_pii"]` — a flagged dataset (medium risk here; high risk returns early to `/confirm-pii-upload`) goes through `generate_ai_summary_safe` + `_summary_frame`, only a clean one keeps the stored-schema `generate_dataset_summary`. **`_summary_frame` redacts EVERY flagged column, and redacts rather than masks (#679, #718):** every column that produced a detection, whatever its confidence, because a weak value-pattern match (confidence in `(PATTERN_MATCH_FLOOR 0.1, 0.5]`) sets `has_pii` but leaves `risk_level="low"`. Each distinct value becomes a numbered token (`[redacted 1]`), missing values stay missing, so the summary's counts for the column remain true and nothing of a value leaves. `PIIDetector.mask_pii` is the **storage** mask (medium risk and above, at `/confirm-pii-upload`) and keeps part of each value on purpose so the stored copy stays readable: a name's first and last character and its length, the last four digits of an SSN or card, an email's domain. Never route anything bound for a third party through it.
- **Funnel telemetry is server-written `ProductEvent` rows (#769).** `app/services/product_events.py::record(user_id, event, once=…)` never raises (telemetry must not fail an upload, a training run or a webhook), and `once` is a per-user dedupe key behind a unique partial index — used for `first_*` events and for Stripe's at-least-once redelivery (`checkout:<session id>`, `cancel:<subscription id>`). Hooks: `account_created` is written by NextAuth `events.createUser` **straight into `product_events` through the adapter's Mongo client** (`apps/frontend/lib/product-events.ts` — the document shape is a cross-language contract with `app/models/product_event.py`); `first_upload` is a `UserData` before/after `Insert`+`Save` hook that records only a **creation** (`save()` on a new doc is an upsert that fires no Insert event — `/datasets/upload` creates that way — and the before-hook's `id is None` check keeps every later save free); `first_model_trained` in `train_model_task`; `quota_denied {metric, tier}` in `enforcement.reserve` and `enforce_storage_ceiling` (plus the `quota_denials_total` counter); `checkout_started` only after Stripe returns a session; `checkout_completed` only when `settled`. Retention is a 13-month TTL, the rows are swept by `_sweep_user_scoped`, and the privacy policy's "What we collect"/"Retention" name them — a new event type needs the same disclosure. `GET /api/v1/admin/funnel` is the readout (activation is judged on the same-length window ending 7 days ago, so a short window is not structurally empty); `/admin` renders it as numbers. `app/api/routes/admin.py` guards at the **router** level on purpose — the per-handler rule above exists so a forgotten dependency can't make a route public, and for an admin-only router the router-level `require_admin` is the stronger form of the same guarantee.
- **FREE has a storage ceiling (#768):** `PlanLimits.storage_bytes` (FREE 500 MB via `PLAN_FREE_STORAGE_BYTES`, UNLIMITED on paid tiers; outside `METERED_METRICS` like `api_key_rate_limit`). `app/billing/storage.py::enforce_storage_ceiling(user, incoming_bytes)` runs **before the S3 put** in every `_MUST_BE_METERED` dataset route (the registry in `test_dataset_routes_are_metered.py` checks the source), plus chunked `init` on the declared size; it sums `UserData.file_size` (set by every writer, None on pre-#768 rows = 0 until `scripts/backfill_dataset_file_sizes.py` has run), `DatasetVersion.file_size` and `MLModel.model_size` (#781), and refuses with a 402 in the `quota_exceeded` shape as `storage_mb` (MB values, `resets_at: null`) so the one plan-limit dialog renders it. A new dataset writer must set `file_size` and call the check. **`file_size` is the size of the file the dataset is on now (#781):** `record_new_file` asks S3 for the new object's size (`utils.s3.object_size`, one HEAD, never raising) and writes it to both twins with the move, so transformations, undo, redo and fixes keep it true without each writer knowing; when the size cannot be read the recorded one stays. The sum counts each stored object once (`storage._dataset_and_version_bytes`: after an undo the dataset's current file is a version's own object). Not counted: the `superseded_s3_urls` copies, whose sizes are not recorded, so the figure is a floor.
- **Metering the upload surface (#459):** `quota("uploads")` belongs on **every** route that creates a dataset, and there are more of them than the name "upload" suggests — `/upload/secure`, `/upload/confirm-pii-upload`, `/upload/chunked/{id}/complete`, `/upload/`, `/datasets/upload`, and `onboarding/sample-datasets/{id}/load` (store.py's bare `POST /api/v1/`, which could never succeed, was removed in #472) (a sample load inserts a full `UserData` unconditionally, so unmetered it mints datasets without limit). `datasets/{id}/features/{fid}/apply` reserves **inside the handler**, only when `create_new_dataset` is true — a route dependency would bill every in-place apply. `tests/test_billing/test_dataset_routes_are_metered.py` is a **registry**, not a list of per-route tests: it walks the live route table and fails on any unclassified POST under its prefixes, which is the only thing that catches a new route. It has two scopes: POSTs under the prefixes in `_IN_SCOPE_PREFIXES`, and since #609 **any write route on any prefix whose handler can reach the construction of a `UserData` or `DatasetMetadata`** (an AST pass over `app/` following calls by simple name; a route mounted outside the prefixes is how the onboarding loader was missed). The failure prints the chain of calls; most routes it flags only reach `ensure_metadata_twin` and go in `_EXEMPT_BY_REACH` with that reason. Matching is by name, so two functions that share a name share a verdict, and a construction behind `getattr` is invisible. Note also that `app.routes` is **not flat** on FastAPI 0.139 — routers are lazy `_IncludedRouter` wrappers, so the naive `isinstance(r, APIRoute)` walk finds almost nothing and cheerfully reports that everything is metered. A 2xx that does no work must hand its unit back with `enforcement.release(request)` — the refund middleware only sees >= 400, and `/upload/secure`'s high-PII branch answers 200 having created nothing, which was charging a unit there *and* again at `/confirm-pii-upload`.
- **Batch prediction concurrency is bounded (#515):** `batch_prediction.py` no longer spawns unbounded `asyncio` tasks. A per-process `asyncio.Semaphore(MAX_CONCURRENT_BATCH_JOBS)` (default 2, resolved per running loop so the test suite's many loops don't share one) gates the auto-started path — excess jobs queue rather than all executing; `auto_start=False` (tests) bypasses it. `create_batch_prediction_job` refuses a caller already at `MAX_CONCURRENT_BATCH_JOBS_PER_USER` (default 3) PENDING/RUNNING jobs with `BatchConcurrencyLimitError` → **429**, checked **before** the S3 upload so a refusal leaves no orphan object and the reserved `predictions` units are refunded by the middleware. Result streaming was already O(chunk_size) (`_read_data_chunks` + a temp-file result stream); this closes the task-spawn half. A job cancelled while still queued is skipped when it acquires the semaphore (cancelling a job already running is #485). **The per-tenant cap is held by the database, and exact for every job that holds a slot (#653):** the count in `_enforce_per_user_cap` is only the early refusal before the upload, since a burst passes a count together. A job is written by `_admit`, which gives it an `admission_slot` in `0..cap-1`; the unique partial index `user_live_slot_unique` on `(user_id, job_type, admission_slot)` covers only PENDING/RUNNING rows, so two live jobs of a tenant cannot share a slot and a create that finds every slot taken is refused (its just-uploaded input is deleted). Nothing releases a slot: any write that moves the job to a terminal status (finish, cancel, the reaper) takes it out of the index. That is why it is a slot index and not a counter, which would need a decrement on every one of those paths. `retry_job` claims a free slot the same way, not the one the failed job once held. Only a duplicate key on that index means "at the cap" (`_is_slot_collision`); any other failure to write the row is raised. Either way the create is undone by `_discard_unadmitted`: a PENDING row that landed although the insert reported failure is deleted (nothing spawned it, and the route's error already refunds it, so the reaper would refund it again, #904), and the input is deleted only once no row is left. A live row with no int slot is outside the index (a job created before #653, or one holding a slot above a cap that was later lowered), so such rows can sit beside a full set of slots until they end. The index's partial filter uses `$in`, which needs MongoDB 6.0 or later, and its `$type: "int"` matches a 32-bit int only, so a slot must never be stored as a long. **A run is bounded by `BATCH_JOB_WALL_CLOCK_SECONDS` (default 3600, #653):** a run holds an execution slot and nothing inside it is time-bounded, so one hung job used to queue every tenant behind it. `_process_batch_job` waits on the run with `asyncio.wait`, not `wait_for`, because the run fires the completion webhook from its own `finally` and the job must read FAILED before the run is cancelled. `_fail_at_wall_clock` writes FAILED only if the job is still RUNNING and refunds the records it never reached; like training, work already inside a worker thread finishes on its own. **A run's unprocessed remainder is refunded once, by whichever path gets there (#653):** `_refund_remainder` first sets `BatchJob.remainder_refunded` with a conditional update and refunds only if it was the one to set it. It sets the marker even when nothing is owed, so a run is settled by the first caller whatever remainder a later one computes. Three paths call it: the run when it notices a cancel between chunks, the queue when it skips a job cancelled before it started (that path used to return without a refund), and the wall clock for a job cancelled while too stuck to notice. A job the wall clock fails gets the marker in the same write as FAILED and is refunded directly, because a retry landing between two writes would have its fresh marker consumed (#904). A retry clears the marker with its new reservation. The stale-job reaper refunds the whole reservation itself and sets the marker in the same write that fails the job, because a job reaped while it was only queued is still picked up when its slot frees, fails its claim, and would be refunded again. A new path that refunds a run must claim or set the marker. **A queued job's heartbeat is pumped while it waits (#653):** `_process_batch_job_admitted` holds `heartbeat_pump` around the semaphore wait as well as the run, so a job whose task is alive is never stale. Before, a job queued past the stale timeout was reaped and refunded while its task was still going to run it, and a retry in between could have the job executed twice or the retry refunded in full. **The create route writes `input_size_bytes` with a one-field `set`, never `job.save()`:** processing is spawned before the route gets the job back, and a full save of that copy wrote PENDING over the run's RUNNING.
- **Stale in-flight jobs are reaped, not left RUNNING forever (#484):** training/batch jobs run in-process, so a restart/deploy/crash used to leave them RUNNING permanently — holding quota and (since #498/#515) a concurrency slot. Both models carry `last_heartbeat` (set at creation, bumped on every progress write — and for training's *partial* `$set` writes it must be included explicitly, plus `app/utils/heartbeat.py`'s background pump keeps it fresh through a slow candidate/chunk). `app/services/job_reaper.py::reap_stale_jobs` marks in-flight jobs whose heartbeat is older than `STALE_JOB_TIMEOUT_SECONDS` (default 1800) FAILED and refunds their reserved quota against the **reserved** period (`period_key_for(created_at)`): training 1 `training_runs`, batch `total_records` `predictions`. It runs on startup and every `JOB_REAPER_INTERVAL_SECONDS` from the lifespan. **Two things make it safe under the 2 gunicorn workers:** staleness is heartbeat-based (never "reap all on startup"), so a live job with a recent heartbeat is never touched; and each reap is an atomic `find_one_and_update` claim, so concurrent reapers claim disjoint jobs and refund exactly once. `retry_job` must refresh `last_heartbeat` or the retry inherits the failed run's stale value and is reaped before it starts. **A training job waiting for a slot is in flight too (#901):** `train_model_task` takes its slot through `_training_slot`, which runs the heartbeat pump over the wait; before that nothing bumped the heartbeat while a job queued, so one that waited past the timeout was failed and refunded, and then trained anyway when a slot freed. On taking the slot `_require_in_flight` re-reads the job and raises `TrainingNoLongerInFlight` for one already in a terminal state or whose row is gone (erased with its dataset or account), whose handler writes nothing: the reaper's FAILED and its refund stand. The "Waiting for an available training slot" line is a partial `$push` (`_log_waiting_for_slot`), like every other write in the task; as a full save it put `cancellation_requested` back. Known limitation: a batch retried across a month boundary then reaped under-refunds the retry period (the `units>=amount` clamp prevents minting).
- **A training task records nothing for a job someone else ended or removed (#901, #936).** `train_model_task` holds its `TrainingJob` in memory for the whole run, and a Beanie `save()` of a document that is no longer in the collection **inserts it**. So an erasure of the dataset or account during a run was undone by the task's last write, which on success also stored a model for the erased data. Two rules: `_require_in_flight` runs on taking a slot **and again when the fit returns** (a job erased, reaped or cancelled in that time builds and stores nothing, and the reaper's FAILED-and-refunded verdict stands), and `_refreshed_job`, which every terminal path calls before its save, raises `TrainingNoLongerInFlight` for a missing row after `_discard_model` removes any model already stored. The write itself is `_record` (a Beanie `replace()`, which raises `DocumentNotFound` for a missing row where `save()` would insert it), because the re-read and the write are two round trips and an erasure can land between them. Any whole-document write of the job from the task goes through `_refreshed_job` and `_record`, never a bare `save()`. Erasure does not wait for the task: a fit in a worker thread cannot be killed, so it runs to its end and is then dropped.
- **Batch cancel actually stops the run (#485):** cancelling used to write CANCELLED and be silently overwritten by the running task's own terminal `save()` (a lost write). Now **every** status-touching write in the batch task is conditional/status-guarded so a concurrent cancel is never clobbered: `_claim_running` (the opening PENDING/RUNNING→RUNNING claim — do NOT revert it to a plain `mark_started(); save()`, that reintroduces the bug just before the first chunk), the per-chunk `_persist_progress` (partial, guarded on RUNNING), and `_finalize_if_running` (terminal write only if still RUNNING). `cancel_job` is an atomic conditional transition. The loop re-checks cancellation between chunks (and once more before the S3 upload) and, on cancel, discards the partial output (never uploaded), refunds the unprocessed remainder via `_refund_remainder` (`total_records - processed` against `period_key_for(created_at)`), and sets the terminal status in memory so the completion webhook reports CANCELLED. A cancelled job is terminal, so #484's reaper never also refunds it. Batch S3 keys are **`batch-jobs/{user_id}/{model_id}/{job_id}/{input.csv|results.ext}`** (#487) — keyed by the unique server-generated `job_id`, generated up front in `create_batch_prediction_job` and threaded into `_prepare_input_data`, not by a second-granularity timestamp (which collided for two same-second jobs, overwriting one input and leaking another tenant's results). A retry reuses the same `job_id`, so it deterministically overwrites its own output. **The bulk transformation job follows the same rule (#925):** `_claim_running` (PENDING to RUNNING, conditional), `_write_if_running(job, *fields)` for every later write (a partial `$set` guarded on RUNNING: progress, `_fail`, completion), a re-check before the dataset moves, and a conditional `cancel_job`. A whole-document `job.save()` in that job wrote RUNNING over a cancel that landed before the task started. Accepted residual, as for batch: a cancel landing after the pre-move re-check still lets the dataset move, and the job ends CANCELLED with its result unrecorded (logged at WARNING).
- **The prediction log is durable and shared, not in-memory (#488):** `prediction_monitoring.PredictionLog` persists to the `PredictionEvent` Mongo collection, not a process-local dict — with 2 gunicorn workers the old dict showed each dashboard only its worker's half of traffic and reset on every deploy. Same interface (`log_prediction` / `get_recent_predictions`); readers/drift are unchanged. Retention is a **TTL index** (`PREDICTION_EVENT_TTL_SECONDS`, 30d) — never re-introduce the old per-model 10000 quadratic trim or keep input rows forever. `get_recent_predictions` sorts `-_id`, caps, reverses to chronological (for the drift older/recent split) and returns UTC-aware timestamps. The serving hot path logs a whole batch with one `insert_many` (`log_predictions`), never one insert per record. `PredictionEvent` stores request `input_data`, so it is **erased with its model** (`erasure_service` deletes it by `model_id` wherever a model is deleted) — a new PII-carrying collection must always be wired into the erasure cascade.
- **Rate limiting (#151, #455, #483):** global `RateLimitMiddleware` on all `/api/v1`; per-key buckets only on `/production/v1/models`. Anonymous requests are keyed on the socket peer, or on **`X-Real-IP`** when `RATE_LIMIT_TRUST_PROXY` is set — nginx sets that header from `$remote_addr` and *overwrites* it, so behind the proxy it is authoritative (one hop only: a CDN or LB in front of nginx would make `$remote_addr` the LB, which needs nginx's `real_ip` module — no such layer exists today). **`X-Forwarded-For` is never read**: nginx *appends* to it, so element `[0]` is whatever the client sent, and reading it under either flag setting let a caller mint a bucket per request. The flag only helps if compose passes it (`docker-compose.staging.yml` does; before #483 it did not, so staging bucketed every anonymous request under nginx's container IP) and every backend `location` sets the header — `tests/test_security/test_nginx_real_ip.py` pins both. **Disabled in the test env** — a test that means to exercise the limiter must build the middleware with `enabled=True`, or its 429 assertions are vacuous. Both stores read `limit <= 0` as **no enforcement**, so a per-key `rate_limit` of 0 does not throttle, it *removes* the only control on the paid serving surface. Hence three guards, all needed: `CreateAPIKeyRequest.rate_limit` is `ge=1`; `app/billing/api_keys.py` clamps it to `api_key_rate_limit_ceiling(tier)` at creation **and** `reconcile_user_api_keys` runs from the Stripe webhook's `_apply` on every subscription save (the limiter never reads a subscription on the hot path, so nothing else would revisit a key minted under a richer tier); and the middleware floors the stored value at 1 for rows written before that. **`reconcile_user_api_keys` moves the effective `rate_limit` BOTH directions to `min(requested_rate_limit, ceiling)` (#588), not only down (#455's original was lower-only).** Creation records the tenant's asked-for value in `APIKey.requested_rate_limit`; a transient non-entitled status (an `async_payment_failed` makes `effective_tier` FREE) clamps the effective value down, and when the subscription returns to entitled the reconcile raises it **back** toward the request — otherwise a paying tenant's 10k/hr key stayed at 1k/hr forever. The pivot is the recorded request: a key *we* clamped rises again; a key the tenant *set low on purpose* has `requested_rate_limit` == that low value, so `min` leaves it there; nothing ever exceeds the request or the tier ceiling. The pipeline update uses `$ifNull(requested_rate_limit, rate_limit)` so pre-#588 rows fall back to their current value — only ever lowered, never surprise-raised (`fix_api_key_rate_limits.py` / a new key is their path). Every tier's ceiling in `plans.py` must stay **finite** — and note the trap: `UNLIMITED` (-1) is that module's documented "no ceiling" sentinel for *every other* limit, but for a rate limit it means the opposite, so `PLAN_*_API_KEY_RATE_LIMIT` reads through `_env_positive_int`, which refuses a non-positive override, warns, and falls back to the default rather than bricking the tier at 1/window. `api_key_rate_limit` is deliberately **not** in `METERED_METRICS`: it is a throughput ceiling, not a per-period counter, and `limit_for` rejects it. `scripts/fix_api_key_rate_limits.py` audits/repairs existing rows.
- **Redis cache surface (#452):** the whole user-facing cache API is `DELETE /api/v1/cache/me`, scoped by the token. **Never build a Redis pattern from caller input**, and never leave one unanchored: rate-limit buckets (`ratelimit:<identity>`) share this Redis, so a `*:{user_id}*` glob purges the caller's own limiter — which is how a cache route became a limiter bypass. A user-scoped key family must be declared in `_USER_SCOPED_KEYS` (exact) or `_USER_SCOPED_PATTERNS` (anchored to a literal namespace prefix, id glob-escaped) in `app/services/redis_cache.py`, or `/me` silently stops purging it. `delete_pattern` stays available for **server-built** patterns (`viz:{dataset_id}:*`, `stats_{dataset_id}_*`). **`delete_pattern` sweeps with `SCAN`, never `KEYS` (#570):** `KEYS` scans the whole keyspace in one blocking call and stalls the shared instance (the rate-limit buckets live here too), so it iterates `SCAN` (`COUNT 500`) and deletes in batches, deduplicated across cursor pages (`SCAN` can return a key twice). `MATCH` uses the same glob grammar as `KEYS`, so the escaped patterns and the return count are unchanged. The `FakeRedis` test double carries the anchored-glob guard on `scan()` (the path `delete_pattern` now takes), not just `keys()`.
- **Version ownership (#446–#448, #453):** everything under `/api/v1/versions` and `/api/v1/datasets/{id}/versions` authorizes on **`DatasetVersion.user_id`** (server-set, indexed) via the `require_owned_dataset` / `require_owned_version` helpers in `app/api/routes/versions.py`. Call them **outside** the handler's `try` — the module's broad `except Exception` blocks turn a 404 into a 500, and `compare_versions` has no `except HTTPException: raise` at all. Unknown and foreign ids must answer identically, and the ownership check runs **before** any other guard, or the guard's own 400 (`Cannot delete base version`) becomes an existence oracle. `versioning_service.get_version(user_id=...)` compares against the same `DatasetVersion.user_id` since #453 (it used to join to `DatasetMetadata` and read `if dataset and ...`, so a version whose dataset row was gone **passed**); `create_transformation_version` resolves its parent through it (#559), so a parent the caller does not own is refused inside the service — a caller that skipped its own guard is no longer a hole. Scoping the entry point is not enough for lineage — `get_lineage_chain` and `compare_versions` walk `parent_version_id`, so they take a `user_id` and stop at the first hop the caller does not own, or another tenant's lineage reaches `lineage_chain`/`lineage_path`/`transformation_count`. **Deleting a version deletes its S3 object too, S3-first, and keeps the row if S3 fails (#561):** `VersioningService.delete_version` removes the object before the Mongo doc and, on failure, raises `VersionArtifactDeletionError` (route → retryable **502**) keeping the row — the only record of the key — so the object stays findable, the same choice #521 made for model artifacts (never the swallow-and-orphan the retention path `cleanup_old_versions` uses). The key is resolved through `parse_s3_url` for any URL shape, and a URL naming a **different** bucket than the configured one is refused (row kept), the #616 guard — deleting that key from our bucket would no-op and orphan the real object, or hit a same-named one. The `DELETE /versions/{id}` route previously dropped only the doc, orphaning the object and destroying its only key-record in the same request.

## Git hooks
- **`./scripts/install-git-hooks.sh` runs automatically at session start** (a `SessionStart` hook in `.claude/settings.json`) and is idempotent; run it by hand in a clone that Claude Code has not opened. It symlinks the tracked
  `.githooks/pre-push`, which refuses a push that updates the default branch — `main`
  requires `CI Success` but `enforce_admins` is false, so a direct push succeeds with
  only a `remote: Bypassed rule violations` line that scrolls past (#604, three times).
  git hands that hook the refs it is about to update on stdin, so it is exact and fires

- `.claude/hooks/no-push-to-main.sh` (wired in `.claude/settings.json`) is the early-
  feedback layer for agent sessions: it refuses before the command runs and explains

Before #594 the file was pasted on by hand and the live copy drifted for two months (#456), so **an edge fix that only edits the repo file still ships nothing until a deploy runs** — and history predates the mechanism, so diff the box (`--check`) before believing an old edge fix is live. The one path that must never be lost in that copy is the Stripe webhook: the backend mounts `POST /webhooks/stripe/webhook` **outside** `/api/v1` (so the limiter can't 429 Stripe's small IP pool, #367), so a `location /api/` block does not cover it and it falls through to Next.js — which *307s Stripe to the sign-in page*, silently, while checkout keeps succeeding and entitlement never follows. Its `location` block carries its own `client_max_body_size`: the route is unauthenticated and `await request.body()` runs before signature verification, and `BodySizeLimitMiddleware` only inspects a **declared** `Content-Length`, so a chunked body bypasses it entirely and only the edge cap binds. `tests/test_security/test_nginx_webhook_route.py` parses the real config against the real mount so the two cannot drift. The same fall-through hits Next.js's own route handlers from the other side: `location /api/` sends every `/api` path to the backend, so each `app/api/**` handler needs a frontend location (NextAuth's `/api/auth/` block, plus the `^/api/(chat$|data/)` regex). `test_nginx_next_api_routes.py` resolves nginx's real precedence for every `route.ts` and fails on a new handler with no edge route (#789); `/api/health` is the one deliberate exemption, because the edge sends it to the backend.
- **Only production is indexable, and the edge decides (#830).** `nginx-staging.conf`'s `map $host $narrative_robots_tag` defaults every host to `noindex, nofollow` and names the production host as the one exception (an empty value makes nginx omit the header). It is keyed on the hostname because production renders this same template (#832): a hard-coded header would ship there, and an env switch could be forgotten on staging. Both server blocks send it, and it is never set outside a `server` block, since the file is included into an `http` context shared with the box's other sites. **No `location` or `if` may declare its own `add_header`:** nginx then drops every inherited header at that level, which is how static assets were served without HSTS. Cache lifetimes are Next.js's to set; the edge adds none. `test_nginx_noindex.py` pins all of it. Certificates are issued with `certbot certonly` (the installer would edit the rendered file) and must exist before `NGINX_SERVER_NAME` names the host, or `nginx -t` fails and the apply rolls back (deployment guide, Step 7).
- Guides: `apps/backend/docs/TEST_INFRASTRUCTURE.md`, `apps/backend/docs/TDD_GUIDE.md`.

## Environment Variables
- Frontend: `.env.local` | Backend: `.env`
- **`NEXT_PUBLIC_API_URL` includes the version prefix** — `http://localhost:8000/api/v1`, matching `.env.local`, the Dockerfile dummy and `ci.yml`. Append only the resource path (`${API_BASE_URL}/datasets/...`); never re-add `/api` or `/api/v1`, and never "normalize" with `.replace(/\/api$/, '')` — that strip matches nothing and hides the mistake. Getting this wrong 404s silently: it broke the AI Insights panel and chunked-upload resume for as long as they existed, and the suites missed it because they built the expected URL with the same expression as the code (#406). `__tests__/lib/apiUrlConstruction.test.ts` pins the paths against the real FastAPI route table. **The other way to get it wrong is no base at all (#470):** the onboarding page and `SampleDatasetSelector` called `fetch('/api/v1/onboarding/…')` — relative to the *frontend* origin, so a 404 with no auth header, on the screen every first-time user is redirected into — and the e2e mocks matched on `url.includes()` so they never noticed. All onboarding calls go through `lib/services/onboarding.ts` now, and the same test file bans bare relative `/api/v1` literals in `app/`, `components/` and `lib/` (Next.js route handlers under `app/api/**` are the one legitimate relative target).
- **`MONGODB_URI` is bare; the database name lives in `MONGODB_DB`** — the backend selects with `client[db_name]` (`app/main.py`), and the frontend's NextAuth adapter takes `MongoDBAdapter(client, { databaseName: process.env.MONGODB_DB })`. **Both halves must be given the same value**, or auth and application data land in different databases. Omitting it does not fail — the driver resolves `client.db(undefined)` to the URI's default database, which on a bare URI is the one literally named `test`; that is where staging's NextAuth users and accounts went until #545. Any deploy surface that passes `MONGODB_URI` to the frontend must pass `MONGODB_DB` too (`docker-compose.staging.yml` does, for both services). `__tests__/lib/authAdapterDatabase.test.ts` pins the wiring — it needs virtual mocks because `@auth/mongodb-adapter` is ESM-only (no `require` condition), which is also why `scripts/check-auth-adapter.mjs` rebuilds the adapter instead of importing `auth.ts`. **Since #551 the frontend fails fast (production only) via `assertDatabaseConfig` (`lib/auth-config.ts`, called at `auth.ts` load):** the invariant is "the database is named exactly once and both halves agree", not "`MONGODB_DB` is set" — a bare URI with no `MONGODB_DB` errors (else the silent `test` fallback), a URI whose path DB disagrees with `MONGODB_DB` errors, and a URI that carries the DB in its path with no `MONGODB_DB` still starts (`.env.staging.example`'s shape). The backend reads `MONGODB_DB` and never a URI path; since #694 `app/config.py::resolve_database_name` refuses to start (in every environment) when the URI's path names a different database, reading the URI as text the way the frontend's `databaseNameFromUri` does, and naming only the two database names in the error, never the URI.
- Required: S3 settings, MongoDB URI, OpenAI API key, NextAuth secret
- **Local development does not share a deployed environment's bucket (#878).** The documented `.env` points S3 at LocalStack (`AWS_ENDPOINT_URL=http://localhost:4566`, bucket created once with `awslocal s3 mb`); a real bucket is an opt-in, and never staging's. Before this, local runs and staging wrote to one bucket, so staging's audits counted local artifacts (all 33 "orphans" in #726) and a local delete acted on shared storage. `app.config.development_uses_a_real_bucket()` is true for `ENVIRONMENT=development` with a bucket, credentials and no `AWS_ENDPOINT_URL`, and `S3Service` logs one warning for it per process, however often the service is built (the bucket's name is not in the line). **The test suite pins its own S3 settings:** `tests/conftest.py` assigns `AWS_ENDPOINT_URL` and blanks the three credential variables before any app import, because `app.config` loads `.env` without override and would otherwise hand every unmocked client the real bucket's credentials. So `S3Service` is in mock mode and `get_s3_client()` is `None` locally as in CI; read a credential in a fixture with `os.getenv(NAME) or "test"`, since the variable is set to nothing. `test_suite_never_reaches_aws.py` builds each kind of client and asserts none points at AWS.
- `SKIP_AUTH=true` bypasses auth — honored **only** when `ENVIRONMENT` is `development`/`test`; startup fails hard otherwise (#149). Maps all requests to `dev-user-default`.

## Automated Workflow Configuration
- **Quality gates before PR:** all tests pass, coverage >85%, ruff/eslint clean, mypy/tsc clean, no TODO/FIXME/NotImplemented markers, security scan (OWASP), `scripts/quality/crap.sh` passes (every function the change adds or modifies scores CRAP < 6, so it is small or tested; split or cover it, never skip it. Exit 2 = a measurement is missing: follow the hint and rerun. Backend coverage needs MongoDB). There is no standing exemption: the last two functions over the ceiling, `train_model_task` and `AutoMLEngine.run`, were split in #842, so a function a change touches is split or covered like any other. **In `.tsx` the gate reads with lizard's TypeScript reader, which misreads two shapes (#808):** a typed destructured parameter (`function X({ a }: { a: T })`) leaves the function's coverage unmatched (exit 2, "unverified"), a type-level arrow (`onClick: () => void` in a props type) is counted as an anonymous function with no coverage, and so is a parenthesized JSX ternary (`{x ? (<A/>) : (<B/>)}`, #855; write `{x ? <A/> : <B/>}`). Separately, a component whose body is only `return <JSX>` gets no statement line in jest's LCOV, so the gate cannot place it either. A fourth shape blinds the reader for the **whole file** (zero functions, exit 2): an inline object type as a generic argument, `React.ComponentType<{ className?: string }>` (#825; name the type, or use `LucideIcon`). And a ternary on string literals followed by a `?.` on the next function can leave a function unclosed, so it swallows its neighbours; when the gate's line ranges look wrong, run `uvx lizard -l typescript <file>` and read the ranges. Take `props: {…}` and destructure it in a first statement (`const { a } = props`), which fixes both, and type callbacks as `VoidFunction`, or, when they take arguments, as a method signature (`onSelect(view: View): void`). A generic function declaration (`function f<T>(…)`) is misread as well (#765): its lines come back unmeasured (exit 2), so take `unknown` and cast at the caller.
- **CodeRabbit:** max 3 iterations; auto-fix style/types/simple-bugs/docs. Escalate on iteration-3 failures, architecture changes, or security decisions.

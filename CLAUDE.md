# CLAUDE.md - Project Conventions and Guidelines

## Project Overview
Narrative Modeling App — an AI-guided platform that democratizes machine learning by helping non-expert analysts build, explore, and deploy models without writing code.

> Per-issue implementation history lives in git/PRs, not here. This file holds durable conventions only.

## Architecture

### Frontend (`apps/frontend/`, Next.js)
- App Router, TypeScript strict, Tailwind CSS
- NextAuth v5 (Google, GitHub); frontend mints an HS256 JWT (`sub=userId`) in the session callback for the backend to verify. **That `session.apiToken` is the only credential that may reach the backend (#527).** The OAuth provider's access token is not persisted in the JWT and does not exist on the session any more — three call sites had been forwarding it (Google's credential, sent to our API) and one route sent the literal `"default"` when it had nothing, which the backend rejects but which was only ever one config change from a user. A proxy route with no `apiToken` answers 401; it never forwards a placeholder. `__tests__/lib/noProviderTokenForwarding.test.ts` greps the frontend for `session.accessToken`, `Bearer nextauth-` and `|| 'default'` so the class cannot return.
- **Tailwind v4, CSS-first (#345):** there is **no `tailwind.config.*`** — the whole theme lives in `app/globals.css` via `@theme` / `@theme inline`, `@utility`, `@custom-variant dark`, and `@plugin` (which is the *only* way plugins load; a plugin in `package.json` is not wired until it has an `@plugin` line). Never wrap a theme token in a colour function: the tokens are `oklch`, so `hsl(var(--token))` composes to invalid CSS that browsers **drop silently** — that shipped ~35 dead utilities and a wholly non-functional dark mode, green the whole time. Every semantic token needs a `-foreground` pair defined in **both** `:root` and `.dark`. `__tests__/styles/themeTokens.test.ts` compiles `globals.css` through real PostCSS and guards all of this; component tests can't, since they never run Tailwind.

- **Dark mode is live (#407):** `next-themes` (`attribute="class"`, `defaultTheme="system"`) via `components/ThemeProvider`, toggled from the sidebar. `attribute` MUST stay `class` — `@custom-variant dark (&:is(.dark *))` keys on it, and the `data-theme` default would silently make every `dark:` utility dead again, which is the state #407 found. Components use **semantic tokens** (`bg-card`, `text-foreground`, `text-muted-foreground`, `bg-muted`, `border-border`), never `bg-white`/`text-gray-900`/`bg-gray-50` — those stay light in dark mode and render text invisible. `__tests__/styles/semanticColours.test.ts` enforces this repo-wide; `components/Sidebar.tsx` is the one exemption (deliberately dark in both themes). jsdom has no `matchMedia`, so `jest.setup.js` polyfills it — every suite rendering through the root layout needs it.
- **Public pages are exactly two prefixes (#473):** `middleware.ts` is deny-by-default, and only `/auth/` and `/legal/` are exempt (plus `/api/`, which self-guards with 401). Both checks keep the **trailing slash** so the exemption cannot leak onto a lookalike route — `/legality` stays protected. **Any route added under `/legal/` is public by construction, not by review** — the prefix check cannot tell a policy page from an admin tool for editing one, so a new file there is unauthenticated the moment it exists. `/legal/terms` and `/legal/privacy` must stay anonymous-reachable: Stripe's reviewers, regulators and prospective customers all read them before an account exists, and behind the session wall they satisfy nothing. Their identity, jurisdiction, refund window and sub-processor table live in one place, `lib/legal/company.ts`, which the pages and their tests both read — the sub-processor list is a legal claim, so every row is traceable to the code that sends the data (notably `dataset_summarization.py`, which ships up to 5 sample rows of the customer's dataset to OpenAI). Retention wording is deliberately no stronger than the cascade actually performs (#497 et al. leave trained models behind), so tightening erasure means loosening the policy text, not the other way round.
- **`/admin` is authorised, not just authenticated (#477):** `middleware.ts` rewrites `/admin` and `/admin/*` to Next's not-found route unless the session token's email is on **`ADMIN_EMAILS`** (`lib/admin-allowlist.ts`), so a signed-in tenant gets the same 404 as for a page that does not exist. The rewrite target is Next's *internal* not-found route, so a unit test can only pin the rewrite header — the HTTP status is checked against a real build: `next build && next start`, mint a session with `@auth/core/jwt`'s `encode` (salt `authjs.session-token`), and `curl -o /dev/null -w '%{http_code}' -H "Cookie: …" /admin` must print 404 for a non-listed email (verified on 16.2.12; the RSC navigation fetch legitimately answers 200 with the not-found tree in the payload). The allowlist **fails closed** — unset means nobody is admin, the opposite of `INVITE_ALLOWLIST`'s empty-means-open — and it is the only admin concept in the codebase; there is no role field. `session.isAdmin` is computed server-side in the `auth.ts` session callback purely so the sidebar can hide the link; never make a route decision from it on the client. The admin page's only backend calls (`/health/status`, `/health/metrics`) do not exist (#479); whatever #479 adds must carry its own admin check, because nothing on the backend mirrors this allowlist yet.
- **A space between an interpolation and the prose after it can vanish in the server render (#473).** Observed once, in a `<p>` whose JSX line *began* with `{expr}` and carried a second one mid-sentence: the served HTML read "Narrative Modeling Appservice" while jsdom rendered it correctly, so the component test stayed green. The obvious generalisation ("two interpolations on a line") does **not** hold — sibling lines with the same shape render fine, so do not go hunting by shape. Write `{' '}` explicitly after any `{expr}` followed by prose and the question never arises. No component test can see this; the check is `curl <page> | grep -E '[A-Za-z0-9.,)]<!-- -->[A-Za-z0-9(]'` against a running build, which flags every glued text-node boundary on the page.

### Backend (`apps/backend/`, FastAPI)
- Async FastAPI, MongoDB via Beanie ODM, AWS S3 for files, `BackgroundTasks` for AI/ML work
- Canonical Beanie model registry: `app/models/registry.py` (shared by app lifespan + `setup_database` fixture)

### MCP Server (`apps/mcp/`, FastMCP)
- Exposes `eda_summary_tool` over SSE; called by the backend on the same host. Entry point `main.py`. FastMCP from the installed `mcp` SDK (`mcp.server.fastmcp`), not vendored.

## Backend Conventions & Recurring Gotchas
- **`app/api/routes/__init__.py`'s `api_router` is attached to nothing (#471, removal in #530).** A router registered only there is dead: the whole data-issues feature 404'd that way while the frontend called it. Mount routers in `app/main.py` directly; `tests/test_api/test_every_router_is_mounted.py` walks the live route table and fails on any route module that is not mounted unless it is allow-listed there with the reason (`trained_model`, legacy CRUD). A feature that has never been reachable has never had its authz, metering or error paths exercised — review it as new code when you mount it (#471 needed `quota("ai_calls")` on `/detect`, released when the analyzer did not run, and the metering registry now follows one import hop so a route reaching a model *through a service* is in scope).
- **Two model surfaces:** `MLModel` (routes under `/api/v1/ml/`) is the **real** trained-model surface — build everything here. `ModelConfig` (`/api/v1/models/`) is **dead legacy**, never created by the training flow; its train/deploy/performance routes are `410 Gone`. Bot plans (Traycer/CodeRabbit) routinely target the wrong one.
- **Schema ↔ type mirrors:** backend Pydantic schemas mirror frontend TS types — change both together. Notably `app/schemas/evaluation.py` ↔ `apps/frontend/lib/types/evaluation.ts`.
- **`MLModel` mock fixture:** adding any optional `MLModel` field breaks the `sample_ml_model` MagicMock under `response_model=MLModel` validation unless the fixture sets it. Recurs constantly.
- **New optional fields degrade:** add `MLModel`/schema fields as optional/defaulted so pre-existing models still validate and endpoints return `partial=true` rather than 500.
- **Route order:** register specific `/ml/{model_id}/<sub>` routes **before** the catch-all `/{model_id}`.
- **Every handler in an authenticated router carries the auth dependency itself (#450, #563):** routers are mounted without router-level `dependencies`, so a handler that forgets `Depends(get_current_user_id)` is public by construction — `/ai/health` sat that way, reporting internal deployment state and making an outbound MCP call for anyone. A health-style endpoint belongs in `health.py` only if it is a readiness dependency of the app; otherwise it is authenticated like its siblings.
- **AI services:** OpenAI (JSON mode) behind the shared circuit breaker + a deterministic rule-based fallback — endpoints must work fully **without** an API key.
- **Removable dependency levers:** heavy optional deps live in PEP 735 `[dependency-groups]` (`interpretability` = shap/numba stack; `tuning` = optuna), kept in `default-groups`, lazy-imported. Slim image: `uv sync --frozen --no-dev --no-group <group>`; the app degrades gracefully.
- **Error handling (#269):** central handlers in `app/middleware/error_handlers.py` sanitize **all 5xx** (generic body + `X-Request-ID`, never echo `str(e)`) and pass 4xx validation text through. Do not reintroduce `str(e)` in 5xx bodies. The sanitiser never sees a **200 `{success: false}`** body, and those used to carry `error=str(e)` too (data-issues, transformations — #637): a handler that reports failure in a 2xx body uses `internal_error_message("<What>")` from the same module (fixed sentence + the request id as the reference the operator greps the logs for) and logs the traceback with `logger.exception`; domain errors with a user-facing `.message` (`ValidationError`, `OperationError`) are the only exception text that may pass through. `tests/test_api/test_error_bodies_are_sanitized.py` forces a failure into every such route and asserts the body carries neither the message nor the S3 key.
- **Two dataset id-spaces:** `DatasetMetadata` (string `dataset_id`, S3 `datasets/{user}/...`, string-keyed children) and legacy `UserData` (ObjectId, `Link` DBRef children) are **dual-written**, linked only by `(user_id, s3_url)`. Deletion cascades across both via `DatasetErasureService` (#259). **That link is mutable, so every writer that moves a dataset to a new file must move both twins (#467):** go through `app/services/dataset_link.py::record_new_file(doc, new_url)`, which finds the twin through the *old* location and points both `file_path` and `s3_url` at the new one (the first move keeps the upload in `DatasetMetadata.source_s3_url`). Writing `s3_url` on one side alone is how erasure lost the PII-carrying twin and training — which reads `UserData.s3_url` — kept using the pre-transform file while the UI showed the transformation applied. `scripts/inventory_dataset_links.py` counts pairs whose link is already broken.
- **Chunked upload (#454, #462, #463, #464):** the flow was broken end-to-end until #582 and its four defects had to land together, so treat it as one surface. Init takes **`Form(...)`**, not query params — the client posts a url-encoded body, and the mismatch 422'd every init before the handler ran. Sessions are owned: `init_upload` records `user_id`, ids come from `secrets.token_urlsafe` (never derived from filename/size/timestamp), and every operation resolves through **`get_session(session_id, user_id)`**, which returns `None` for both unknown and foreign ids so the two answer identically — a distinguishable response confirms another tenant's session id exists. Session ids are also spliced into filenames under `temp_dir`, hence the `[A-Za-z0-9_-]` guard. `complete` **claims** the session (reads and removes it in one synchronous step) before any await: there is no await between the lookup and `user_data.insert()`, so two racing completes otherwise both pass the checks and write two S3 objects, two `UserData` rows and two charged quota units, both 200 so nothing refunds. Its body runs under `try/finally` — the concurrency slot is released on **every** exit, and exactly once (one `start_upload` at init; releasing in the chunk route *as well* pinned the count at 0 and stopped the cap binding). S3 keys are **server-derived**, `datasets/{user_id}/[masked_]{uuid}.{ext}`, built only by `dataset_s3_key` in `app/utils/s3.py` — every dataset-writing route (`/upload/`, `/secure`, `/confirm-pii-upload`, chunked `complete`) calls it, and there is deliberately no helper that can express a key without the owner (#581 deleted `generate_s3_filename`, which three routes were still reaching for). The client filename is metadata only and must never reach the key. Objects written before #581 sit at the bucket root as bare `{uuid}.{ext}`; `scripts/reconcile_unprefixed_s3_keys.py` moves them under their owner (copy, verify ETag+length, rewrite `UserData`/`DatasetMetadata`, then delete; orphans reported, never touched; dry-run by default). Erasure's `_s3_key` derives keys through the same `parse_s3_url` the readers use (#481) — the hand-rolled parser it replaced returned `bucket/key` for endpoint-style URLs and kept presigned query strings, so `delete_object` matched nothing and erasure reported success over a surviving object. The sibling routes `/secure` and `/confirm-pii-upload` still enforce a high-risk-PII confirmation gate the chunked route does not (#583).
- **Client filenames are normalised at the model (#585):** `UserData` and `DatasetMetadata` run `sanitize_filename` on `filename` / `original_filename` — basename only, no control characters, no leading dots, ≤255 chars, never empty — so every writer (`/upload/secure`, `/confirm-pii-upload`, `/chunked/{id}/complete`, `/upload/`, `/datasets/upload`, and the next one) stores the same safe form. Both documents also set `Settings.validate_on_save = True`: Pydantic validates on construction, not on assignment, so `PUT /user_data/{id}`'s `setattr` path skipped the validators until save re-ran them and no consumer building a `Content-Disposition` header or a path from them has to know they were once raw. The S3 key never came from the filename (#464); this closes the stored copy. Normalise rather than reject: exporters produce odd-but-honest names, and a raw copy "alongside" would keep the trap.
- **Which S3 location to download (#170, #466):** `s3_url` is always a URL; `file_path` is a **raw key** right after an upload and a **full URL** once a transformation has written one back. The validated downloader takes only URLs, so `file_path or s3_url` handed a key to it and the *first* transformation on every dataset failed while every later one worked. Never branch on the shape yourself — go through `app/utils/s3.py::downloadable_url(file_path, s3_url)`, which passes a URL through and places a key in the allowed bucket; the strict resolver then checks it like any other URL. `S3Service.download_file_bytes` is the one *key-only* entry point — feed it the key from `resolve_validated_object(downloadable_url(...), allow_legacy_root=True)` (bucket allowlist checked *before* the key is extracted; the allowance keeps pre-#581 root-level datasets readable until #615), never `file_path` directly. Only a LocalStack test (`tests/test_integration/test_transformation_first_apply_localstack.py`) can see this class of bug; a mocked downloader accepts anything.
- **`UserData.id` is an ObjectId; a request id is a string (#465):** `UserData.id == file_id` and `{"_id": request.dataset_id}` build `{"_id": "<str>"}` and match nothing — ten endpoints answered a permanent 404 while their tests patched `find_one` and stayed green. Coerce with `app/utils/object_id.py::require_object_id(value, what)` (400 on a malformed id); only `Document.get(str)` is coerced by Beanie itself. A handler that wraps its lookup in `try/except Exception` must `except HTTPException: raise` first, or the 404 becomes a 200 `{success: false, error: "404: …"}` — which is what the four `transformations.py` handlers did. Tests for a lookup must seed a real document; a patched `find_one` cannot see this class of bug.
- **One S3 download core (#531, #567):** every read of a stored URL or key goes through `app/utils/s3.py` — `resolve_validated_object()` (parse → `allowed_bucket()` → `validate_object_key()`) and `check_object_size()`. Exactly one `get_file_from_s3` (utils, BytesIO) and one `download_file_from_s3` (`s3_service`, temp file) exist, both on that core; `S3Service.download_file_bytes` validates its key the same way. **No route or service may call boto3's `get_object`/`download_file*` itself** — `tests/test_services/test_s3_download_registry.py` finds any raw download outside the core and fails, which is how `column_stats.py` and the preview route were caught bypassing the allowlist. The BytesIO reader alone admits the pre-#581 root-level `(masked_){uuid}.{ext}` shape (`allow_legacy_root=True`) because production `UserData.s3_url` still points at those objects until the operator runs #615; that flag is the one line to flip afterwards. The temp-file path stays strict. **Only the download surface is validated:** `S3Service.upload_file_obj`, `delete_file`, `get_file_size` and `generate_presigned_url` take server-derived keys against the configured bucket without going through the core — do not hand them client input. Every reader now pays one `head_object` for the size cap before the read.
- **Transformation engine contract:** the engine maps only a few transform types; `FILL_MISSING` uses `method` (mean/median numeric-only). The `/datasets` upload path stores `data_schema=[]` with real columns in `inferred_schema` (a `SchemaInference` dump).
- **Changing an existing index's options needs a new index name (#565).** Beanie builds indexes at `init_beanie`; turning `Indexed()` into `Indexed(unique=True)` keeps the name `experiment_id_1`, and Mongo refuses to rebuild an existing name with different options (`IndexOptionsConflict`), so the app would fail to start against any collection that already has the old index. Declare the new one as a named `IndexModel` in `Settings.indexes` (`experiment_id_unique`), leave the legacy index to `scripts/check_ab_test_duplicates.py --drop-legacy-index`, and run that script's duplicate check before the first deploy — a unique index that cannot build also fails startup.
- **Beanie `save()`** surfaces a unique-index violation as `RevisionIdWasChanged`, not `DuplicateKeyError`.
- **Artifact integrity (#266):** model artifacts are HMAC-SHA256 signed (signature in Mongo, bytes in S3); joblib/pickle loads verify before deserializing and refuse on mismatch.
- **Model export (#468):** `ModelStorageService.load_model(model_id, user_id)` is tenant-scoped and returns a **tuple** `(model, feature_engineer)`; `ModelExportService._load_owned` is the one place that calls it, after `_owned()` has answered 404 for a model the caller does not own (checked *before* the converter-availability check, so a missing converter never changes the answer for someone else's model). Every export route maps `NotFoundError` → 404, `ExportFormatUnavailable` → 501 (body sanitised by the 5xx handler; `/export/formats` carries `available` flags), other `ValueError` → 400. ONNX lives in the `export` dependency group — in `default-groups` so dev and CI run the real conversion, excluded from the image by the Dockerfile's `--no-group export` (so production answers 501 unless that flag is dropped); PMML needs a Java runtime, has no group, and is advertised/served only when `java` is on the path. The Docker ZIP ships `model.pkl`/`feature_engineer.pkl` pickled from the loaded artifacts with `requirements.txt` pinned to the pickling scikit-learn/numpy/pandas — but `feature_engineer.pkl` is the platform's own `FeatureEngineer`, whose module the container cannot import (#632), so only models saved without a feature engineer run standalone today. The test for this surface must mock `load_model` with the real signature and tuple; the old suite mocked a dict-returning one-argument shape and stayed green while every format 500'd.
- **Model cache + inference (#265):** `_ModelArtifactCache` is a TTL-LRU keyed by `(model_id, user_id)`, invalidated on delete/retrain/deploy. All inference routes through `run_locked_inference` (per-model lock + `to_thread`).
- **datetime:** use `datetime.now(UTC)` / the `app/utils/datetime.py` helpers (`utcnow`, `as_utc`). Mongo reads datetimes back **naive** — coerce stored values with `as_utc` before arithmetic against aware `now`.
- **Plan enforcement (#368):** `app/billing/enforcement.py`. `quota(<metric>)` is a route dependency that **atomically reserves** a unit via `metering.consume()` — one conditional `$inc` (`units <= limit - amount` + `upsert`), where a record already at the cap misses the filter, the upsert collides with the unique index, and that `DuplicateKeyError` **is** the denial. Answers **402** (not 429 — that's #151's) with limit/used/resets_at/upgrade_available. **Enforcement is the only thing that counts these metrics** — a guarded route must NOT also call `metering.record()`. `QuotaRefundMiddleware` returns the reserved units on any >=400, so a malformed upload doesn't burn quota — it refunds the **reserved amount against the reserved period**, since a request that fails across a month rollover would otherwise credit a month it never charged. JSON predict routes use `quota(..., per_record=True)` — a `predictions` limit must count predictions, not requests, or batching becomes the way around it. **A batch retry charges like a creation (#460)** — it re-reads the same S3 input from the start (there is no resume), so it re-executes the *full* `progress.total_records`, which is the field to size the reservation from (set at creation, deliberately not reset by `retry_job`; note it is the service's pandas count, which can differ by one from the route's `_count_csv_rows` on a trailing blank line). `retry_job` **claims** the job with one conditional `find_one_and_update` carrying every precondition — status and a `$expr` retry-budget check — because read-check-write let a double-click spawn two processing tasks over one document. The route's own 404/409 checks exist for the *message*, not the mutual exclusion. Batch jobs count their CSV rows (stdlib `csv`, so a quoted newline isn't a row) and reserve them **before creating the job** — creation `auto_start`s processing, so a check afterwards would have to unwind a running job, and an unconditional true-up isn't a limit at all (`MAX_BATCH_PREDICT_RECORDS` is 1000x the FREE ceiling). Reservations on one request **accumulate** rather than replace: a batch reserves twice, and overwriting silently burns the first on every failed job. Enforcement fails **closed** (a storage error denies); `record()` fails open. Any test hitting a metered route needs `setup_database` — the dependency reads `Subscription`, and class-level Beanie field access raises `AttributeError` without an initialised Beanie. **Model calls are metered too (#461):** `ai_calls` is the fourth metric, and it is the one ceiling that is **finite on every tier, ENTERPRISE included** — it is the backstop against an unbounded OpenAI invoice, so `plans.py` reads it through `_env_positive_int` and a `-1` override falls back and warns rather than uncapping it. Every route that can reach a model carries `quota("ai_calls")`, including the two 501 stubs in `ai_analysis.py` (so #274 cannot reopen the hole) and `ai_orchestration.py`'s `/recommend-tools` and `/stage-guidance`, whose "rule-based" service takes an OpenAI pass whenever a key is present; `tests/test_billing/test_ai_routes_are_metered.py` is the registry for `/api/v1/ai` (all methods, not just POST). **The Next.js `/api/chat` proxy must never call OpenAI itself** — it did, outside every backend control, so the monthly ceiling did not apply to it; it now forwards to the backend's `POST /ai/chat` (fail-fast bounds, API JWT) and the frontend has no `openai` dependency at all. **Every AI route has a rule-based fallback, and a fallback is not a paid call:** the route must `enforcement.release(request)` when the service reports no model ran — `generated_by != "openai"` (report card, error suggestions), `generated_by != "hybrid"` (orchestration), `metadata["ai_used"]` false (feature suggestions) — or a keyless deployment bills, then blocks, purely local analysis. A service that gains a model call must also gain that signal. `/billing/status` derives its `limits` from `METERED_METRICS`, never a hand-written tuple, or the billing page silently hides a metric.
- **Entitlement (#366, #458, #510):** `Subscription.is_entitled` is the single predicate; `effective_tier` is what callers read (`plan_tier` alone keeps serving PRO to a lapsed row). It requires **both** an entitled status **and** an unlapsed period. `PAST_DUE` is entitled on purpose — Stripe is still retrying — but `unpaid` is **not**: that is the status a subscription reaches once Stripe has *given up*, and mapping the two together handed permanent paid access to a customer whose payments had permanently failed. Never re-merge them. The period check exists because status is only as fresh as the last webhook and nothing reconciles on a schedule, so without it one dropped event grants a tier forever; the grace is **per status** and the two must not collapse into one: `ENTITLEMENT_GRACE` (3 days) absorbs delivery lag on an ACTIVE row whose renewal already happened, while `DUNNING_GRACE` (30 days) covers PAST_DUE, because Stripe's Smart Retries run out to ~4 weeks and a single 3-day window would cut off on day three a customer whose card succeeds on day eight — silently rescinding the serve-through-dunning policy stated right above it. A **missing** `current_period_end` falls back to `updated_at` + the same grace — bounded, never "entitled forever", which is the same bug wearing a different field. Both values come back from Mongo naive, so both go through `as_utc`. `current_period_end` itself lives on the subscription **item** in the pinned API version (`STRIPE_API_VERSION` in `stripe_client.py`, guarded by `tests/test_billing/test_stripe_api_version.py` against the SDK's own constant — *not* `stripe.api_version`, which `_client()` overwrites, making that assertion pin==pin); `_period_end()` reads the legacy top-level location first and the item second, and must never clear a known value on an event that omits it. `scripts/reconcile_subscriptions.py` is the repair path for the other direction (a missed **renewal**, which no local rule can fix) and the backfill for pre-#510 rows; it reconciles **tier as well as status** — an upgrade changes only the price, so a status-and-period comparison reports "everything matches" while an ENTERPRISE customer is enforced as PRO — and its write is conditional on `updated_at` so a webhook landing mid-run is not overwritten.
- **Training config is bounded per tier (#500):** `POST /ml/train` takes typed `TrainingConfigRequest` / `TuningConfigRequest` / `FeatureConfigRequest` with `extra="forbid"` — an undeclared knob cannot reach the engine, so add new engine knobs to the request model *and* to `TrainingCeilings` in `app/billing/plans.py` (the single source of per-tier ceilings), or they are unreachable. Anything over the caller's ceiling is a **422 naming the knob, value and limit — never clamped** (a clamped run trains a model the caller did not ask for). Estimator hyperparameters (`n_estimators`, `max_depth`) are not caller-reachable at all — the tuner's search space is server-defined. Every run ends at the tier's `wall_clock_seconds` via `asyncio.wait_for` in `train_model_task`; the engine's own `time_limit` is *soft* (checked between candidates, after the tuning phase) and stops nothing by itself. A fit already inside a worker thread cannot be killed — the job is marked FAILED and the thread finishes on its own. FREE's ceilings must stay >= the `comprehensive` mode preset (`tests/test_billing/test_training_ceilings.py` guards it) or that mode silently disappears for free users.
- **Metering the upload surface (#459):** `quota("uploads")` belongs on **every** route that creates a dataset, and there are more of them than the name "upload" suggests — `/upload/secure`, `/upload/confirm-pii-upload`, `/upload/chunked/{id}/complete`, `/upload/`, `/datasets/upload`, and `onboarding/sample-datasets/{id}/load` (store.py's bare `POST /api/v1/`, which could never succeed, was removed in #472) (a sample load inserts a full `UserData` unconditionally, so unmetered it mints datasets without limit). `datasets/{id}/features/{fid}/apply` reserves **inside the handler**, only when `create_new_dataset` is true — a route dependency would bill every in-place apply. `tests/test_billing/test_dataset_routes_are_metered.py` is a **registry**, not a list of per-route tests: it walks the live route table and fails on any unclassified POST under its prefixes, which is the only thing that catches a new route. Note its two real limits — it polices **only** the prefixes in `_IN_SCOPE_PREFIXES` (a dataset-creating route mounted elsewhere is invisible; that is exactly how the onboarding loader was missed), and `app.routes` is **not flat** on FastAPI 0.139 — routers are lazy `_IncludedRouter` wrappers, so the naive `isinstance(r, APIRoute)` walk finds almost nothing and cheerfully reports that everything is metered. A 2xx that does no work must hand its unit back with `enforcement.release(request)` — the refund middleware only sees >= 400, and `/upload/secure`'s high-PII branch answers 200 having created nothing, which was charging a unit there *and* again at `/confirm-pii-upload`.
- **Rate limiting (#151, #455, #483):** global `RateLimitMiddleware` on all `/api/v1`; per-key buckets only on `/production/v1/models`. Anonymous requests are keyed on the socket peer, or on **`X-Real-IP`** when `RATE_LIMIT_TRUST_PROXY` is set — nginx sets that header from `$remote_addr` and *overwrites* it, so behind the proxy it is authoritative (one hop only: a CDN or LB in front of nginx would make `$remote_addr` the LB, which needs nginx's `real_ip` module — no such layer exists today). **`X-Forwarded-For` is never read**: nginx *appends* to it, so element `[0]` is whatever the client sent, and reading it under either flag setting let a caller mint a bucket per request. The flag only helps if compose passes it (`docker-compose.staging.yml` does; before #483 it did not, so staging bucketed every anonymous request under nginx's container IP) and every backend `location` sets the header — `tests/test_security/test_nginx_real_ip.py` pins both. **Disabled in the test env** — a test that means to exercise the limiter must build the middleware with `enabled=True`, or its 429 assertions are vacuous. Both stores read `limit <= 0` as **no enforcement**, so a per-key `rate_limit` of 0 does not throttle, it *removes* the only control on the paid serving surface. Hence three guards, all needed: `CreateAPIKeyRequest.rate_limit` is `ge=1`; `app/billing/api_keys.py` clamps it to `api_key_rate_limit_ceiling(tier)` at creation **and** re-clamps a tenant's keys from the Stripe webhook's `_apply` on every subscription save (the limiter never reads a subscription on the hot path, so nothing else would revisit a key minted under a richer tier); and the middleware floors the stored value at 1 for rows written before that. Every tier's ceiling in `plans.py` must stay **finite** — and note the trap: `UNLIMITED` (-1) is that module's documented "no ceiling" sentinel for *every other* limit, but for a rate limit it means the opposite, so `PLAN_*_API_KEY_RATE_LIMIT` reads through `_env_positive_int`, which refuses a non-positive override, warns, and falls back to the default rather than bricking the tier at 1/window. `api_key_rate_limit` is deliberately **not** in `METERED_METRICS`: it is a throughput ceiling, not a per-period counter, and `limit_for` rejects it. `scripts/fix_api_key_rate_limits.py` audits/repairs existing rows.
- **Redis cache surface (#452):** the whole user-facing cache API is `DELETE /api/v1/cache/me`, scoped by the token. **Never build a Redis pattern from caller input**, and never leave one unanchored: rate-limit buckets (`ratelimit:<identity>`) share this Redis, so a `*:{user_id}*` glob purges the caller's own limiter — which is how a cache route became a limiter bypass. A user-scoped key family must be declared in `_USER_SCOPED_KEYS` (exact) or `_USER_SCOPED_PATTERNS` (anchored to a literal namespace prefix, id glob-escaped) in `app/services/redis_cache.py`, or `/me` silently stops purging it. `delete_pattern` stays available for **server-built** patterns (`viz:{dataset_id}:*`, `stats_{dataset_id}_*`).
- **Version ownership (#446–#448, #453):** everything under `/api/v1/versions` and `/api/v1/datasets/{id}/versions` authorizes on **`DatasetVersion.user_id`** (server-set, indexed) via the `require_owned_dataset` / `require_owned_version` helpers in `app/api/routes/versions.py`. Call them **outside** the handler's `try` — the module's broad `except Exception` blocks turn a 404 into a 500, and `compare_versions` has no `except HTTPException: raise` at all. Unknown and foreign ids must answer identically, and the ownership check runs **before** any other guard, or the guard's own 400 (`Cannot delete base version`) becomes an existence oracle. `versioning_service.get_version(user_id=...)` compares against the same `DatasetVersion.user_id` since #453 (it used to join to `DatasetMetadata` and read `if dataset and ...`, so a version whose dataset row was gone **passed**); `create_transformation_version` resolves its parent through it (#559), so a parent the caller does not own is refused inside the service — a caller that skipped its own guard is no longer a hole. Scoping the entry point is not enough for lineage — `get_lineage_chain` and `compare_versions` walk `parent_version_id`, so they take a `user_id` and stop at the first hop the caller does not own, or another tenant's lineage reaches `lineage_chain`/`lineage_path`/`transformation_count`.

### Test footguns
- **Route tests (#267):** `tests/test_api/conftest.py::mock_async_client` mounts only `health` + `secure_upload`, so requests to any other router 404 and `assert x in [200, 404, 422]`-style checks pass vacuously. Use **`async_authorized_client`** (full app, auth overridden) + real Mongo docs and assert **exact** statuses. For the X-API-Key production surface, insert a real `APIKey` and pass the raw `sk_live_…` header. The in-memory `prediction_log` is process-global and never cleared by `setup_database` — reset it when asserting per-model counts.
- **Frontend lint is warning-capped (#333):** Next 16 removed `next lint`, so `npm run lint` is `eslint . --max-warnings 233`. The ceiling is deliberate and ratchets **down** as debt clears — never up to accommodate new warnings. **Adding one new warning anywhere (a stray `any` is the usual culprit) fails CI even though nothing errored.** Fix the warning, or lower the number deliberately — never widen `globalIgnores` to dodge it. Lint scope is the whole project, not `next lint`'s `app`/`components`/`lib`, so `e2e/` and `__tests__/` are linted too (with `no-console`/`no-require-imports` relaxed there).
- **React Compiler rules (#373 → #393):** four of the five `eslint-plugin-react-hooks` v7 rules are burned down and enforced as **`error`** (`immutability`, `static-components`, `refs`, `preserve-manual-memoization`) — reintroducing one fails the build. Only `set-state-in-effect` is still `warn` (46 sites, #393), which is what keeps the `react-compiler-rules-pending-burndown` block alive and `reactCompiler: true` off. **Counts from these rules are lower bounds:** the compiler bails out of a component at its first error, so fixing one rule can *reveal* more violations of another — clearing `immutability` raised `set-state-in-effect` from 26 to 46. Re-measure after each batch instead of working a fixed list.
- **`apps/frontend/__mocks__/` auto-applies to EVERY suite (#390):** it sits next to `node_modules`, so jest uses those manual mocks for node-module imports with **no `jest.mock()` call anywhere**. A mock left on an old major's API does not fail loudly — it keeps rendering from props the real library ignores, turning a broken component into a green suite. This bit exactly once already: after the react-window v1→v2 migration, `ColumnSelector`'s 53 tests failed correctly while `BulkColumnSelector`'s 16 **passed against an equally broken component**, because that suite also declared its own inline v1 mock. When bumping a mocked dependency's major, **update the mock in the same PR and make it throw on the old prop shape**, then mutation-check it (revert the component; the tests must fail).
- **Charts run against real recharts (#346):** every chart suite mocks **only** `ResponsiveContainer`, via `jest.mock('recharts', () => jest.requireActual('@/__tests__/utils/sizedRecharts').sizedRecharts())`. jsdom lays out 0×0, so the real container measures zero and renders nothing — that is the *whole* reason the old suites stubbed every primitive as a prop-ignoring passthrough, which made them blind to the library (pointing every `dataKey` in `ROCCurveChart` at a nonexistent field passed all 5 tests). Assert on drawn output: `axisTicks(container, 'x'|'y')` from the same helper (recharts 3 hoists tick labels into `.recharts-{x,y}Axis-tick-labels`, **not** under `.recharts-xAxis`), `.recharts-bar-rectangle`, `.recharts-line-curve[d]`, `.recharts-reference-line line`. Two things jsdom still can't do: recharts resolves the tooltip's active index from mouse geometry, so `Tooltip` stays a clone-injecting stub in `BarChart`/`LineChart`, and chart-level `onClick` fires with every field null. **A recharts major's breakages have been type-level, not runtime** — v3 spreads the datum onto the item it hands `onClick`, so reverting an adapter to the v2 shape leaves jest green and only `tsc` catches it. Do not treat a green chart suite as migration evidence without a `tsc` run.
- **E2E shares one user, so shared-state specs need their own project (#550):** `onboarding.spec` resets the test user's onboarding progress and walks it back; under `fullyParallel` + 2 workers, every other spec's dashboard visit inside that window hits the #152 first-time redirect. It runs in `chromium-smoke-onboarding` / `chromium-full-onboarding` with `dependencies` on the main project — any new spec that resets shared backend state goes the same way. When a smoke run goes red after a dependency bump, read the artifacts before retrying: `error-context.md` is the page snapshot at failure and `trace.zip` carries every response body under `resources/<sha1>`; that is how a "flaky" batch-prediction test turned out to be `isMountedRef` cleared on cleanup and never re-armed (StrictMode runs cleanup, then the effect again).
- **Frontend jest.setup (#268):** the global `beforeEach` sets `global.fetch` to **reject** by default — any test that fetches must stub `global.fetch` explicitly. `useRouter()` returns a stable per-test spy at `global.__NEXT_ROUTER_MOCKS__` (`push`/`replace`/…) for asserting redirects. Contract locked by `__tests__/setup/jestSetupContract.test.tsx`. Radix tabs need `mouseDown`+`mouseUp`+`click`, not a bare `click`.

## Environment Variables
- Frontend: `.env.local` | Backend: `.env`
- **`NEXT_PUBLIC_API_URL` includes the version prefix** — `http://localhost:8000/api/v1`, matching `.env.local`, the Dockerfile dummy and `ci.yml`. Append only the resource path (`${API_BASE_URL}/datasets/...`); never re-add `/api` or `/api/v1`, and never "normalize" with `.replace(/\/api$/, '')` — that strip matches nothing and hides the mistake. Getting this wrong 404s silently: it broke the AI Insights panel and chunked-upload resume for as long as they existed, and the suites missed it because they built the expected URL with the same expression as the code (#406). `__tests__/lib/apiUrlConstruction.test.ts` pins the paths against the real FastAPI route table. **The other way to get it wrong is no base at all (#470):** the onboarding page and `SampleDatasetSelector` called `fetch('/api/v1/onboarding/…')` — relative to the *frontend* origin, so a 404 with no auth header, on the screen every first-time user is redirected into — and the e2e mocks matched on `url.includes()` so they never noticed. All onboarding calls go through `lib/services/onboarding.ts` now, and the same test file bans bare relative `/api/v1` literals in `app/`, `components/` and `lib/` (Next.js route handlers under `app/api/**` are the one legitimate relative target).
- **`MONGODB_URI` is bare; the database name lives in `MONGODB_DB`** — the backend selects with `client[db_name]` (`app/main.py`), and the frontend's NextAuth adapter takes `MongoDBAdapter(client, { databaseName: process.env.MONGODB_DB })`. **Both halves must be given the same value**, or auth and application data land in different databases. Omitting it does not fail — the driver resolves `client.db(undefined)` to the URI's default database, which on a bare URI is the one literally named `test`; that is where staging's NextAuth users and accounts went until #545. Any deploy surface that passes `MONGODB_URI` to the frontend must pass `MONGODB_DB` too (`docker-compose.staging.yml` does, for both services). `__tests__/lib/authAdapterDatabase.test.ts` pins the wiring — it needs virtual mocks because `@auth/mongodb-adapter` is ESM-only (no `require` condition), which is also why `scripts/check-auth-adapter.mjs` rebuilds the adapter instead of importing `auth.ts`.
- Required: AWS credentials, MongoDB URI, OpenAI API key, NextAuth secret
- `SKIP_AUTH=true` bypasses auth — honored **only** when `ENVIRONMENT` is `development`/`test`; startup fails hard otherwise (#149). Maps all requests to `dev-user-default`.

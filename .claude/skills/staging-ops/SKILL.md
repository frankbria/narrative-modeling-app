# Staging operations

Staging access rules (ssh staging-ts only) are in the root CLAUDE.md. Runbooks: docs/ops/.

- **Deploys:** `deploy.yml` ships `main` → staging over SSH via the tailnet (`HOST` must be the tailnet name/address, labelled the same in `SSH_KNOWN_HOSTS`; port 22 is firewalled publicly). `integration-tests.yml` is manual.
- **Every workflow step reaches the box through `scripts/deploy/on_box.sh` (#790, #756)**, never its own `ssh`: a repo script or a QUOTED heredoc (`<<'REMOTE'`) reading `"$DEPLOY_PATH"` from env. It quotes with `printf %q` and runs the body from a file with stdin at `/dev/null`. `test_deploy_on_box.py` fails on a raw `ssh` or `'$DEPLOY_PATH'` in a workflow.
- **Staging health (#552, #756, #757, #768, #973):** `python -m app.health_probe` (in the backend container) checks `/health/ready` plus a fresh Mongo connection, S3, OpenAI and `signups_24h` (> `SIGNUP_ALERT_THRESHOLD_24H` is unhealthy); every status must be `healthy` or `healthy (<detail>)`, and failures print a class name or HTTP status, never a message. `scripts/deploy/frontend_probe.sh` asks the frontend's `GET /api/health/ready` (`lib/health/readiness.ts`: fresh Mongo connection + a backend-verified minted token) from inside the container; that route must stay unreachable through the edge. `staging-health.yml` runs hourly and opens/closes a `[P1] [ops]` issue deduped on `Staging health probe is failing`; `deploy.yml` gates on `/health/ready` then the probes. On failure, `scripts/deploy/backend_state.sh` reports container state and an exception-*class* histogram, never raw log lines (public repo). Credential rotation: `docs/ops/CREDENTIAL_ROTATION.md` (`up -d --force-recreate`, never `restart`; `test_staging_health_wiring.py`).
- **Staging env vars (#457, #474):** a variable reaches a container only if `docker-compose.staging.yml` lists it. `scripts/deploy/preflight_staging_env.sh` requires every `${VAR:?}` there, so mark a new variable `${VAR:-}` until it is provisioned. Optional passthrough arrives as `""`: treat blank as unset, and every consumer reads through the same accessor (`stripe_client.setting()`). `PLAN_*` overrides are passed nowhere in deployment (`test_plan_limits_are_the_product_values.py`); only `apps/frontend/test-e2e.sh` sets them.
- **Edge config (#594, #789, #830, #768):** `nginx-staging.conf` is a template rendered and deployed by `scripts/deploy/apply_nginx_conf.sh` (placeholders in `SUBST_VARS` only, `test_nginx_template.py`; `sed`, not `envsubst`; no-op until `NGINX_SERVER_NAME` is set; restores the backup if `nginx -t` fails; `--check` diffs the box). An edge fix ships only when a deploy runs. The Stripe webhook (`POST /webhooks/stripe/webhook`, outside `/api/v1`) needs its own `location` with `client_max_body_size` (`test_nginx_webhook_route.py`). Each `app/api/**` handler needs a frontend location (`test_nginx_next_api_routes.py`; `/api/health` is the exemption). `/api/auth/` is rate-limited (`narrative_auth` zone; `test_nginx_auth_rate_limit.py`). Only the production host is indexable (`map $host $narrative_robots_tag`); no `location`/`if` may declare its own `add_header` (`test_nginx_noindex.py`). Certificates via `certbot certonly`, before `NGINX_SERVER_NAME` names the host.
